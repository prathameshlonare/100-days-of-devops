## Part 1: Why Kubernetes Exists & The Core Mental Model (20 min)

### The Docker Limitation: The "Single Ship" Problem
Back in Phase 3, you built Docker containers using `docker run` and `docker-compose`.
Docker is great for running containers on **one single machine**. But imagine Dorm-and-Dish in production with 100 microservices across 15 cloud servers:
1. **No Automatic Self-Healing:** If a VM crashes or an API container dies at 3 AM, Docker does not automatically resurrect it on a healthy server.
2. **No Intelligent Scheduling:** If server #3 has 90% CPU usage, Docker has no scheduler to automatically deploy container #51 onto server #7 where memory is free.
3. **Fragile Networking & Discovery:** When containers restart, their IP addresses change. In Docker, your frontend has to manually track changing IP addresses.

### The Analogy: Port Master vs Ship Captain
- **Docker / Containerd:** The **Ship Captain**. It is responsible for running the engine of a single ship (one container on one machine).
- **Kubernetes (K8s):** The **Port Master**. It directs an entire fleet of hundreds of ships across many docks (nodes). If a ship sinks, the Port Master commissions an identical replacement immediately.

---

### The Kubernetes Architecture (Master vs Worker)

A Kubernetes cluster is split into two distinct tiers:

```
┌────────────────────────────────────────────────────────────────────────┐
│                   CONTROL PLANE (The Master / Brain)                   │
│                                                                        │
│   [ kubectl ] ──▶ [ kube-apiserver ] ◀──▶ [ etcd (State Database) ]   │
│                          ▲                                             │
│            ┌─────────────┴─────────────┐                               │
│            ▼                           ▼                               │
│   [ kube-scheduler ]        [ kube-controller-manager ]                │
└────────────────────────────────────────────────────────────────────────┘
                                   │
              (Sends PodSpecs via TLS to Worker Nodes)
                                   │
┌──────────────────────────────────▼─────────────────────────────────────┐
│                       WORKER NODE (The Muscle)                         │
│                                                                        │
│   [ kubelet ] ──────▶ [ Container Runtime (containerd) ]               │
│        │                          │                                    │
│        │                          ▼                                    │
│        │                 ┌──────────────────┐                          │
│        │                 │  POD (Nginx App) │                          │
│        │                 └──────────────────┘                          │
│        ▼                                                               │
│   [ kube-proxy ] ───▶ (Manages local iptables network routing)         │
└────────────────────────────────────────────────────────────────────────┘
```

#### The 4 Control Plane Components (The Brain):
1. **`kube-apiserver` (The Front Door):** The only component that talks directly to the database. All commands (`kubectl`), worker nodes (`kubelet`), and controllers communicate exclusively through REST API calls to the API server.
2. **`etcd` (The Single Source of Truth):** A distributed, highly consistent key-value database. It stores the entire cluster state, secrets, and configs.
3. **`kube-scheduler` (The Placement Engine):** Watches for newly created Pods with no assigned node. It evaluates node CPU/RAM capacity, taints, and affinities, and binds the Pod to the best available node.
4. **`kube-controller-manager` (The Reconciliation Loop):** Continuously compares **Desired State** (what you asked for in YAML) vs **Actual State** (what is physically running in the cluster). If a node dies, it schedules replacements.

#### The 3 Worker Node Components (The Muscle):
1. **`kubelet` (The On-Node Captain):** An agent running directly on the node OS. It receives Pod specifications (`PodSpecs`) from the API server, instructs the container runtime to launch containers, monitors container health, and reports back.
2. **Container Runtime (`containerd`):** The software that pulls container images from registries and runs Linux namespaces and cgroups.
3. **`kube-proxy` (The Network Traffic Controller):** Manages IP routing and iptables rules on the node, enabling Pod-to-Pod communication and Service load balancing.

## Part 2: Hands-On Build — Your First Pod Manifest (60 min)

### What is a Pod?
Kubernetes does **NOT** run containers directly. It wraps containers in an abstraction called a **Pod**.
- A Pod is the smallest deployable computing unit in Kubernetes.
- A Pod represents one or more containers that share the **same Network IP address**, the **same port space (`localhost`)**, and the **same shared storage volumes**.


### Step 2: Write Your First Pod Manifest (`pod.yaml`)
Create `pod.yaml`:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: day31-web-server
  labels:
    app: dorm-dish-web
    env: dev
spec:
  containers:
    - name: nginx-container
      image: nginx:1.25-alpine
      ports:
        - containerPort: 80
      resources:
        limits:
          memory: "128Mi"
          cpu: "200m"
        requests:
          memory: "64Mi"
          cpu: "100m"
```

#### Anatomical Breakdown:
- **`apiVersion: v1`**: Pods are part of the core Kubernetes API group `v1`.
- **`kind: Pod`**: Tells Kubernetes what object to create.
- **`metadata`**: Identifies the Pod. `name` must be unique within a namespace. `labels` are key-value tags used for routing and selectors.
- **`spec`**: The desired state. Defines the container image, container ports, and compute resource boundaries (`requests` and `limits`).

---

### Step 3: Deploy the Pod
Apply the manifest to your local cluster:

```powershell
kubectl apply -f pod.yaml
```

Output:
```text

```

Run these core triage commands:


2. **Inspect the live Pod events and runtime state:**
   ```powershell

   ```
   Scroll down to the **Events** section at the bottom. This is your primary diagnostic feed:
   - `Scheduled` (by kube-scheduler)
   - `Pulling image "nginx:1.25-alpine"` (by kubelet via containerd)

   You will see: **"Welcome to nginx!"**

## Part 3: Break-It Lab — The "Bare Pod" Survival Trap (45 min)

**INTENTIONAL RUNTIME FAILURE — Safe local scratch lab.**

### The Problem: Why Senior Engineers NEVER Deploy Bare Pods
Junior engineers often think: *"I deployed a Pod with `kind: Pod`. If the container crashes or someone deletes it, Kubernetes will automatically recreate it, right?"*

**WRONG.**

A "Bare Pod" (a standalone `kind: Pod` without a Deployment or ReplicaSet) has **NO controller watching it**. If a bare Pod is killed, or if the node running it catches fire, the Pod is **permanently dead**.

Let's prove this behavior.

---

### Step 1: Kill the Container from the Inside
Simulate a catastrophic application crash by executing a command inside the container that immediately kills the Nginx process:

```powershell
kubectl exec day31-web-server -- nginx -s stop
```

Now immediately run:
```powershell
kubectl get pods
```

#### What to Observe:
Notice the `RESTARTS` column incremented:
```text
NAME               READY   STATUS    RESTARTS      AGE
day31-web-server   1/1     Running   1 (10s ago)   3m
```
Because the `kubelet` process running on the worker node noticed the container died, its default restart policy (`restartPolicy: Always`) restarted the container **inside the same Pod**.

---

### Step 2: Now Delete the Pod
Now, simulate a node eviction or an engineer deleting the Pod:

```powershell
kubectl delete pod day31-web-server
```

Now run:
```powershell
kubectl get pods
```
Output:
```text
No resources found in default namespace.
```

**Notice:** Kubernetes did **NOT** recreate the Pod! It vanished.  
Why? Because there was no **Deployment controller** or **ReplicaSet controller** declared to maintain the desired count of replicas.

---

### Step 3: Inspect Cluster-Wide Events
Whenever something fails in Kubernetes, your first reflex must be querying recent cluster events:

```powershell
kubectl get events --sort-by=.metadata.creationTimestamp
```

This streams the cluster timeline, proving which controller or component took action:
- `Killing`: Stopping container nginx-container
- `Deleted`: Pod deleted by user

## Part 4: Troubleshooting Record

```markdown
## Troubleshooting Record — Day 031
**Problem:** A standalone Pod was deleted, but Kubernetes failed to recreate it, resulting in service downtime.
**Symptoms:** `kubectl get pods` returned `No resources found in default namespace`. The application was completely offline.
**Environment:** Local Kubernetes v1.30+ cluster running on Docker Desktop (Windows).
**What I checked:** 
1. Checked `kubectl get pods` to verify if a replacement pod was in `Pending` state.
2. Ran `kubectl get events --sort-by=.metadata.creationTimestamp` to see event history.
3. Inspected the original manifest `pod.yaml` for a controller definition.
**Commands used:** 
- `kubectl delete pod day31-web-server`
- `kubectl get events`
- `kubectl describe pod ...`
**Evidence:** The manifest defined `kind: Pod` directly. No `kind: Deployment` or `kind: ReplicaSet` was managing the object.
**Hypothesis:** Kubernetes controllers only manage replicas if explicitly wrapped in higher-level workload resources (Deployments).
**Root Cause:** A bare Pod has no self-healing controller. Kubelet restarts failed containers *within* an active Pod, but if the Pod itself is deleted or evicted, Kubernetes removes it permanently.
**Fix:** In production, never deploy raw Pods. Always deploy workloads wrapped in `kind: Deployment`, which continuously enforces the desired replica count.
**Verification:** Learned the behavioral boundary between container-level restarts (handled by Kubelet) and Pod-level lifecycle management (handled by Controller Manager).
**Prevention:** Enforce policy validation tools (e.g. Kyverno or OPA Gatekeeper) in CI/CD to reject standalone `kind: Pod` manifests from production branches.
**What I learned:** Kubelet provides container-level restarts, but the Controller Manager provides Pod-level self-healing.
```

## Part 5: Job Readiness & Interview Defense (15 min)

### Interview Question:
*"Walk me through what happens under the hood in the Kubernetes architecture from the exact millisecond an engineer types `kubectl apply -f pod.yaml` until the container is actually running."*

### Top 1% Senior Answer Breakdown:
1. **Client & API Server Authentication:** `kubectl` validates the YAML, authenticates with credentials from `~/.kube/config`, and sends an HTTP POST request to `kube-apiserver`.
2. **Persistence in `etcd`:** The API server authenticates, authorizes (RBAC), validates the schema, and commits the Pod specification into `etcd`.
3. **Scheduling:** The `kube-scheduler` watches the API server for unassigned Pods (`nodeName: ""`):
   - It filters nodes (checking CPU/memory requests).
   - It scores surviving nodes.
   - It writes a binding decision back to `kube-apiserver`, which updates `etcd`.
4. **Execution by `kubelet`:** The `kubelet` daemon on the assigned worker node detects the assignment via watch stream from the API server:
   - Kubelet calls the Container Runtime (`containerd`) via the Container Runtime Interface (CRI).
   - containerd pulls the image from the registry.
   - It configures Linux namespaces and cgroups and starts the container.
   - Kubelet configures the network interface via CNI (Container Network Interface).
5. **State Reporting:** Kubelet reports the container status (`Running`, Pod IP) back to `kube-apiserver`, which updates `etcd`.
