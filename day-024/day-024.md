## Part 2: HCL 101 & Providers (30 min)

### The Problem
Terraform needs to know *what* cloud it's talking to and *how* to authenticate. AWS has different APIs than Azure or Google Cloud.

### Build It Now 
1. Open your terminal and create today's workspace:
   ```bash
   mkdir -p ~/devops-journey/day-024-tf
   cd ~/devops-journey/day-024-tf
   ```
2. Create a file named `provider.tf` in your editor.
3. Add the AWS provider block:
   ```hcl
   terraform {
     required_providers {
       aws = {
         source  = "hashicorp/aws"
         version = "~> 5.0"
       }
     }
   }

   provider "aws" {
     region = "eu-north-1"
     # It will automatically use your local AWS CLI credentials
   }
   ```

### Try It Now
Run this in your terminal:
```bash
terraform init
```
**What happened?** Terraform read your `provider.tf` file, saw you wanted AWS, and downloaded the AWS plugin into a hidden `.terraform` folder. You must run `init` anytime you add a new provider or module.

### Exercise
1. Look in your directory. What new hidden folder was created?
2. Why is the region hardcoded to `eu-north-1` in the provider block instead of inside the `terraform {}` block? (Hint: Terraform itself is cloud-agnostic; the `provider` block configures the specific AWS plugin).

## Part 3: First Resource (VPC) & Plan/Apply (30 min)

### The Problem
We need a VPC, but we want to define it in code, not clicks. 

### Build It Now
1. Create a file named `main.tf`.
2. Add the VPC resource block:
   ```hcl
   resource "aws_vpc" "main" {
     cidr_block           = "10.24.0.0/16"
     enable_dns_support   = true
     enable_dns_hostnames = true

     tags = {
       Name = "day24-lab-vpc"
     }
   }
   ```

### Try It Now
Run the dry-run command:
```bash
terraform plan
```
Output will show a green `+ create`. It tells you exactly what AWS API calls it *intends* to make. 

Now, execute it:
```bash
terraform apply
```
Type `yes` when prompted.

**Verification:** Go to the AWS Console -> VPC -> Your VPCs. You will see `day24-lab-vpc` exists! You just provisioned infrastructure via API.

## Part 4: Subnets & Implicit Dependencies (30 min)

### The Problem
A subnet must belong to a VPC. How does Terraform know the VPC's ID if the VPC hasn't been created yet?

### Build It Now
Append this to your `main.tf`:
```hcl
resource "aws_subnet" "public" {
  vpc_id                  = aws_vpc.main.id
  cidr_block              = "10.24.1.0/24"
  availability_zone       = "eu-north-1a"
  map_public_ip_on_launch = true

  tags = {
    Name = "day24-lab-public-sub"
  }
}
```

### Try It Now
Look at `vpc_id = aws_vpc.main.id`. 
You didn't hardcode a string like `vpc-0abcd1234`. You referenced the resource type (`aws_vpc`), the local reference name (`main`), and the attribute (`id`). 

This creates an **implicit dependency**. Terraform now knows it MUST create the VPC before it creates the subnet.

Run:
```bash
terraform apply -auto-approve
```
*(Note: `-auto-approve` skips the "yes" prompt. Use it safely).*

## Part 5: State File Basics (30 min)

### The Problem
How does Terraform know that running `apply` again shouldn't create a *second* VPC?

### Try It Now
Look in your directory for a file named `terraform.tfstate`. Open it in VS Code.

This is a JSON file mapping your code (`aws_vpc.main`) to the real AWS reality (`vpc-0123456789abcdef0`).
When you run `plan`, Terraform:
1. Reads your `.tf` files.
2. Reads the `terraform.tfstate` file.
3. Calls the AWS API to refresh the real-world status.
4. Compares them and decides what to do.

**Golden Rule:** NEVER edit `terraform.tfstate` manually.

## Part 6: Break-It Lab (45 min)

**INTENTIONAL FAILURE — Safe scratch lab.**

### Prove WORKING First (mandatory gate)
Run `terraform plan`. It should say:
`No changes. Your infrastructure matches the configuration.`
Gate passed ✅.

### What We're Breaking
We will try to create a private subnet, but we will accidentally give it the exact same CIDR block as the public subnet.

### Steps to Break It
Append this to `main.tf`:
```hcl
resource "aws_subnet" "private" {
  vpc_id            = aws_vpc.main.id
  cidr_block        = "10.24.1.0/24"   # ERROR: Same as public subnet!
  availability_zone = "eu-north-1b"

  tags = {
    Name = "day24-lab-private-sub"
  }
}
```

### Symptoms to Observe
Run:
```bash
terraform plan
```
Wait, `plan` actually succeeds! It says `+ create`. Why? Because Terraform just checks syntax and state. It doesn't know AWS's internal networking rules.

Now run:
```bash
terraform apply -auto-approve
```
**CRASH:** `Error: creating EC2 Subnet: InvalidSubnet.Conflict: The CIDR '10.24.1.0/24' conflicts with another subnet`

### YOUR TURN: Diagnose
1. Why did `terraform plan` succeed if the code was invalid?
2. Which system threw the actual error: Terraform CLI or the AWS API?
3. How do you fix it?

*(Fix: Change the private subnet CIDR to `10.24.2.0/24`, then run `terraform apply` again. It will succeed).*

## Part 7: Troubleshooting Challenge (30 min)

### Scenario
> A developer needed to clean up some old resources and manually deleted the `day24-lab-vpc` directly in the AWS Console. 
> You run `terraform plan` the next day. 

### Investigation Path
1. **SYMPTOM:** The VPC is gone from the console, but your `main.tf` still has the code.
2. **OBSERVATION:** What will `terraform plan` do? Will it error? Will it do nothing?
3. **HYPOTHESIS:** Terraform's state file thinks the VPC exists, but the refresh phase will realize it's missing.
4. **CHECK:** Go to the AWS console and manually delete your `day24-lab-public-sub` (just the subnet).
5. **EVIDENCE:** Run `terraform plan`.
6. **ROOT CAUSE:** State drift. The real world drifted from the expected state.
7. **FIX:** Terraform automatically plans to `+ create` the missing subnet to make reality match your code again.
8. **VERIFY:** Run `terraform apply` to restore the deleted subnet.
9. **PREVENTION:** Revoke manual console deletion permissions from users. All changes must go through Terraform.

## Part 8: Build Task (60 min)

Your final task is to complete the network foundation by adding an Internet Gateway and a Route Table. 

Append this code to your `main.tf` and run `terraform apply`.

```hcl
# Internet Gateway
resource "aws_internet_gateway" "igw" {
  vpc_id = aws_vpc.main.id

  tags = {
    Name = "day24-lab-igw"
  }
}

# Route Table for Public Subnet
resource "aws_route_table" "public" {
  vpc_id = aws_vpc.main.id

  route {
    cidr_block = "0.0.0.0/0"
    gateway_id = aws_internet_gateway.igw.id
  }

  tags = {
    Name = "day24-lab-rt-public"
  }
}

# Associate Route Table with Public Subnet
resource "aws_route_table_association" "public_assoc" {
  subnet_id      = aws_subnet.public.id
  route_table_id = aws_route_table.public.id
}
```

## Part 9: Root-Cause Discussion (15 min)

Why did the CIDR overlap bug pass `terraform plan` but fail `terraform apply`?

Terraform `plan` evaluates your local `.tf` files against the `.tfstate` file. It verifies that the HCL syntax is valid and resolves dependencies. It does *not* simulate AWS backend logic (like CIDR overlap rules, IAM permission evaluations, or name uniqueness constraints). 

The error happened during `apply` because Terraform sent the API request to AWS (`CreateSubnet`), and the **AWS API** returned an HTTP 400 error. Terraform simply printed the AWS API error to your terminal.

## Part 11: Job Readiness (10 min)

**Interview Question:**
"Walk me through the difference between `terraform init`, `plan`, and `apply`."

**Strong Answer:**
"When starting a new project, I run `terraform init` to download the provider plugins, like the AWS provider, into the `.terraform` directory. `terraform plan` is a dry-run; it reads my `.tf` configuration, refreshes the state against the live cloud environment, and outputs an execution plan showing what will be added, changed, or destroyed. `terraform apply` takes that plan and makes the actual REST API calls to AWS to provision the infrastructure, and then updates the local `terraform.tfstate` file to map the new resources."

## Part 12: Recap (10 min)

| Command | What it does |
|---|---|
| `terraform init` | Downloads providers, sets up working directory |
| `terraform plan` | Dry run. Compares code to state to reality |
| `terraform apply` | Executes the plan via API calls |
| `terraform destroy` | Destroys everything tracked in the state file |

**The Pattern:**
1. Write HCL.
2. `terraform init` (only once or when adding providers).
3. `terraform plan` (always check what it's going to do).
4. `terraform apply`.
5. Check AWS console to verify.
