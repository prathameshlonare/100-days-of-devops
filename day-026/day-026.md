## Part 1: Why This Matters for Dorm-and-Dish (15 min)

In Days 24 and 25, every time you ran `terraform apply`, Terraform generated a file named `terraform.tfstate` right in your local folder.

### The 4 Fatal Flaws of Local State in Production:

1. **State Corruption via Concurrent Execution (Race Conditions):**
   Imagine two developers on the Dorm-and-Dish team (or a developer and an automated GitHub Actions pipeline) run `terraform apply` at the exact same second. With local state or remote storage without locking, both read the old state, make conflicting modifications to AWS, and overwrite each other's state file. Half your infrastructure becomes unmanaged "orphan" resources, and the state JSON becomes corrupt.
2. **Merge Conflicts on State in Git:**
   Never commit `terraform.tfstate` to Git. State files contain timestamps, serial numbers, and line-by-line resource hashes. Two commits will trigger massive Git merge conflicts that are nearly impossible to resolve manually without corrupting the JSON graph.
3. **Plaintext Secret Exposure:**
   Terraform state files contain every attribute of your resources in plaintext, including database passwords, initial SSH keys, and IAM credentials. Pushing local state to GitHub exposes sensitive tokens immediately.
4. **Out-of-Sync Local Divergence:**
   If Developer A deploys a database from their laptop, Developer B's laptop has no record of it. When Developer B runs `terraform plan`, Terraform attempts to recreate or destroy what Developer A just built.

### Feeder Role Relevance:
- **Cloud Support Engineer:** Customer tickets stating `"Error acquiring the state lock: ConditionalCheckFailedException"` are extremely common when CI/CD pipelines crash mid-deployment. You must know how to inspect DynamoDB lock rows and clear deadlocks safely.
- **Junior DevOps Engineer:** Centralizing state into S3 with server-side encryption, versioning for disaster rollback, and DynamoDB for distributed locking is the mandatory prerequisite for any team CI/CD pipeline.

## Part 2: Bootstrap S3 Bucket & DynamoDB Lock Table (30 min)

### The Problem
Terraform cannot store its own backend state in an S3 bucket or lock with DynamoDB until that S3 bucket and DynamoDB table actually exist! This is known as the **chicken-and-egg problem** of infrastructure-as-code. 

In enterprise environments, backend infrastructure is bootstrapped either manually via the AWS Console or using a one-time setup step. Today we bootstrap our state backend in `eu-north-1`.

### Build It Now

1. **Open AWS Console** and ensure your region selector in the top right is set to **Stockholm (`eu-north-1`)**.

2. **Create the S3 State Bucket:**
   - Navigate to **S3** -> Click **Create bucket**.
   - **Bucket name:** `day26-tfstate-bucket-<your-account-id>` (replace `<your-account-id>` with your 12-digit AWS account number).
   - **AWS Region:** `Europe (Stockholm) eu-north-1`.
   - **Object Ownership:** ACLs disabled (recommended).
   - **Block Public Access:** Keep all 4 checkboxes **checked** (Block *all* public access). State files must never be public!
   - **Bucket Versioning:** Select **Enable**. *(Critical: If state corrupts, S3 versioning allows instant rollback to an earlier JSON state).*
   - **Default encryption:** Server-side encryption with **Amazon S3 managed keys (SSE-S3)**.
   - Click **Create bucket**.

3. **Create the DynamoDB Lock Table:**
   - Navigate to **DynamoDB** -> Click **Create table**.
   - **Table name:** `day26-tfstate-locks`
   - **Partition key:** `LockID` (Case-sensitive! It must be exact: capital `L`, capital `ID`).
   - **Data type:** `String`.
   - **Table class:** DynamoDB Standard.
   - **Capacity mode:** Select **Customize settings** -> Select **On-demand** (Pay-per-request). This ensures $0 cost while idle.
   - Click **Create table**.

### Try It Now
Verify both resources using the AWS CLI in your terminal:

```bash
# Check the S3 bucket exists and is versioned
aws s3api get-bucket-versioning --bucket day26-tfstate-bucket-<your-account-id> --region eu-north-1

# Check the DynamoDB table status
aws dynamodb describe-table --table-name day26-tfstate-locks --region eu-north-1 --query "Table.TableStatus"
```

Expected output for the DynamoDB table: `"ACTIVE"`.

### Exercise
1. What happens if you name the DynamoDB partition key `id` or `lock_id` instead of `LockID`?  
   *(Answer: Terraform's AWS provider hardcodes the query parameter `LockID`. Any other key name causes `terraform apply` to crash immediately with a schema mismatch error).*
2. Why is S3 Versioning mandatory for production Terraform backends?  
   *(Answer: Every time Terraform updates state, S3 saves a new version object. If an apply partially corrupts state, you can restore previous versions without data loss).*

## Part 3: Configure the Remote S3 Backend in Terraform (30 min)

### The Problem
We have the S3 bucket and DynamoDB table ready in AWS. Now we must instruct Terraform to stop writing `terraform.tfstate` to the local folder and instead stream state directly to S3, using DynamoDB to lock state during operations.

### Build It Now

1. Create a dedicated workspace directory for Day 26:
   ```bash
   mkdir -p D:\projects\Learning\devops-journey\01-daily-posts\day-26\day-26-tf
   cd D:\projects\Learning\devops-journey\01-daily-posts\day-26\day-26-tf
   ```

2. Create `backend.tf`:
   ```hcl
   terraform {
     backend "s3" {
       bucket         = "day26-tfstate-bucket-<your-account-id>" # Replace with your real bucket name
       key            = "day26/scratch/terraform.tfstate"       # Path inside S3 bucket
       region         = "eu-north-1"
       dynamodb_table = "day26-tfstate-locks"
       encrypt        = true
     }
   }
   ```

> [!IMPORTANT]
> **Why can't we use variables inside the `backend` block?**  
> Notice that `bucket` and `region` are hardcoded strings. You **cannot** write `bucket = var.bucket_name` inside a `terraform { backend "s3" {} }` block!  
> Why? Terraform initializes the backend during `terraform init`, before it even reads `variables.tf` or loads variable values.

3. Create `provider.tf`:
   ```hcl
   terraform {
     required_version = ">= 1.5.0"
     required_providers {
       aws = {
         source  = "hashicorp/aws"
         version = "~> 5.0"
       }
     }
   }

   provider "aws" {
     region = "eu-north-1"
   }
   ```

4. Create `main.tf` with a minimal VPC and Subnet to track in state:
   ```hcl
   resource "aws_vpc" "lab_vpc" {
     cidr_block           = "10.26.0.0/16"
     enable_dns_support   = true
     enable_dns_hostnames = true

     tags = {
       Name        = "day26-lab-vpc"
       Environment = "lab"
     }
   }

   resource "aws_subnet" "public_sub" {
     vpc_id                  = aws_vpc.lab_vpc.id
     cidr_block              = "10.26.1.0/24"
     availability_zone       = "eu-north-1a"
     map_public_ip_on_launch = true

     tags = {
       Name = "day26-lab-public-sub"
     }
   }
   ```

5. Create `outputs.tf`:
   ```hcl
   output "vpc_id" {
     description = "VPC ID"
     value       = aws_vpc.lab_vpc.id
   }

   output "subnet_id" {
     description = "Public Subnet ID"
     value       = aws_subnet.public_sub.id
   }
   ```

## Part 5: How State Locking Works in DynamoDB (30 min)

### The Mechanism
What actually happens in DynamoDB when you run a command?

```
[ Developer Terminal ]                         [ AWS S3 ]              [ AWS DynamoDB ]
         |                                         |                          |
         | --- 1. Request State Lock ------------> | -----------------------> | (Writes Item: LockID)
         |                                         |                          |  -> SUCCESS
         | --- 2. Read State --------------------> | (Streams state JSON)     |
         |                                         |                          |
         | --- 3. Execute AWS API Changes          |                          |
         |                                         |                          |
         | --- 4. Write New State ---------------> | (Uploads new version)    |
         |                                         |                          |
         | --- 5. Release State Lock ------------> | -----------------------> | (Deletes Item: LockID)
```

1. **Before any mutation:** Terraform calls the DynamoDB `PutItem` API with a conditional expression: `attribute_not_exists(LockID)`.
2. **If LockID does NOT exist:** The item is written. Terraform now owns the lock.
3. **If LockID ALREADY exists:** DynamoDB rejects the call with `ConditionalCheckFailedException`. Terraform immediately aborts with an error, preventing dual execution.
4. **After mutation:** Terraform calls DynamoDB `DeleteItem` to remove the lock.

## Part 7: Troubleshooting Challenge (30 min)

### Real-World Incident Scenario
> A developer on your team configures an S3 backend for a new microservice. When they run `terraform init`, everything passes. But the first time they run `terraform apply`, Terraform halts with:
> `Error: Error locking state: ResourceNotFoundException: Cannot do operations on a non-existent table`
> The developer insists: *"I created the DynamoDB table in the AWS Console 5 minutes ago! Why is Terraform saying it doesn't exist?"*

### Investigation Path (9-Step Chain)
1. **SYMPTOM:** `terraform apply` fails with `ResourceNotFoundException: Cannot do operations on a non-existent table`.
2. **OBSERVATION:** The error comes from DynamoDB, not S3. S3 read succeeded, but DynamoDB lock acquisition failed.
3. **HYPOTHESIS:** One of three causes:
   - A: The table name in `backend.tf` has a typo.
   - B: The DynamoDB table was created in a different AWS region than the backend config.
   - C: The IAM user/role lacks permissions for `dynamodb:PutItem`.
4. **CHECK:**
   - Step A: Compare the `dynamodb_table` string in `backend.tf` with the AWS Console.
   - Step B: Check the region of the DynamoDB table in the AWS Console.
5. **EVIDENCE:** In the AWS Console, the DynamoDB table was created in `us-east-1` (N. Virginia, default Console view), but `backend.tf` specifies `region = "eu-north-1"`.
6. **ROOT CAUSE:** Regional mismatch. DynamoDB tables are regional resources. Terraform queried `eu-north-1` for a table that only existed in `us-east-1`.
7. **FIX:** Create the table in `eu-north-1`, or update `backend.tf` if the table was intended elsewhere.
8. **VERIFY:** Re-run `terraform init -reconfigure` and `terraform apply`. The lock acquires successfully.
9. **PREVENTION:** Use a bootstrap Terraform module to create both the S3 bucket and DynamoDB table together in the same target region, rather than manual Console click-ops.

## Part 9: Root-Cause Discussion (15 min)

### The Question:
*How does DynamoDB guarantee that two identical `apply` commands executed at the exact same millisecond cannot both succeed?*

### The Technical Answer:
1. **DynamoDB Conditional Writes:**
   Terraform uses DynamoDB's `PutItem` with an expression:
   `attribute_not_exists(LockID)`
2. **Strongly Consistent Storage:**
   DynamoDB's internal storage nodes execute a Paxos/Raft consensus protocol on partition writes. When two requests arrive simultaneously for the exact same partition key (`LockID`):
   - The first request commits to the storage node.
   - The second request evaluates `attribute_not_exists(LockID)`. Because the first write already placed the partition key in the index, the condition evaluates to `FALSE`.
   - DynamoDB rejects the second write with HTTP status 400 (`ConditionalCheckFailedException`).
3. **No File Locking on S3:**
   S3 is an object store, not a POSIX filesystem. S3 does not natively support file locks (`flock`). This is why S3 **requires** a companion database like DynamoDB to manage mutex (mutual exclusion) locks.

## Part 11: Job Readiness (10 min)

### Interview Question:
*"Why do we use an S3 bucket and DynamoDB table for Terraform remote state instead of keeping state in Git or on a shared NFS network drive?"*

### Strong Answer:
"Storing Terraform state in Git is a major anti-pattern for three reasons: first, state files contain unencrypted secrets and credentials in plaintext; second, Git has no locking mechanism, so concurrent pipeline runs will trigger race conditions and state corruption; third, simultaneous commits cause unresolvable merge conflicts in complex JSON dependency trees.

Using S3 combined with DynamoDB solves all three problems:
1. **Security & Recovery:** S3 encrypts state at rest via KMS or AES-256, allows strict IAM bucket policies, and enables S3 Versioning so we can roll back corrupted state instantly.
2. **Concurrency & Locking:** S3 alone is an object store without file locking. DynamoDB acts as a distributed mutex: before any plan or apply, Terraform uses DynamoDB conditional writes (`attribute_not_exists(LockID)`) to acquire an exclusive lock. If another apply is running, subsequent requests fail safely with `ConditionalCheckFailedException`, guaranteeing state integrity."

### Concept Summary Table

| Component | Technology | Role |
|---|---|---|
| State Storage | AWS S3 Bucket | Stores `terraform.tfstate` JSON remotely with encryption |
| State Versioning | S3 Object Versioning | Preserves historical snapshots for disaster recovery |

4. **Migrate State:** Run `terraform init` (or `terraform init -migrate-state`) to copy state to S3.
5. **Execute Safely:** Run `plan` and `apply`; observe lock acquisition and release.
6. **Teardown Cleanly:** Destroy managed infra first, then empty and delete S3 bucket and DynamoDB table.
