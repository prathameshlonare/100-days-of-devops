## Part 1: Why Networking Matters in DevOps (10 min)

Every service you'll ever deploy communicates over a network. Containers talk to each other through ports. Load balancers route traffic. APIs respond on HTTP. If you don't understand networking, you can't debug why "the app isn't working."

Here's what we'll cover today:

| Command | What it does |
|---------|--------------|
| `ss` | See which ports are listening |
| `curl` | Test HTTP endpoints |
| `dig` / `nslookup` | Check DNS resolution |
| `ping` / `traceroute` | Test connectivity and latency |
| `ip` | View network interfaces |

## Part 2: ss — See What's Listening (20 min)

### The Problem
Your app runs on port 8080. A user says it's unreachable. How do you check if the app is actually listening?

### The Command

```bash
ss -tlnp
```

Let's break it down:
- `-t` = TCP only (skip UDP)
- `-l` = only show listening sockets (not established connections)
- `-n` = don't resolve names (show raw IPs/ports — faster)
- `-p` = show the process using the socket

### Try It Now

Run this on your machine:

```bash
ss -tlnp
```

You'll see output like:

```
State    Recv-Q   Send-Q   Local Address:Port   Process
LISTEN   0        128      0.0.0.0:22           users:(("sshd",pid=1234,fd=3))
LISTEN   0        128      0.0.0.0:80           users:(("nginx",pid=5678,fd=6))
```

### What This Tells You

| Column | Meaning |
|--------|---------|
| State | LISTEN = waiting for connections |
| Local Address:Port | 0.0.0.0:80 = listening on ALL interfaces, port 80 |
| Process | Which program owns this port |

### Exercise 1

1. Run `ss -tlnp` on your machine
2. Find which ports are listening
3. Identify which process owns each port
4. Answer: Is port 22 (SSH) listening? What process owns it?

### Quick Cheat

Just want to check one port?

```bash
ss -tlnp | grep 8080
```

No output? Nothing is listening on 8080.

### Old Way: netstat

```bash
netstat -tlnp
```

Same idea, older command. On modern Linux, `ss` is faster and preferred. But you'll see `netstat` in old tutorials and scripts.

## Part 3: curl — Test HTTP Endpoints (20 min)

### The Problem
A service is listening on port 8080. But is it actually responding correctly? You need to test the HTTP layer.

### Basic: Just Get the URL

```bash
curl https://example.com
```

This dumps the full HTML to your terminal. Useful, but messy.

### Get Only Headers

```bash
curl -I https://example.com
```

Output:

```
HTTP/2 200
content-type: text/html
date: Sat, 05 Jul 2026 12:00:00 GMT
```

`-I` (capital I) = HEAD request. Shows status code and headers only. This is what you'll use 90% of the time.

### Check Status Code Only

```bash
curl -o /dev/null -s -w "%{http_code}" https://example.com
```

- `-o /dev/null` = discard the body
- `-s` = silent (no progress bar)
- `-w "%{http_code}"` = print only the status code

Output: `200`

### Test a Local Service

If your app runs on localhost:8080:

```bash
curl -I http://localhost:8080/health
```

- 200 = healthy
- 500 = server error
- Connection refused = nothing listening on that port

### Follow Redirects

```bash
curl -L -I http://example.com
```

`-L` follows redirects. Without it, you'll just see a 301/302.

### Exercise 2

1. Run `curl -I https://google.com` — what status code do you get?
2. Run `curl -I http://localhost:22` — what happens?
3. Run `curl -o /dev/null -s -w "%{http_code}" https://github.com` — what's the code?

### Real DevOps Use

You'll use curl in health checks, monitoring scripts, CI/CD pipelines:

```bash
# Check if API is healthy before deploying
if [ $(curl -o /dev/null -s -w "%{http_code}" http://localhost:8080/health) -eq 200 ]; then
    echo "Service is healthy"
else
    echo "Service is DOWN"
fi
```

## Part 4: dig and nslookup — DNS Resolution (15 min)

### The Problem
Your app connects to `api.example.com`. But is it resolving to the right IP? DNS is the phonebook of the internet.

### nslookup (Simple)

```bash
nslookup example.com
```

Output:

```
Server:    127.0.0.53
Address:   127.0.0.53#53

Non-authoritative answer:
Name:      example.com
Address:   93.184.216.34
```

### dig (Detailed)

```bash
dig example.com
```

Gives you a lot of output. Use `+short` for clean results:

```bash
dig +short example.com
```

Output: `93.184.216.34`

### Check Specific Record Types

```bash
# MX records (mail servers)
dig +short example.com MX

# CNAME records
dig +short www.example.com

# TXT records (SPF, DKIM)
dig +short example.com TXT
```

### Exercise 3

1. Run `nslookup google.com` — what IP does it resolve to?
2. Run `dig +short google.com` — same IP?
3. Run `dig +short google.com MX` — what mail servers does Google use?
4. Run `dig +short localhost` — what happens?

## Part 5: ping and traceroute — Connectivity & Latency (15 min)

### ping — Is It Reachable?

```bash
ping -c 4 google.com
```

`-c 4` = send only 4 packets (without it, ping runs forever)

Output:

```
64 bytes from 142.250.190.78: icmp_seq=1 ttl=116 time=12.3 ms
64 bytes from 142.250.190.78: icmp_seq=2 ttl=116 time=11.8 ms
```

Key info: `time=` is your latency. Under 50ms is good. Over 200ms = problems.

### traceroute — Where Are Packets Going?

```bash
traceroute google.com
```

Shows every hop between you and the destination. Useful for finding where latency spikes or packets drop.

```
 1  192.168.1.1   1.2 ms
 2  10.0.0.1      5.4 ms
 3  72.14.236.204 12.1 ms
 ...
```

If hop 5 shows 300ms, that's where your problem is.

### Windows Users

On Windows (if you're testing locally):
- `ping -n 4 google.com` (use `-n` instead of `-c`)
- `tracert google.com` (instead of `traceroute`)

### Exercise 4

1. Run `ping -c 4 8.8.8.8` — what's the average latency?
2. Run `ping -c 4 localhost` — should always be <1ms
3. Run `traceroute google.com` — how many hops?

## Part 6: ip — Network Interfaces (10 min)

### Old Way: ifconfig

```bash
ifconfig
```

Might not be installed on modern Linux. Use `ip` instead.

### Modern Way: ip

```bash
# Show all interfaces and IPs
ip addr show

# Show only eth0
ip addr show eth0

# Show routing table
ip route show
```

### Exercise 5

1. Run `ip addr show` — find your IP address (look for `inet 192.168.x.x`)
2. Run `ip route show` — what's your default gateway?

## Part 7: Build Task — network-check.sh (30 min)

Now let's combine everything into a real script.

### Create the File

```bash
cd devops-journey/sysadmin-toolkit
nano network-check.sh
```

### Write This Script

```bash
#!/bin/bash

# network-check.sh — Quick network diagnostics
# Usage: ./network-check.sh <hostname> [port]

HOST=${1:-"google.com"}
PORT=${2:-"80"}

echo "========================================="
echo "  Network Check: $HOST"
echo "========================================="

# 1. Ping check
echo ""
echo "[1] PING TEST"
echo "-----------------------------------------"
ping -c 3 -W 2 $HOST 2>/dev/null | tail -1

# 2. DNS resolution
echo ""
echo "[2] DNS RESOLUTION"
echo "-----------------------------------------"
dig +short $HOST 2>/dev/null || nslookup $HOST 2>/dev/null | grep "Address:" | tail -1

# 3. Port check (if port provided)
if [ -n "$PORT" ]; then
    echo ""
    echo "[3] PORT CHECK (port $PORT)"
    echo "-----------------------------------------"
    ss -tlnp 2>/dev/null | grep ":$PORT " && echo "Port $PORT is LISTENING" || echo "Port $PORT is NOT listening"

    echo ""
    echo "[4] HTTP STATUS"
    echo "-----------------------------------------"
    HTTP_CODE=$(curl -o /dev/null -s -w "%{http_code}" --connect-timeout 5 http://$HOST:$PORT 2>/dev/null)
    echo "HTTP Status: $HTTP_CODE"
fi

echo ""
echo "========================================="
echo "  Done"
echo "========================================="
```

### Make It Executable

```bash
chmod +x network-check.sh
```

### Test It

```bash
# Check google.com on port 80
./network-check.sh google.com 80

# Check your own machine
./network-check.sh localhost 22

# Check a non-existent host
./network-check.sh fakehost12345.com
```

### What You Just Built

A diagnostic tool that:
- Tests if a host is reachable (ping)
- Resolves DNS
- Checks if a specific port is listening
- Tests HTTP status code

This is the kind of script you'd run before debugging "why isn't my app working?"

## Part 8: Recap (5 min)

### What You Learned

| Command | Use Case |
|---------|----------|
| `ss -tlnp` | See all listening ports + processes |
| `curl -I` | Test HTTP endpoints, get status codes |
| `dig +short` | Clean DNS resolution |
| `ping -c 4` | Test connectivity + latency |
| `traceroute` | Find where packets slow down |
| `ip addr show` | View network interfaces |

### The Pattern

When something network-related breaks:
1. `ss -tlnp` — is the service listening?
2. `curl -I` — is it responding?
3. `dig` — is DNS resolving?
4. `ping` — is the host reachable?
5. `traceroute` — where's the problem?
