> **Goal:** Understand what DevOps actually is — not as a tool, but as a way of thinking. By the end, you'll be able to explain DevOps to anyone and know exactly what you're building toward for the next 100 days.

---

## Part 1: Why DevOps Exists (20 min)

### The Problem Before DevOps

Imagine this:

- **Developer** writes code, throws it over the wall to ops
- **Ops team** receives code they've never seen, tries to deploy it
- Something breaks. Developer says "works on my machine." Ops says "not our fault."
- Both teams blame each other. The user gets a broken product.

This is how software was built for decades. Silos. Finger-pointing. Slow releases.

### What DevOps Actually Is

DevOps is NOT:
- A tool (not Docker, not Kubernetes, not Jenkins)
- A job title (even though it's on LinkedIn)
- A department

DevOps IS:
- A **culture** — dev and ops work together
- A **set of practices** — automation, CI/CD, monitoring
- A **mindset** — continuous improvement, shared responsibility

### The DevOps Lifecycle

```
Plan → Code → Build → Test → Release → Deploy → Operate → Monitor
  ↑                                                              |
  └──────────────────────────────────────────────────────────────┘
                          (it's a loop)
```

| Phase | What Happens | Tools |
|-------|--------------|-------|
| Plan | Decide what to build | Jira, Trello |
| Code | Write the application | Git, VS Code |
| Build | Compile/package | Maven, npm, Docker |
| Test | Verify it works | Jest, Pytest, Selenium |
| Release | Version and package | Git tags, Semantic Versioning |
| Deploy | Put it on servers | Docker, Kubernetes, Terraform |
| Operate | Keep it running | Ansible, systemd |
| Monitor | Watch for problems | Prometheus, Grafana, CloudWatch |

## Part 2: DevOps vs Traditional IT (15 min)

### Traditional (Before DevOps)

| Dev Team | Ops Team |
|----------|----------|
| Write code | Deploy code |
| Want fast changes | Want stability |
| "Move fast" | "Don't break anything" |
| Release monthly | Release when forced |
| Success = features | Success = uptime |

They have **opposite goals**. That's the problem.

### DevOps (After)

| Everyone Together |
|-------------------|
| Dev + Ops + QA + Security all in one team |
| Shared goal: deliver value fast AND reliably |
| Everyone owns the pipeline |
| Release when ready (could be daily) |
| Success = user value |

### The Three Ways (DevOps Principles)

1. **Flow** — Optimize the whole pipeline, not individual steps
2. **Feedback** — Get feedback fast, fix fast
3. **Continuous Improvement** — Never stop learning, never stop fixing

## Part 6: Recap (5 min)

### What You Learned

| Concept | Key Takeaway |
|---------|--------------|
| DevOps lifecycle | It's a loop, not a line |
| DevOps culture | Collaboration > tools |
| Three Ways | Flow, Feedback, Continuous Improvement |
| DevOps engineer role | Automate everything, monitor everything |
| Your starting point | Skill audit is your baseline |

### The Pattern

When someone asks "What is DevOps?":
1. Start with the problem (silos, slow releases, blame)
2. Explain the culture (shared responsibility)
3. Mention the lifecycle (Plan → Monitor → loop)
4. Say "It's not a tool — it's a way of thinking"
