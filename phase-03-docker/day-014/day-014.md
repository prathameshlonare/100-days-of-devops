## Part 1: Why This Matters for Online-voting-system & Core Mental Model (15 min)

Day 13 proved `backend` DNS works. Now two production rules: frontend must NOT reach db directly (security), votes must survive `down/up` (durability). Today both fail by default — one net + no volume loses both.

Core mental model — two nets = public/private subnets, one volume = disk outside container:

```text
frontend-net (public)       backend-net (private)
[frontend] <---> [backend] <---> [db + voting-data volume]
   |                  |                    |
browser            API only            no browser, no frontend DNS
```

Why this shape: backend sits on both nets like an app server with two NICs. Frontend resolves `backend` but `db` NXDOMAIN — that timeout is correct. Volume lives outside any container — `down` (no `-v`) keeps it, `down -v` nukes it.

Feeder role link: Support triages "data lost after redeploy" with `volume ls/inspect` + `compose config` before blaming the app.

### The Pattern (use it in Part 3)

1. SYMPTOM — votes gone after recreate, both Up
2. OBSERVE — `volume ls`, `logs`, `exec ls /data`
3. HYPOTHESIZE — anonymous volume, missing mount, `down -v`
4. CHECK — `inspect` mount > `config` volumes > `exec` file list
5. EVIDENCE → ROOT CAUSE → FIX → VERIFY → PREVENT

## Part 2: Hands-On Build — Isolated + Persistent Stack (60 min)

One build only. Backend writes votes to `/data` (volume). Db holds the same volume so data has two owners, frontend has none.

Step 1 — Layout:
```powershell
mkdir day14-scratch; cd day14-scratch
mkdir frontend, backend
```

Step 2 — `backend/server.js`. Why write to `/data`: that path will be the named volume. No volume = file dies with container.
```javascript
const http = require('http');
const fs = require('fs');
const API_PORT = 4000;
const FILE = '/data/votes.txt';
try { fs.mkdirSync('/data', {recursive:true}); } catch(e) {}
const srv = http.createServer((req, res) => {
  if (req.url === '/api/health') {
    res.writeHead(200, {'Content-Type':'application/json'});
    res.end(JSON.stringify({status:'ok'})); return;
  }
  if (req.url.startsWith('/api/vote')) {
    fs.appendFileSync(FILE, 'vote\n');
    const n = fs.readFileSync(FILE, 'utf8').trim().split('\n').length;
    res.writeHead(200, {'Content-Type':'application/json'});
    res.end(JSON.stringify({votes:n})); return;
  }
  res.writeHead(404); res.end();
});
srv.listen(API_PORT, '0.0.0.0', () => console.log('backend 4000 data=' + FILE));
```

Step 3 — `backend/Dockerfile`:
```dockerfile
FROM node:18-alpine
WORKDIR /app
COPY server.js .
EXPOSE 4000
CMD ["node", "server.js"]
```

Step 4 — `frontend/server.js` (same as Day 13, points at backend):
```javascript
const http = require('http');
const API = process.env.API_URL || 'http://backend:4000';
const srv = http.createServer((req, res) => {
  res.writeHead(200, {'Content-Type':'text/plain'});
  res.end('day14 frontend api=' + API + '\n');
});
srv.listen(3000, '0.0.0.0', () => console.log('frontend 3000 api=' + API));
```

Step 5 — `frontend/Dockerfile`:
```dockerfile
FROM node:18-alpine
WORKDIR /app
COPY server.js .
EXPOSE 3000
CMD ["node", "server.js"]
```

Step 6 — `docker-compose.yml`. Why each net/volume line:
```yaml
services:
  frontend:
    build: ./frontend
    ports: ["3000:3000"]
    environment: ["API_URL=http://backend:4000"]
    networks: [frontend-net]
    depends_on: [backend]
  backend:
    build: ./backend
    ports: ["4000:4000"]
    volumes: [voting-data:/data]
    networks: [frontend-net, backend-net]
    depends_on: [db]
  db:
    image: busybox
    command: ["sleep", "infinity"]
    volumes: [voting-data:/data]
    networks: [backend-net]
networks:
  frontend-net:
  backend-net:
volumes:
  voting-data:
```
- `networks:` per service — declares NICs. Why backend on both: only bridge between public and private.
- `volumes: voting-data:/data` — named volume mount. Why named not bind: survives `down`, managed by Docker, works on any OS.
- `db: busybox sleep` — minimal holder. Why not real DB: proves volume sharing + isolation without 100MB pull.

Step 7 — Up + prove isolation + persistence:
```powershell
docker compose -p day14lab up -d --build
docker compose -p day14lab ps
curl.exe http://localhost:4000/api/vote
curl.exe http://localhost:4000/api/vote
docker compose -p day14lab exec frontend nslookup backend
docker compose -p day14lab exec frontend nslookup db
docker volume inspect day14lab_voting-data
```
Expected:
```text
{"votes":1} then {"votes":2}
backend resolves 172.x, db times out (correct — no shared net)
Mountpoint: /var/lib/docker/volumes/day14lab_voting-data/_data
```
Why `nslookup db` must fail from frontend: proves public cannot touch private. If it resolves, nets are wrong — stop here.

### GATE — Prove WORKING (mandatory)

```powershell

curl.exe http://localhost:4000/api/vote
docker compose -p day14lab exec backend ls -l /data
```
Pass = 3/3 Up + votes increments + `/data/votes.txt` exists in backend AND db (`exec db ls -l /data`). Fail = fix now. No break on broken base.

## Part 3: Break-It Lab & Live Triage — GUIDED TODAY (45 min)

Prove WORKING first: votes increment, file in both backend and db. Keep stack up.

Inject ONE failure: drop the backend volume mount (anonymous/ephemeral storage). This mirrors real "data lost after redeploy" tickets.

Step 1 — Inject break. Edit `docker-compose.yml` backend to remove its volume (db keeps its own):
```yaml
  backend:
    build: ./backend
    ports: ["4000:4000"]
    # volumes REMOVED — backend now writes to container layer
    networks: [frontend-net, backend-net]
```
Apply:
```powershell
docker compose -p day14lab up -d --build
curl.exe http://localhost:4000/api/vote
curl.exe http://localhost:4000/api/vote
docker compose -p day14lab down
docker compose -p day14lab up -d
curl.exe http://localhost:4000/api/vote
```

SYMPTOMS (write down before reading on):
- After recreate, votes reset to `{"votes":1}` instead of continuing from 4+
- `exec backend ls /data` shows fresh/empty file, `exec db ls /data` shows old votes — split brain
- Both Up, no errors in logs — silent data loss, the worst kind

What would you check first? Run in order:

Check 1 — volume + mounts (30 sec). Why first: distinguishes missing mount from deleted volume:
```powershell
docker volume ls --filter name=day14lab
docker compose -p day14lab exec backend ls -l /data
docker compose -p day14lab exec db ls -l /data
docker inspect --format='{{range .Mounts}}{{.Name}}:{{.Destination}} {{end}}' day14lab-backend-1
```
Evidence: backend inspect shows NO `voting-data:/data`, db still has it. Two divergent files — backend wrote to overlay, not volume.

Check 2 — recipe (30 sec). Why second: fix lives in compose, not daemon:
```powershell
cat docker-compose.yml
```
Evidence: backend has no `volumes:` key. Root cause confirmed: writes went to container writable layer, destroyed on recreate.

Check 3 — logs confirm silence (15 sec). Why last: proves why this escapes alerting:
```powershell
docker compose -p day14lab logs backend
```
Evidence: no error — app behaved correctly, infra discarded it.

The Fix — re-attach named volume, recreate, verify durability:
```powershell
# restore volumes: [voting-data:/data] under backend
docker compose -p day14lab up -d --build
curl.exe http://localhost:4000/api/vote
curl.exe http://localhost:4000/api/vote
docker compose -p day14lab down
docker compose -p day14lab up -d
curl.exe http://localhost:4000/api/vote
```
Verification: after `down` (no `-v`) votes continue incrementing, `exec backend ls` and `exec db ls` agree. `down -v` would nuke — never use it on stateful stacks.

Prevention: always `volumes: [name:/data]` for stateful paths; `docker compose config` in CI to assert mounts; document `down` vs `down -v` in README.

**Fix Card:** `- Day 014: votes reset to 1 after down/up, both Up no errors → volume ls > inspect mounts backend vs db > cat compose → re-add voting-data:/data to backend, up -d --build`
