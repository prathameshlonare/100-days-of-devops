## Part 1: Why This Matters for Online-voting-system & Core Mental Model (15 min)

Yesterday one container ran. Real voting app is two: React frontend (3000) calls backend API (4000). Without compose you juggle two terminals, two `run` commands, manual `--link`, one typo kills demo day.

Core mental model — one file creates three things:

```text
docker-compose.yml --up--> containers + network + DNS names
frontend --http://backend:4000--> backend (by service name, never localhost, never IP)
```

Why service name: compose creates a private bridge net + embedded DNS. Inside that net `backend` resolves to backend container IP. `localhost` inside frontend means frontend itself — the #1 compose bug you will fix in Part 3.

Feeder role link: Cloud Support sees "frontend Up, backend Up, but API ECONNREFUSED" weekly. Triage is `compose ps` > `compose logs` > `exec nslookup/curl`, not rebuild-first.

### The Pattern (use it in Part 3)

1. SYMPTOM — both Up, but API fails
2. OBSERVE — `compose ps`, `compose logs frontend`
3. HYPOTHESIZE — wrong URL (localhost), wrong port, backend down
4. CHECK — logs > `exec nslookup backend` > `exec curl backend:4000`
5. EVIDENCE → ROOT CAUSE → FIX → VERIFY → PREVENT

## Part 2: Hands-On Build — Two Services, One Command (60 min)

Single build only. Minimal Node servers — no `npm install` delay, same compose shape as real React + API.

Step 1 — Scratch layout (assume nothing exists):
```powershell
mkdir day13-scratch; cd day13-scratch
mkdir frontend, backend
```

Step 2 — `backend/server.js`. Why plain http: one file, `/api/health` proves backend alive.
```javascript
const http = require('http');
const srv = http.createServer((req, res) => {
  if (req.url === '/api/health') {
    res.writeHead(200, {'Content-Type': 'application/json'});
    res.end(JSON.stringify({status:'ok', service:'voting-backend'}));
    return;
  }
  res.writeHead(404); res.end();
});
// 0.0.0.0 so bridge traffic via eth0 is accepted, not just container loopback.
srv.listen(4000, '0.0.0.0', () => console.log('backend listening 4000'));
```

Step 3 — `backend/Dockerfile`. Why exec CMD:
```dockerfile
FROM node:18-alpine
WORKDIR /app
COPY server.js .
EXPOSE 4000
CMD ["node", "server.js"]
```

Step 4 — `frontend/server.js`. Why it calls backend on start: makes DNS failure visible in logs without a browser.
```javascript
const http = require('http');
const API = process.env.API_URL || 'http://backend:4000';
function check() {
  http.get(API + '/api/health', (r) => {
    let b=''; r.on('data',c=>b+=c); r.on('end',()=>console.log('[API-CHECK] OK ' + b));
  }).on('error', (e) => console.log('[API-CHECK] FAIL ' + e.message + ' url=' + API));
}
const srv = http.createServer((req, res) => {
  res.writeHead(200, {'Content-Type':'text/plain'});
  res.end('day13 frontend running, api=' + API + '\n');
});
srv.listen(3000, '0.0.0.0', () => { console.log('frontend listening 3000 api=' + API); check(); });
```

Step 5 — `frontend/Dockerfile`:
```dockerfile
FROM node:18-alpine
WORKDIR /app
COPY server.js .
EXPOSE 3000
CMD ["node", "server.js"]
```

Step 6 — `docker-compose.yml`. Why each key:
```yaml
services:
  frontend:
    build: ./frontend
    ports: ["3000:3000"]
    environment:
      - API_URL=http://backend:4000
    depends_on:
      - backend
  backend:
    build: ./backend
    ports: ["4000:4000"]
```
- `build: ./frontend` — builds image from that Dockerfile. Why not `image:`: we own the recipe.
- `ports: host:container` — publishes to your laptop. Why needed: `EXPOSE` alone is doc-only.
- `environment: API_URL` — injects backend address. Why env not hardcoded: same image runs dev/prod with different URL.
- `depends_on` — starts backend first. Why limited: orders start, does NOT wait for healthy — logs may show one retry, that is normal.

Step 7 — Up + prove:
```powershell
docker compose -p day13lab up -d --build
docker compose -p day13lab ps
curl.exe http://localhost:4000/api/health
curl.exe http://localhost:3000
docker compose -p day13lab logs frontend
```
Expected:
```text
{"status":"ok","service":"voting-backend"}
day13 frontend running, api=http://backend:4000
[API-CHECK] OK {"status":"ok","service":"voting-backend"}
```
Why `-p day13lab`: prefixes containers/nets (`day13lab-frontend-1`) so Day 12 leftovers never collide.

### GATE — Prove WORKING (mandatory)

```powershell
docker compose -p day13lab ps
curl.exe http://localhost:3000
curl.exe http://localhost:4000/api/health
```
Pass = both `Up` + both curls return bodies + frontend log `API-CHECK OK`. Fail = fix now. Break in Part 3 is forbidden on a broken base.

## Part 3: Break-It Lab & Live Triage — GUIDED TODAY (45 min)

Prove WORKING first: you just did — both curls OK. Keep stack up.

Inject ONE failure: frontend points at `localhost` instead of service name. This is the classic "works outside Docker, fails inside" bug.

Step 1 — Inject break. Edit `docker-compose.yml` frontend env to:
```yaml
- API_URL=http://localhost:4000
```
Apply:
```powershell
docker compose -p day13lab up -d
docker compose -p day13lab ps
curl.exe http://localhost:3000
docker compose -p day13lab logs frontend
```

SYMPTOMS to observe (write down before reading on):
- Both services still `Up` — no `Exited`, unlike Day 012
- `curl localhost:3000` returns `api=http://localhost:4000` (wrong URL baked in)
- Frontend log: `[API-CHECK] FAIL connect ECONNREFUSED 127.0.0.1:4000 url=http://localhost:4000`

What would you check first? Do not skip. Run in this order:

Check 1 — status (10 sec). Why first: rules out crash:
```powershell
docker compose -p day13lab ps
```
Evidence: both `Up`. So backend did not die — URL/routing is suspect, not CMD.

Check 2 — logs (30 sec). Why second: app named its target:
```powershell
docker compose -p day13lab logs frontend
docker compose -p day13lab logs backend
```
Evidence: frontend tried `127.0.0.1:4000` and refused; backend shows zero incoming request. Request never left frontend container.

Check 3 — on-box DNS + port (60 sec). Why last: proves service name works, localhost does not:
```powershell
docker compose -p day13lab exec frontend nslookup backend
docker compose -p day13lab exec frontend wget -qO- http://backend:4000/api/health
docker compose -p day13lab exec frontend wget -qO- http://localhost:4000/api/health
```
Evidence you should see: `nslookup backend` resolves to `172.x`; `curl backend:4000` returns JSON; `curl localhost:4000` refuses. Root cause: `localhost` inside a container is that container itself, not the host or sibling. Bridge traffic must use service DNS `backend`.

The Fix — correct URL, recreate, verify:
```powershell
# fix docker-compose.yml back to - API_URL=http://backend:4000
docker compose -p day13lab up -d
curl.exe http://localhost:3000
docker compose -p day13lab logs frontend
```
Verification: page shows `api=http://backend:4000`, log shows `[API-CHECK] OK`, backend log shows request.

Prevention: never hardcode `localhost` for inter-service calls; always `http://<service-name>:<port>` + env var; add startup `nslookup <dep>` in entrypoint for fast DNS proof.

**Fix Card:** `- Day 013: both Up but API ECONNREFUSED 127.0.0.1 → compose ps > compose logs frontend > exec nslookup backend + curl backend:4000 → fix API_URL to http://backend:4000, up -d`
