## Part 1: Why This Matters for Online-voting-system & Core Mental Model (15 min)

Your React voting app ran on your laptop (Node 18) but broke on a teammate's laptop (Node 16, Windows, different `npm install` result). For Cloud Support / Junior Cloud roles this is the daily ticket: "works on my machine."

Core mental model — one flow, memorize it:

```text
Dockerfile (recipe) --build--> Image (frozen snapshot) --run--> Container (running process)
```

Why this order matters: you never debug a container by editing the container. You fix the recipe, rebuild the snapshot, replace the process. Every Docker RCA follows that direction.

Feeder role link: Cloud Support triages `Exited 1` and `port already in use` with `docker ps -a / logs / inspect` before escalating. That is exactly Part 3 today.

### The Pattern (use it in Part 3)

1. SYMPTOM — `Exited (1)`, `curl` fails
2. OBSERVE — `docker ps -a`, `docker logs`
3. HYPOTHESIZE — bad CMD, bad port, missing file
4. CHECK — logs > inspect > Dockerfile in that order
5. EVIDENCE → ROOT CAUSE → FIX → VERIFY → PREVENT

## Part 2: Hands-On Build — One Container From Zero (60 min)

Build a minimal frontend stand-in. Why minimal: React `npm run build` takes 5+ min and hides the Dockerfile lesson. Once this works, the same Dockerfile shape builds the real React app.

Step 1 — Make scratch dir (assume nothing exists):

```powershell
mkdir day12-scratch; cd day12-scratch
```

Step 2 — Create `server.js` (what runs inside). Why Node http, no deps: zero `npm install` delay, one file to debug.

```javascript
const http = require('http');
const server = http.createServer((req, res) => {
  res.writeHead(200, {'Content-Type': 'text/plain'});
  res.end('day12 voting-frontend running\n');
});
// 0.0.0.0 is mandatory inside containers. 127.0.0.1 would listen only on container loopback and -p would still refuse.
server.listen(3000, '0.0.0.0', () => console.log('listening on 3000 pid=' + process.pid));
```

Step 3 — Create `Dockerfile` (the recipe). Why each line:

```dockerfile
FROM node:18-alpine
WORKDIR /app
COPY server.js .
EXPOSE 3000
CMD ["node", "server.js"]
```

- `FROM node:18-alpine` — pins Node 18 on 5MB Alpine. Why pin: `latest` drifts and breaks builds.
- `WORKDIR /app` — sets cwd inside image. Why: avoids `/` pollution, predictable `COPY` target.
- `COPY server.js .` — bakes file into image. Why explicit file, not `COPY . .`: smaller context, no `node_modules` leak.
- `EXPOSE 3000` — documentation only, does NOT publish. Why still write it: tells readers + tooling which port to `-p`.
- `CMD ["node","server.js"]` — exec-form JSON array. Why exec not `CMD node server.js`: exec runs node as PID 1 so signals work; shell form wraps in `/bin/sh` and swallows `docker stop`.

Step 4 — Create `.dockerignore`. Why: keeps context <10KB, prevents host `node_modules` overwriting image.

```text
node_modules
.git
.env
```

Step 5 — Build:

```powershell
docker build -t day12-lab-frontend .
```

Expected tail:

```text
 => exporting to image
 => => naming to docker.io/library/day12-lab-frontend
```

Why `-t`: names the snapshot. Without tag you get `<none>` and cannot `run` reliably.

Step 6 — Run:

```powershell
docker run -d --name day12-lab-run -p 3000:3000 day12-lab-frontend
docker ps
curl.exe http://localhost:3000
docker logs day12-lab-run
```

Expected:

```text
day12 voting-frontend running
listening on 3000 pid=1
```

Why `-d --name -p`: detached keeps terminal, name allows `logs/exec/stop` by name, `-p host:container` is host-port first. `curl` must return the string. If not, STOP — do not go to Part 3.

### GATE — Prove WORKING (mandatory)

```powershell
docker ps --filter name=day12-lab-run
curl.exe http://localhost:3000
```

Pass = `Up` + body text. Fail = fix now. Part 3 break is forbidden on a broken base.

## Part 3: Break-It Lab & Live Triage — GUIDED TODAY (45 min)

Prove WORKING first: you just did — `curl` returned text. Leave that container running.

We now inject ONE realistic failure: typo in CMD filename. This is the #1 fresher ticket — `Exited (1)` after a Dockerfile edit.

Step 1 — Inject break. Edit `Dockerfile` last line to:

```dockerfile
CMD ["node", "serverr.js"]
```

Rebuild + replace:

```powershell
docker stop day12-lab-run; docker rm day12-lab-run
docker build -t day12-lab-frontend .
docker run -d --name day12-lab-run -p 3000:3000 day12-lab-frontend
docker ps -a
curl.exe http://localhost:3000
```

SYMPTOMS to observe (write these down before reading on):

- `docker ps -a` shows `Exited (1) 2 seconds ago`, not `Up`
- `curl: (52) Empty reply` or `Failed to connect`
- No app output on `localhost:3000`

What would you check first? Do not skip. Run in this order:

Check 1 — status + exit code (10 sec). Why first: tells crash vs network:

```powershell
docker ps -a --filter name=day12-lab-run
docker inspect --format='Exit:{{.State.ExitCode}} Err:{{.State.Error}}' day12-lab-run
```

Evidence you should see: `Exit:1`. Means app died inside, not a port block.

Check 2 — logs (30 sec). Why second: app printed its death reason:

```powershell
docker logs day12-lab-run
```

Evidence you should see:

```text
Error: Cannot find module '/app/serverr.js'
```

Root cause is now visible: wrong filename, double `r`.

Check 3 — confirm recipe (30 sec). Why last: fix lives in Dockerfile, not container:

```powershell
cat Dockerfile
```

Evidence: `serverr.js` vs actual `server.js` on disk (`dir` shows `server.js` only).

The Fix — correct the recipe, rebuild the snapshot, replace the process:

```powershell
# fix Dockerfile back to CMD ["node", "server.js"]
docker rm day12-lab-run
docker build -t day12-lab-frontend .
docker run -d --name day12-lab-run -p 3000:3000 day12-lab-frontend
curl.exe http://localhost:3000
docker logs day12-lab-run
```

Verification: `curl` returns `day12 voting-frontend running`, `docker ps` shows `Up`, logs show `listening on 3000`.

Prevention: use `COPY server.js .` + matching CMD together; add CI check `docker run --rm image node -c "require('./server.js')"` or at minimum `ls` the context before build.

**Fix Card:** `- Day 012: container Exited(1), curl empty reply → docker ps -a > docker logs > cat Dockerfile → fix CMD typo to ["node","server.js"], rebuild + rerun`

## Part 5: Job Readiness & Interview Defense (15 min)

**Interview Q:** "You deploy a container, `docker ps` shows `Exited (1)` after 3 seconds and the page never loads. Walk me through triage."

Strong answer must include:

1. Order is `ps -a` for exit code, then `logs` for app error, then `inspect/Dockerfile` — not rebuild-first. Exit 1 = app crash inside, distinct from port/DNS.
2. Exact evidence: `Cannot find module` points to CMD/COPY mismatch; fix is recipe change + rebuild, not `exec` into dead container.
3. Prevention + distinction: exec-form CMD as PID 1, `.dockerignore`, and `-p host:container` vs `EXPOSE` doc-only.

Feeder link: Cloud Support L1 does this triage in under 2 min before escalating to image owner.
