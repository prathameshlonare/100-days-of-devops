## Part 1: Why This Matters for Dorm-and-Dish (15 min)

Your Dorm-and-Dish frontend calls a backend API. In production that backend sits behind two bouncers you never see:

- **Security Group = the bouncer at the apartment door.** Attached to the EC2's network card (ENI). Knows who came in, remembers them, lets their reply out automatically. Allow-only — it cannot say "block this one IP", only "allow these".
- **NACL = the bouncer at the building gate.** Attached to the whole subnet. No memory — checks every packet going in AND every packet going out against a numbered list, first match wins. Can say ALLOW or DENY.

Day 21 taught routing (can the packet find a road). Today teaches filtering (does anyone stop it on the road). "Works from localhost, hangs from outside" and "SSH works for me, times out for my teammate" are both Day-22-shaped tickets — and both are top Cloud Support / NOC interview questions.

| Concept | What it does | Dorm-and-Dish use |
|---------|-------------|-------------------|
| Security Group (stateful) | Remembers connections; return traffic auto-allowed | Web SG: allow 80/443 from internet, 22 from your IP only |
| NACL (stateless) | Forgets everything; every packet re-checked both directions | Subnet gate: allow 80/443 in, **ephemeral 1024-65535 out** for replies |
| Ephemeral ports | Random return-port the client picks (cover-all 1024-65535) | The invisible half of every HTTP request — miss it and `curl` hangs |
| Rule numbers | NACL evaluation order, lowest first, first match wins | Allow-100 before Deny-300 matters; reversed order silently blocks |
| SG source | Who is allowed in (CIDR or another SG) | SSH `your-ip/32` works, `friend-ip` times out = source rule, not a broken server |

### Feeder Role Relevance

**Today's skill is relevant to:** Cloud Support Engineer, NOC Technician, Infrastructure Support, Junior System Administrator.

**Why:** "curl hangs but the server is running" is almost always SG-vs-NACL confusion, and support engineers triage it daily.

## Part 3: NACLs — Stateless, Numbered, Ephemeral Ports (30 min)

**VIDEO (same video, second half):**
Watch the NACLs section (~next 10-15 min: subnet-level, rule numbers, ephemeral ports demo).
Pause-and-do: (1) when he shows rule numbers (100/200/300 + `*` deny), pause and open VPC → Network ACLs → your default NACL → find the `*` row; (2) when he draws the return path to an ephemeral port, pause and sketch your own: client `:54312 → server :80`, reply `server :80 → client :54312`; (3) after, do the console exercise below and read your NACL's Inbound vs Outbound tabs out loud.

### The Problem

Default NACLs allow everything, so Day 21 never noticed them. Real teams harden subnets with custom NACLs — and the #1 self-inflicted outage is: allow inbound 80/443, forget outbound ephemeral 1024-65535. Symptom: `curl -v` prints `Connected...` then hangs forever. The request arrived; the reply died at the subnet gate.

### Build It Now — harden your subnet's NACL (console clicks)

1. VPC → Network ACLs → find the NACL associated with `day22-lab-public` (default, allow-all both directions) → select it → Inbound rules tab → note rule `100 ALLOW ALL` + `* DENY ALL`.
2. Stay read-only for now — you will break a *copy* of this logic in Part 6. Do NOT edit the allow-all NACL yet. Just answer: which rule number would a DENY need to beat an ALLOW? (Lower number wins.)
3. Memorize the pair every flow needs:

| Flow | NACL inbound | NACL outbound |
|---|---|---|
| Internet → your web (port 80) | ALLOW TCP 80 from `0.0.0.0/0` | ALLOW TCP **1024-65535** to `0.0.0.0/0` (the reply!) |
| Your web → internet (apt, port 443) | ALLOW TCP **1024-65535** from `0.0.0.0/0` (the reply!) | ALLOW TCP 443 to `0.0.0.0/0` |

AWS's cover-all ephemeral range is **1024-65535**. Use it in labs; tighten only when you know every client OS.

### Key facts (Level-1 core — memorize these 4)

1. NACLs attach to the **subnet** — every instance in it shares the same gate.
2. **Stateless:** no memory. Both directions need explicit rules, including ephemeral returns.
3. **Numbered, first match wins**, plus implicit `* DENY`. Custom NACLs start deny-all; default NACL starts allow-all.
4. **CIDR only** — a NACL can never reference another SG by ID.

### Try It Now

VPC → Network ACLs → select your NACL → Subnet associations tab → confirm `day22-lab-public` is listed. This screen answers "which gate guards my server?" for every future ticket.

### Exercise

1. If inbound has `100 ALLOW 80` and `200 DENY 80`, which wins? What if the DENY were rule 50?
2. Your EC2 `curl https://google.com` leaves via 443 — which inbound NACL range must exist for the reply to get back in?
3. Say aloud the one-line difference: "SG is ___ and attaches to ___. NACL is ___ and attaches to ___."

## Part 4: The Packet Walk — Both Bouncers in Order (30 min)

Draw this on paper — one packet each way. This drawing answers 80% of interview triage questions.

**Inbound (internet → your nginx):**

```
Client → IGW → Route table (0.0.0.0/0 → igw?) → NACL INBOUND (port 80 allowed?)
  → SG INBOUND (port 80 allowed?) → nginx :80
```

**Reply (nginx → client):**

```
nginx → SG OUTBOUND (tracked? auto-ALLOW ✅) → NACL OUTBOUND (ephemeral 1024-65535 allowed?)
  → Route table → IGW → Client :<ephemeral>
```

Three consequences worth memorizing:

1. **Route beats everything:** no `0.0.0.0/0 → igw` (Day 21's lesson) and neither SG nor NACL matters — the packet has no road.
2. **NACL is checked before SG inbound, and after SG outbound.** A clean SG with a broken NACL still hangs — that's Part 6.
3. **`curl` hang location tells you the layer:** `Could not resolve host` = DNS; `Connection timed out` before connect = SG source/NACL inbound/route; `Connected... hangs waiting for reply` = NACL outbound ephemeral missing.

## Part 7: Troubleshooting Challenge (30 min)

**Scenario-based debugging — answer before reading the chain.**

### Scenario

> Teammate "hardened" the Dorm-and-Dish subnet yesterday: custom NACL, inbound `100 ALLOW 80`, `110 ALLOW 443`, `120 ALLOW 22` from `0.0.0.0/0`. Outbound `100 ALLOW 80`, `110 ALLOW 443`. SG unchanged (allows 80/443 inbound, all outbound). This morning: site `curl -v` hangs after `Connected`, `apt update` on the box fails, SSH still works. Teammate insists "SG allows it, so the network is fine." You have 30 minutes before standup.

### Investigation Path (follow in order, don't skip)

1. **SYMPTOM:** `Connected` then hang (inbound arrived, reply never returned) + outbound `apt` also failing. Both directions broken at the return leg.
2. **OBSERVATION:** On-box `curl localhost` = 200 (app alive). Laptop `curl public-ip` hangs. So: app ✅, road inbound ✅, reply path ❌.
3. **HYPOTHESIS:** NACL outbound missing ephemeral 1024-65535 — stateless gate dropping replies — plus NACL inbound missing ephemeral for the `apt` return leg.
4. **CHECK:** VPC → Network ACLs → select the subnet's NACL → Outbound rules tab (then Inbound rules tab). Compare against the Part 3 pair-table.
5. **EVIDENCE:** Outbound has 80/443 only — no 1024-65535 row. Inbound likewise has no 1024-65535 row for `apt` replies.
6. **ROOT CAUSE:** Custom NACL replaced the allow-all default without adding ephemeral return rules. SG is irrelevant — it auto-allows returns (stateful); the NACL drops them (stateless).
7. **FIX (console):** VPC → Network ACLs → Edit outbound rules → add `120 ALLOW TCP 1024-65535 → 0.0.0.0/0` → Save → Edit inbound rules → add `130 ALLOW TCP 1024-65535 ← 0.0.0.0/0` → Save. Wait ~30s.
8. **VERIFY:** Laptop `curl -v http://<ip>` → `200` + body. On-box `sudo apt update` → hits repos successfully. SSH still `OK`.
9. **PREVENTION:** Team rule — "every NACL change ships with its ephemeral pair, both directions" + screenshot the NACL tabs into the PR + prefer SGs for allow-lists, NACLs only for explicit DENY/subnet boundaries.

## Part 8: Build Task — `sg-nacl-diagnose.sh` (60 min)

A 30-second triage script you run ON the box when `curl` hangs. It checks the app layer locally (`ss`, `curl localhost`, UFW) and then prints the exact console screens to check for SG/NACL/route — because those live outside the box and no on-box command can see them.

### Create the file

```bash
mkdir -p ~/devops-journey/day-22 && cd ~/devops-journey/day-22
nano sg-nacl-diagnose.sh
```

### Write this script (FULL code — copy-paste ready)

```bash
#!/bin/bash
# sg-nacl-diagnose.sh — "curl hangs" triage for Dorm-and-Dish EC2 web servers.
# Usage: ./sg-nacl-diagnose.sh [port]   (default port 80)
# On-box half runs real checks; network-filter half prints the console path
# because SG/NACL/route tables are invisible from inside the instance.
set -u

PORT="${1:-80}"
echo "=== SG+NACL triage — port $PORT ==="

echo "--- [1/4] Is anything listening? (ss) ---"
if ss -tulpn 2>/dev/null | grep -q ":$PORT "; then
  ss -tulpn | grep ":$PORT "
else
  echo "MISS: nothing LISTENs on :$PORT -> fix the app (systemctl status nginx), not SG/NACL."
fi

echo "--- [2/4] Does localhost serve? (app vs network split) ---"
CODE=$(curl -s -o /dev/null -w "%{http_code}" --max-time 5 "http://localhost:$PORT" || echo "000")
echo "localhost:$PORT -> HTTP $CODE"
if [ "$CODE" = "200" ]; then
  echo "OK: app alive. Any laptop-side hang is SG/NACL/route, not nginx."
else
  echo "MISS: app itself broken (HTTP $CODE) -> journalctl -u nginx -xe first."
fi

echo "--- [3/4] Local firewall? (ufw/iptables) ---"
if command -v ufw >/dev/null 2>&1; then
  sudo ufw status 2>/dev/null | head -5 || echo "(ufw not active)"
else
  echo "(ufw not installed — skip)"
fi
echo "(If OUTPUT policy is DROP/REJECT on $PORT, allow it before blaming AWS.)"

echo "--- [4/4] Console path — check in THIS order ---"
cat <<'EOF'
1. EC2 -> Instances -> day22-web -> Status check = 2/2? (If 1/2, stop: infra fault, not filters.)
2. VPC -> Route Tables -> day22-lab-public-rt -> Routes: 0.0.0.0/0 -> day22-lab-igw present?
3. VPC -> Network ACLs -> subnet day22-lab-public -> OUTBOUND has TCP 1024-65535 ALLOW? (hang-after-Connected = this row missing)
   -> INBOUND has TCP 1024-65535 ALLOW? (apt/curl-out failing = this row missing)
4. EC2 -> Security Groups -> day22-lab-web-sg -> Inbound: port open? Source column matches YOUR ip (ssh) / 0.0.0.0/0 (http)?
Rule of thumb: 'Connected then hangs' = NACL ephemeral. 'Timeout before connect' = SG source / NACL inbound / route.
EOF
echo "=== done ==="
```

## Part 9: Root-Cause Discussion (15 min)

Why did both drills behave the way they did?

- **Drill A (NACL ephemeral):** `curl` reached `Connected` because inbound 80 was allowed — then the server's reply (`:80 → client :<ephemeral>`) hit the NACL outbound table, matched no 1024-65535 ALLOW, fell to `* DENY`, and died silently. Silent drops (not RSTs) = hangs, not "connection refused". That's why the symptom is a hang.
- **Drill B (SG source):** your packet never matched any inbound SG rule (source `203.0.113.99/32` ≠ your IP), so the ENI dropped it before nginx existed. No `Connected` line at all — timeout before connect. Different hang location, different bouncer.
- **The mental model:** SG asks "have I seen this connection?" (state → auto-allow replies). NACL asks "does this single packet match a numbered row?" (no memory → you must write both halves). Route asks "is there even a road?" Every "unreachable" ticket is one of those three questions — ask them in order: road (route) → gate (NACL) → door (SG) → app.
