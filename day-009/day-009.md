# Day 9/100 — Branching & Merging

> **Goal:** By the end of this session, you'll understand Git branches — how to create them, switch between them, merge changes, and handle merge conflicts. You'll practice on your real projects.

## Part 1: Why This Matters in DevOps (10 min)

Imagine you're building a new feature for your voting app. You start editing files. Halfway through, a bug is reported in production. You need to fix the bug NOW — but your feature code isn't done yet.

Without branches: You either ship broken code or manually save your work somewhere.

With branches: You switch to a "main" branch, fix the bug, merge it back, and continue your feature. Everything stays clean.

In DevOps, branches are how teams work in parallel without stepping on each other's toes. Every CI/CD pipeline, every code review, every production deploy starts with a branch.

| Command | What it does |
|---------|--------------|
| `git branch` | List branches, mark current |
| `git branch <name>` | Create a new branch |
| `git checkout <name>` | Switch to a branch |
| `git checkout -b <name>` | Create + switch in one step |
| `git merge <branch>` | Merge a branch into current |
| `git branch -d <name>` | Delete a merged branch |

## Part 2: Creating & Switching Branches (15 min)

### The Problem

You have a project on `main`. You want to add a feature without affecting the stable code. You need a separate workspace.

### The Commands

**Check what branch you're on:**

```bash
git branch
```

Output:

```
* main
```

The `*` means you're on `main`. That's your only branch right now.

**Create a new branch:**

```bash
git branch feature-add-login
```

This creates a branch called `feature-add-login` — a copy of `main` at this exact moment. It doesn't switch to it yet.

**Switch to the new branch:**

```bash
git checkout feature-add-login
```

Output:

```
Switched to branch 'feature-add-login'
```

Now `git branch` shows:

```
  main
* feature-add-login
```

You're on `feature-add-login`. Any changes you make here don't affect `main`.

**The shortcut — create + switch in one step:**

```bash
git checkout -b feature-add-dashboard
```

This does `git branch` + `git checkout` in one command. Use this one.

### Try It Now

```bash

git branch
```

Output should show:

```

* feature-test-branch
```

## Part 3: Making Changes on a Branch (20 min)

### The Problem

You're on a feature branch. You make changes, commit them. Meanwhile, `main` stays untouched. This is the whole point — isolation.

### The Workflow

**Step 1: Make sure you're on the feature branch**

```bash
git checkout feature-test-branch
```

**Step 2: Make a change**

```bash
echo "# Feature Branch" > feature.md
git add feature.md
git commit -m "add feature.md on feature branch"
```

**Step 3: Check the branch state**

```bash
git log --oneline
```

Output:

```
a1b2c3d (HEAD -> feature-test-branch) add feature.md on feature branch
x9y8z7w (main) previous commit message
```

**Step 4: Switch back to main**

```bash
git checkout main
```

**Step 5: Check if the file exists on main**

```bash
ls feature.md
```

Output:

```
ls: cannot access 'feature.md': No such file or directory
```

The file doesn't exist on `main`. The change is isolated to `feature-test-branch`. That's branching working perfectly.

**Step 6: Switch back and confirm**

```bash
git checkout feature-test-branch
ls feature.md
```

Output:

```
feature.md
```

It's there. Your changes are safe on your branch.

## Part 4: Merging Branches (20 min)

### The Problem

Your feature is done. You tested it. Now you want to bring those changes into `main`. That's merging.

### The Workflow

**Step 1: Switch to the branch you want to merge INTO**

```bash
git checkout main
```

**Step 2: Merge the feature branch**

```bash
git merge feature-test-branch
```

Output:

```
Updating x9y8z7w..a1b2c3d
Fast-forward
 feature.md | 1 +
 1 file changed, 1 insertion(+)
 create mode 100644 feature.md
```

"Fast-forward" means `main` was behind and just moved forward. No conflicts.

**Step 3: Verify**

```bash
ls feature.md
git log --oneline
```

The file is on `main` now. The commit history shows the merge.

**Step 4: Delete the feature branch (cleanup)**

```bash
git branch -d feature-test-branch
```

Output:

```
Deleted branch feature-test-branch (was a1b2c3d).
```

The branch is gone, but the commits remain on `main`. Branches are just labels — deleting them doesn't delete work.

### What "Fast-Forward" Means

When you merge and `main` hasn't changed since you created the branch, Git just moves the `main` pointer forward. No extra commit needed. This is clean and common.

## Part 5: Handling Merge Conflicts (20 min)

### The Problem

You and a teammate both edited the same line in the same file on different branches. When you try to merge, Git doesn't know which version to keep. That's a merge conflict.

### The Scenario

**Step 1: Create a conflict**

```bash
git checkout -b branch-a
echo "line from branch-a" > conflict.txt
git add conflict.txt
git commit -m "edit on branch-a"
```

```bash
git checkout main
echo "line from main" > conflict.txt
git add conflict.txt
git commit -m "edit on main"
```

**Step 2: Try to merge**

```bash
git merge branch-a
```

Output:

```
Auto-merging conflict.txt
CONFLICT (content): Merge conflict in conflict.txt
Automatic merge failed; fix conflicts and then commit the result.
```

Git is confused. Both branches changed the same file. You need to decide.

**Step 3: Open the file**

```bash
cat conflict.txt
```

Output:

```
<<<<<<< HEAD
line from main
=======
line from branch-a
>>>>>>> branch-a
```

- `<<<<<<< HEAD` — what's on `main` (the branch you're on)
- `=======` — separator
- `>>>>>>> branch-a` — what's on the other branch

**Step 4: Fix it**

Edit the file. Keep what you want, remove the markers:

```bash
echo "line from branch-a" > conflict.txt
```

Or combine both:

```bash
echo "line from main" > conflict.txt
echo "line from branch-a" >> conflict.txt
```

**Step 5: Commit the merge**

```bash
git add conflict.txt
git commit -m "merge branch-a, resolved conflict"
```

The conflict is resolved. The merge is complete.

### Try It Now

```bash
cd ~/devops_learning/projects/Online-voting-system

echo "version A" > demo.txt
git add demo.txt
git commit -m "version A"

git checkout main
echo "version B" > demo.txt
git add demo.txt
git commit -m "version B"

git merge conflict-demo
cat demo.txt
# Edit to resolve, then:
git add demo.txt
git commit -m "resolved conflict"
```

## Part 6: Build Task — Branch Workflow Script (30 min)

Let's build a script that automates a proper branching workflow — the kind used in real teams.

### Create the Script

```bash
cat > ~/devops_learning/scripts/branch-workflow.sh << 'EOF'
#!/bin/bash
# branch-workflow.sh — Create a feature branch, make changes, merge back
# Usage: ./branch-workflow.sh <branch-name> <file-name> <content>

set -e

BRANCH_NAME=$1
FILE_NAME=$2
CONTENT=$3

if [ -z "$BRANCH_NAME" ] || [ -z "$FILE_NAME" ] || [ -z "$CONTENT" ]; then
    echo "Usage: ./branch-workflow.sh <branch-name> <file-name> <content>"
    echo "Example: ./branch-workflow.sh feature-add-api api.md \"# API Documentation\""
    exit 1
fi

echo "=== Step 1: Ensuring we're on main ==="
git checkout main

echo "=== Step 2: Creating and switching to branch: $BRANCH_NAME ==="
git checkout -b "$BRANCH_NAME"

echo "=== Step 3: Creating file: $FILE_NAME ==="
echo "$CONTENT" > "$FILE_NAME"
git add "$FILE_NAME"
git commit -m "add $FILE_NAME on $BRANCH_NAME"

echo "=== Step 4: Switching back to main ==="
git checkout main

echo "=== Step 5: Merging $BRANCH_NAME into main ==="
git merge "$BRANCH_NAME"

echo "=== Step 6: Cleaning up branch ==="
git branch -d "$BRANCH_NAME"

echo "=== Done! ==="
echo "File '$FILE_NAME' is now on main."
echo "Branch '$BRANCH_NAME' has been deleted."
git log --oneline -3
EOF

chmod +x ~/devops_learning/scripts/branch-workflow.sh
```

### What This Does

1. Switches to `main` (safe starting point)
2. Creates a feature branch
3. Creates a file, commits it
4. Switches back to `main`
5. Merges the feature branch
6. Deletes the feature branch (cleanup)

This is the standard workflow in every professional team. The branch exists only while you're working on the feature.

### Test It

```bash
cd ~/devops_learning/projects/Online-voting-system
~/devops_learning/scripts/branch-workflow.sh feature-add-changelog CHANGELOG.md "# Changelog\n\n- Day 9: Added branching workflow"
```

Output should show each step executing and end with the commit history.

### Real-World Value

In a real job, this is how you'll work:
1. Get a ticket (task)
2. Create a branch from `main`
3. Make changes, commit often
4. Push branch, open a Pull Request
5. Team reviews, you fix feedback
6. Merge to `main`
7. Delete the branch

The script above covers steps 2-7 locally. Day 10 covers pushing and Pull Requests.

### The Pattern — When You Need a Branch

1. `git status` — make sure working tree is clean
2. `git checkout main` — start from stable code
3. `git checkout -b feature-<name>` — create isolated workspace
4. Make changes, commit often with `git add . && git commit -m "description"`
5. `git checkout main` — go back to stable code
6. `git merge feature-<name>` — bring changes back
7. `git branch -d feature-<name>` — clean up
