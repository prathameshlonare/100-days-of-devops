## Part 1: Why This Matters for Dorm-and-Dish & Core Mental Model (15 min)

When you deploy Dorm-and-Dish in a CI/CD pipeline, temporary preview environments will be spun up for pull requests and torn down when the PR merges. If `terraform destroy` fails, orphan resources keep running in AWS, quietly generating hundreds of dollars in unexpected cloud bills.

### The Dependency Graph (Creation vs Destruction)

Terraform calculates resource order using a **Directed Acyclic Graph (DAG)**:

```
[ CREATION ORDER: Forward Graph ]
aws_vpc.this
  └── aws_subnet.public & aws_internet_gateway.this
        └── aws_route_table.public & aws_security_group.this
              └── aws_instance.this

[ DESTRUCTION ORDER: Inverted Reverse Graph ]
aws_instance.this  (Terminated first)
  └── aws_security_group.this & aws_route_table.public  (Deleted second)
        └── aws_subnet.public & aws_internet_gateway.this  (Deleted third)
              └── aws_vpc.this  (Deleted last)
```

1. **Creation:** Dependencies are created from the outside in (VPC first, compute last).
2. **Destruction:** Dependencies are deleted from the inside out (compute first, VPC last).

### The Real-World Nightmare: `DependencyViolation`
AWS will **refuse** to delete a subnet or VPC if any active resource (such as an unmanaged Elastic Network Interface, an AWS Lambda ENI, or an unmanaged load balancer) is still attached to it. Terraform cannot delete what it does not know about.

## Part 2: Hands-On Build (60 min)

### Build the Full Multi-Tier Stack

1. Create your workspace directory:
   ```bash
   mkdir -p D:\projects\Learning\devops-journey\01-daily-posts\day-029\day-29-tf
   cd D:\projects\Learning\devops-journey\01-daily-posts\day-029\day-29-tf
   ```

2. Create `provider.tf`:
   ```hcl
   terraform {
     required_version = ">= 1.5.0"
     required_providers {
       aws = {
         source  = "hashicorp/aws"
         version = "~> 5.0"
       }
     }
   }

   provider "aws" {
     region = "eu-north-1"
   }
   ```

3. Create `main.tf`:
   ```hcl
   # 1. Dynamic AMI Lookup
   data "aws_ami" "amazon_linux_2023" {
     most_recent = true
     owners      = ["amazon"]

     filter {
       name   = "name"
       values = ["al2023-ami-2023.*-x86_64"]
     }
   }

   # 2. VPC
   resource "aws_vpc" "this" {
     cidr_block           = "10.29.0.0/16"
     enable_dns_support   = true
     enable_dns_hostnames = true

     tags = {
       Name = "day29-lab-vpc"
     }
   }

   # 3. Public Subnet
   resource "aws_subnet" "public" {
     vpc_id                  = aws_vpc.this.id
     cidr_block              = "10.29.1.0/24"
     availability_zone       = "eu-north-1a"
     map_public_ip_on_launch = true

     tags = {
       Name = "day29-lab-public-sub"
     }
   }

   # 4. Internet Gateway
   resource "aws_internet_gateway" "this" {
     vpc_id = aws_vpc.this.id

     tags = {
       Name = "day29-lab-igw"
     }
   }

   # 5. Route Table
   resource "aws_route_table" "public" {
     vpc_id = aws_vpc.this.id

     route {
       cidr_block = "0.0.0.0/0"
       gateway_id = aws_internet_gateway.this.id
     }

     tags = {
       Name = "day29-lab-public-rt"
     }
   }

   resource "aws_route_table_association" "public" {
     subnet_id      = aws_subnet.public.id
     route_table_id = aws_route_table.public.id
   }

   # 6. Security Group
   resource "aws_security_group" "web_sg" {
     name        = "day29-lab-sg"
     description = "Allow inbound SSH and HTTP"
     vpc_id      = aws_vpc.this.id

     ingress {
       description = "SSH"
       from_port   = 22
       to_port     = 22
       protocol    = "tcp"
       cidr_blocks = ["0.0.0.0/0"]
     }

     ingress {
       description = "HTTP"
       from_port   = 80
       to_port     = 80
       protocol    = "tcp"
       cidr_blocks = ["0.0.0.0/0"]
     }

     egress {
       from_port   = 0
       to_port     = 0
       protocol    = "-1"
       cidr_blocks = ["0.0.0.0/0"]
     }

     tags = {
       Name = "day29-lab-sg"
     }
   }

   # 7. EC2 Web Server
   resource "aws_instance" "web" {
     ami                         = data.aws_ami.amazon_linux_2023.id
     instance_type               = "t3.micro"
     subnet_id                   = aws_subnet.public.id
     vpc_security_group_ids      = [aws_security_group.web_sg.id]
     associate_public_ip_address = true

     user_data = <<-EOF
                 #!/bin/bash
                 dnf update -y
                 dnf install -y httpd
                 systemctl start httpd
                 systemctl enable httpd
                 echo "<h1>Day 29: Full Lifecycle Lab Online</h1>" > /var/www/html/index.html
                 EOF

     tags = {
       Name = "day29-lab-ec2"
     }
   }
   ```

## Part 3: Break-It Lab & Live Triage (45 min)

**INTENTIONAL TEARDOWN BLOCKER — Safe scratch lab.**

### What We're Breaking: Rogue ENI Dependency Blocker
We will inject an unmanaged AWS Elastic Network Interface (ENI) directly into our subnet via the AWS CLI (simulating another engineer attaching a network card or an AWS service like a Lambda function or RDS proxy provisioning an interface inside your subnet).

When you run `terraform destroy`, Terraform will terminate the EC2 instance, but when it attempts to delete the Subnet and VPC, the AWS API will reject the request with `DependencyViolation`.

---

### Step 1: Inject the Unmanaged ENI into your Subnet
1. Grab your subnet ID from Terraform:
   ```powershell
   $SUBNET_ID = terraform output -raw subnet_id
   ```
2. Create an unmanaged network interface directly in AWS:
   ```powershell
   aws ec2 create-network-interface --subnet-id $SUBNET_ID --description "Rogue unmanaged ENI blocker" --tag-specifications "ResourceType=network-interface,Tags=[{Key=Name,Value=rogue-blocker-eni}]" --region eu-north-1
   ```
   *(Notice AWS creates the ENI. Terraform has zero record of it in `terraform.tfstate`!)*

---

### Step 2: Trigger the Teardown Failure
Now attempt to destroy your environment:
```powershell
terraform destroy -auto-approve
```

### Symptoms to Observe
Terraform terminates the EC2 instance and deletes the security group, but suddenly crashes on the subnet deletion:

```text
aws_instance.web: Destruction complete after 30s
aws_security_group.web_sg: Destruction complete after 2s
aws_route_table_association.public: Destruction complete after 1s
aws_route_table.public: Destruction complete after 1s
aws_internet_gateway.this: Destruction complete after 1s
aws_subnet.public: Destroying... [id=subnet-0xxxxxxxxxxxx]
╷
│ Error: deleting EC2 Subnet (subnet-0xxxxxxxxxxxx): DependencyViolation: The subnet 'subnet-0xxxxxxxxxxxx' has dependencies and cannot be deleted.
│   status code: 400, request id: xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx
╵
```

Terraform halts. The Subnet and the VPC are stuck in your AWS account and cannot be deleted!

---

### Step 3: Diagnostic Triage (Investigate the Hostage Subnet)
Run these checks in your terminal to see why the subnet cannot be deleted:

1. **Query all active network interfaces inside the stuck subnet:**
   ```powershell
   aws ec2 describe-network-interfaces --filters "Name=subnet-id,Values=$SUBNET_ID" --region eu-north-1 --query "NetworkInterfaces[].[NetworkInterfaceId,Description,Status]" --output table
   ```

2. **Output:**
   ```text
   --------------------------------------------------------------
   |                  DescribeNetworkInterfaces                 |
   +-----------------------+-----------------------------+------+
   |  eni-0a1b2c3d4e5f67890| Rogue unmanaged ENI blocker | available|
   +-----------------------+-----------------------------+------+
   ```
   **Evidence:** The rogue ENI is sitting inside the subnet in `available` status, holding the subnet hostage.

---

### Step 4: The Fix — Clear the Dependency & Complete Teardown
1. Delete the unmanaged network interface:
   ```powershell
   # Grab the ENI ID from the previous query and delete it:
   aws ec2 delete-network-interface --network-interface-id <eni-id-here> --region eu-north-1
   ```

2. Now re-run `terraform destroy`:
   ```powershell
   terraform destroy -auto-approve
   ```

3. **Verify:**
   ```text
   aws_subnet.public: Destruction complete after 1s
   aws_vpc.this: Destruction complete after 1s

   Destroy complete! Resources: 2 destroyed.
   ```
   The dependency blocker is gone, and Terraform cleanly removes the subnet and VPC.

## Part 4: Troubleshooting Record

```markdown
## Troubleshooting Record — Day 029
**Problem:** `terraform destroy` failed with `DependencyViolation: The subnet has dependencies and cannot be deleted`.
**Symptoms:** EC2 and SG deleted successfully, but subnet and VPC destruction aborted with HTTP 400.
**Environment:** Terraform v1.5+ -> AWS Stockholm (eu-north-1).
**What I checked:** 
1. Checked whether any EC2 instances were still shutting down.
2. Queried the AWS EC2 API for active network interfaces attached to the subnet using `aws ec2 describe-network-interfaces`.
**Commands used:** 
- `terraform destroy`
- `aws ec2 describe-network-interfaces --filters "Name=subnet-id,Values=..."`
- `aws ec2 delete-network-interface --network-interface-id ...`
**Evidence:** An unmanaged Elastic Network Interface (ENI) was discovered in `available` state inside the subnet.
**Hypothesis:** An out-of-band resource was attached to the subnet, preventing the AWS EC2 control plane from allowing subnet deletion.
**Root Cause:** Subnets cannot be deleted while ENIs exist inside their CIDR block. Because the ENI was created outside Terraform, Terraform's dependency graph had no knowledge of it.
**Fix:** Manually deleted the unmanaged ENI via AWS CLI, then re-ran `terraform destroy`.
**Verification:** Subnet and VPC destroyed cleanly; `terraform show` confirmed empty state.
**Prevention:** In shared AWS accounts, avoid manual ENI creation. Enforce automated tagging and IAM service control policies (SCPs) to prevent rogue resource attachments in automated pipeline subnets.
**What I learned:** Terraform destroys resources in reverse dependency order, but out-of-band cloud dependencies cause API-level `DependencyViolation` crashes.
```

## Part 5: Job Readiness & Interview Defense (15 min)

### Interview Question:
*"During a CI/CD pipeline teardown of an ephemeral environment, `terraform destroy` fails with `DependencyViolation: The subnet has active dependencies`. The pipeline fails and blocks subsequent deployments. How do you triage, resolve, and prevent this?"*

### Top 1% Senior Answer Breakdown:
1. **Explain the physical mechanism:** AWS subnets cannot be deleted while any ENI (Elastic Network Interface) has an IP allocated inside that subnet's CIDR block.
2. **Immediate triage:** Run `aws ec2 describe-network-interfaces --filters Name=subnet-id,Values=<id>` to identify the ENI's description, attached instance, or requester ID (e.g. `amazon-elb`, `lambda.amazonaws.com`, or manual).
3. **Resolve:** If it's a managed AWS service (like an ALB or RDS instance), delete the parent resource first. If it's an orphaned ENI, detach and delete it via `aws ec2 delete-network-interface`, then resume `terraform destroy`.
4. **Prevention:** Implement automated pre-destroy pipeline hooks or AWS Config rules to flag unmanaged ENIs, and isolate ephemeral pipeline environments into dedicated subnets.
