## Part 2: EC2 Instances and AMIs (20 min)

### The Problem

You need a server. Not a physical one — a virtual one that you can create in 2 minutes, destroy when you're done, and pay only for what you use. That's EC2.

### The Concept

An **EC2 instance** is a virtual machine running in AWS data centers. You pick:
1. **AMI (Amazon Machine Image)** — the operating system (Ubuntu, Amazon Linux, etc.)
2. **Instance Type** — how much CPU/RAM you get
3. **Key Pair** — how you'll authenticate
4. **Security Group** — what traffic is allowed in/out

Think of it like this:
- **AMI** = the OS installation disc (but pre-installed)
- **Instance Type** = the hardware specs (CPU, RAM)
- **Key Pair** = your SSH key (password authentication)
- **Security Group** = the firewall rules

### Instance Types — What to Pick

| Type | vCPU | RAM | Cost/hr | Use Case |
|------|------|-----|---------|----------|
| `t2.micro` | 1 | 1 GB | ~$0.01 | Free tier, testing, learning |
| `t2.small` | 1 | 2 GB | ~$0.02 | Small apps, light traffic |
| `t2.medium` | 2 | 4 GB | ~$0.04 | Medium workloads |
| `t3.micro` | 2 | 1 GB | ~$0.01 | Burstable, free tier eligible |

**For today:** Use `t2.micro` — it's free tier eligible (750 hrs/month for 12 months).

## Part 3: Key Pairs — Your SSH Key (15 min)

### The Problem

When you create an EC2 instance, you need a way to prove you're you when connecting. AWS uses **key pairs** — cryptographic keys that replace passwords.

### The Concept

SSH key pairs work like a lock and key:
- **Public key** (lock) — stored on the EC2 instance
- **Private key** (key) — stored on your machine (the `.pem` file)

When you connect, your private key proves you have access. Without it, SSH refuses to connect.

### Creating a Key Pair

**Option A: Through AWS Console (recommended for first time)**
1. EC2 → **Key Pairs** → **Create key pair**
2. Name: `dorm-and-dish-key`
3. Type: RSA
4. Format: `.pem` (for Windows/Linux/Mac)
5. Click **Create key pair**
6. The `.pem` file downloads automatically — **save it somewhere safe**

**Option B: Through AWS CLI**
```bash
aws ec2 create-key-pair \
  --key-name dorm-and-dish-key \
  --query 'KeyMaterial' \
  --output text > dorm-and-dish-key.pem
```

### Critical: Protect Your Key

```bash
# On Linux/Mac — set read-only permissions
chmod 400 dorm-and-dish-key.pem

# On Windows (PowerShell) — restrict access
icacls dorm-and-dish-key.pem /inheritance:r /grant:r "$($env:USERNAME):(R)"
```

**Why this matters:** SSH refuses to use a key file that's too permissive. If your key is readable by others, SSH will warn you or refuse to connect.

### Exercise 2 — Create Your Key Pair

1. Go to EC2 → Key Pairs → Create key pair
2. Name it `dorm-and-dish-key`
3. Download the `.pem` file
4. Move it to a secure location (e.g., `~/.ssh/dorm-and-dish-key.pem`)
5. Set permissions (Linux/Mac): `chmod 400 ~/.ssh/dorm-and-dish-key.pem`
6. Verify: `ls -la ~/.ssh/dorm-and-dish-key.pem` — should show `-r--------`

## Part 4: Security Groups — Your Firewall (20 min)

### The Problem

An EC2 instance with no security group rules is either completely inaccessible or completely open. You need to define exactly what traffic is allowed.

### The Concept

A **Security Group** is a stateful firewall at the instance level. It controls:
- **Inbound rules** — what traffic can reach your instance
- **Outbound rules** — what traffic your instance can send (default: all allowed)

"Stateful" means: if you allow inbound traffic on port 80, the response traffic is automatically allowed back out — you don't need a separate outbound rule for the response.

### Essential Rules for Today

| Direction | Protocol | Port | Source | Purpose |
|-----------|----------|------|--------|---------|
| Inbound | TCP | 22 | Your IP | SSH access |
| Inbound | TCP | 80 | 0.0.0.0/0 | HTTP (nginx) |
| Outbound | All | All | 0.0.0.0/0 | Default — allow all |

### The Critical Difference: 0.0.0.0/0 vs Your IP

| Source | What It Means | Risk |
|--------|---------------|------|
| `0.0.0.0/0` | Anyone on the internet | High — anyone can try to connect |
| `My IP` | Only your current IP address | Low — only you can connect |

**For SSH:** Use "My IP" — you don't want the whole internet trying to SSH into your server.
**For HTTP:** Use `0.0.0.0/0` — you want anyone to access your website.

### Creating a Security Group

1. EC2 → **Security Groups** → **Create security group**
2. Name: `dorm-and-dish-sg`
3. Description: "SSH + HTTP for Dorm-and-Dish"
4. VPC: Default VPC (or the one you'll use)
5. **Inbound rules:**
   - Type: SSH, Port: 22, Source: My IP
   - Type: HTTP, Port: 80, Source: Anywhere (`0.0.0.0/0`)
6. **Outbound rules:** Leave default (allow all)
7. Click **Create security group**

### Exercise 3 — Create Your Security Group

1. Create the security group as described above
2. After creating, click on it → **Inbound rules** tab
3. Verify you see exactly 2 rules: SSH (22) and HTTP (80)
4. Note the Security Group ID (starts with `sg-`)

## Part 6: EC2 Status Checks — 1/2 vs 2/2 (10 min)

### The Problem

Your instance shows "Running" — but is it actually healthy? EC2 has two built-in status checks that tell you whether the problem is AWS infrastructure or your OS configuration.

### The Two Status Checks

| Check | What It Tests | Who Fixes It |
|-------|---------------|--------------|
| **System Status Check (1/2)** | Is the underlying AWS hardware/network healthy? | AWS — you can't fix this |
| **Instance Status Check (2/2)** | Is your OS booting and responding correctly? | You — wrong AMI, bad config, corrupted filesystem |

### What You'll See in the Console

```
Status Checks
  ✓ 2/2 checks passed
```

or if something is wrong:

```
Status Checks
  ✗ 1/2 checks passed
  System Status Check: Failed
  Instance Status Check: Failed
```

### When Each Fails

| Symptom | Likely Cause | What To Do |
|---------|--------------|------------|
| System check failed | AWS hypervisor issue, host hardware problem | Stop → Start (NOT reboot) to migrate to new host. If persistent, contact AWS Support. |
| Instance check failed | OS not booting, kernel panic, incorrect user data, disk corruption | Get system log (Actions → Monitor → Get system log), check for boot errors |
| Both failed | Could be either — start with system check | Stop → Start first; if still failing, check system log |

### Key Difference: Stop/Start vs Reboot

- **Reboot** = same underlying host. If the host is broken, reboot won't help.
- **Stop/Start** = new host. Migrates your instance to healthy AWS infrastructure.

### Exercise 5 — Check Your Status

1. Click on your instance
2. Find **Status Checks** tab
3. Confirm: **2/2 checks passed**
4. Note: If you see 1/2 or 0/2, the next step is to check the system log — not to assume your code is broken

## Part 8: Break-It Lab — SSH Failure (20 min)

**INTENTIONAL FAILURE — Safe to break, safe to fix**

### What We're Breaking

We'll simulate the most common SSH failure: **Connection refused / Timeout** caused by a Security Group misconfiguration.

### Steps to Break It

**Method 1: Remove SSH rule from Security Group**

1. Go to EC2 → Security Groups → `dorm-and-dish-sg`
2. **Inbound rules** → Edit inbound rules
3. **Delete** the SSH (port 22) rule
4. Save rules
5. Try to SSH again:
   ```bash
   ssh -i ~/.ssh/dorm-and-dish-key.pem ubuntu@YOUR_PUBLIC_IP
   ```

**What happens:** The command hangs, then times out after ~30 seconds:
```
ssh: connect to host 54.123.45.67 port 22: Connection timed out
```

### Symptoms to Observe

| Symptom | What It Means |
|---------|---------------|
| Hangs for 30 seconds then times out | Packet is being dropped (not rejected) |
| No "Connection refused" message | The port is blocked, not closed |
| `curl` to port 22 also hangs | It's a network/firewall issue, not SSH service issue |

### YOUR TURN: Diagnose

Before I show you the fix, answer:
1. What would you check first?
2. Which command would give you the most information?
3. What's your hypothesis?

**Investigation path (try these):**

```bash
# Step 1: Can you reach the server at all?
ping -c 4 YOUR_PUBLIC_IP

# Step 2: Can you reach port 80 (HTTP)?
curl -I http://YOUR_PUBLIC_IP

# Step 3: Can you reach port 22 (SSH)?
nc -zv YOUR_PUBLIC_IP 22
# Or from Windows:
Test-NetConnection -ComputerName YOUR_PUBLIC_IP -Port 22

# Step 4: Check the security group in AWS Console
# EC2 → Security Groups → dorm-and-dish-sg → Inbound rules
```

### The Fix

1. Go to Security Groups → `dorm-and-dish-sg` → Inbound rules → Edit
2. **Add rule:**
   - Type: SSH
   - Port: 22
   - Source: My IP
3. Save rules
4. Try SSH again — it connects immediately

### What You Should Notice

- Ping worked (ICMP is allowed by default outbound)
- HTTP worked (port 80 was open)
- SSH failed (port 22 was blocked)
- **The problem was the Security Group, not the SSH service**

## Part 9: Troubleshooting Challenge — EC2 Instance Unreachable (15 min)

**Scenario-based debugging — I won't give you the answer immediately**

### Scenario

You just launched an EC2 instance for Dorm-and-Dish. The console shows "Running" and "2/2 checks passed." Your friend tries to open `http://YOUR_PUBLIC_IP` in their browser and gets: **"This site can't be reached — ERR_CONNECTION_TIMED_OUT."**

You try to SSH and also get a timeout. But you can ping the public IP just fine.

### Investigation Path

Follow this chain (don't skip steps):

**1. SYMPTOM: What's happening?**
- HTTP times out from friend's browser
- SSH times out from your machine
- Ping works

**2. OBSERVATION: What do the logs/show?**
```bash
# From your machine:
ping -c 4 YOUR_PUBLIC_IP          # Works
curl -I http://YOUR_PUBLIC_IP     # Times out
ssh -i key.pem ubuntu@IP          # Times out
```

**3. HYPOTHESIS: What could cause this?**
- Security Group missing HTTP (80) and SSH (22) inbound rules?
- NACL blocking inbound traffic?
- Instance in a private subnet with no route to internet?
- Route table missing Internet Gateway route?

**4. CHECK: What command verifies your hypothesis?**
```bash
# Check if port 80 is reachable:
nc -zv YOUR_PUBLIC_IP 80
# Or from PowerShell:
Test-NetConnection -ComputerName YOUR_PUBLIC_IP -Port 80

# Check if port 22 is reachable:
nc -zv YOUR_PUBLIC_IP 22
```

**5. EVIDENCE: What did you find?**
- `nc -zv IP 80` → Connection timed out (port 80 blocked)
- `nc -zv IP 22` → Connection timed out (port 22 blocked)
- Ping works → IP-level connectivity is fine

**6. ROOT CAUSE: Why did this happen?**
The Security Group was created with **no inbound rules**. Both HTTP and SSH are blocked at the instance firewall level. Ping works because ICMP is allowed by default in the VPC's NACL, but TCP ports 22 and 80 require explicit Security Group rules.

**7. FIX: What's the solution?**
1. EC2 → Security Groups → `dorm-and-dish-sg` → Inbound rules → Edit
2. Add rule: SSH (22), Source: My IP
3. Add rule: HTTP (80), Source: Anywhere (`0.0.0.0/0`)
4. Save rules

**8. VERIFY: How do you confirm it's fixed?**
```bash
# Test SSH:
ssh -i key.pem ubuntu@YOUR_PUBLIC_IP    # Connects immediately

# Test HTTP:
curl -I http://YOUR_PUBLIC_IP           # Returns 200 OK

# Friend opens browser → sees nginx default page
```

**9. PREVENTION: How do you avoid this next time?**
- Always verify Security Group rules immediately after launch
- Keep a checklist: SSH (22) from My IP + HTTP (80) from 0.0.0.0/0
- Use infrastructure-as-code (Terraform) to define Security Groups — less chance of forgetting a rule

## Part 12: Root-Cause Discussion + Troubleshooting Record (10 min)

### Why the Break-Fix Worked

The SSH failure wasn't random. Here's the chain:

```
SSH connection request
    │
    ├── Your machine sends TCP SYN to port 22
    ├── AWS Security Group checks: "Is port 22 allowed from this IP?"
    ├── Answer: NO (we deleted the rule)
    └── AWS drops the packet (no response at all)
```

**Key insight:** When a Security Group blocks traffic, the packet is **dropped** — not rejected. That's why you see "Connection timed out" instead of "Connection refused." A dropped packet gets no response, so your client waits until it gives up.

### What the Symptoms Told Us

| Symptom | Told Us |
|---------|---------|
| Ping worked | Server is reachable at the IP level |
| HTTP worked | Port 80 is open |
| SSH timed out | Port 22 is blocked (not closed) |
| No error from server | Problem is upstream (firewall), not on the server |

### The Mental Model

When something is unreachable:
1. **Is the server alive?** → Ping it
2. **Is the specific port open?** → `nc -zv IP PORT`
3. **If port is blocked:** → Check Security Group rules
4. **If port is open but connection fails:** → Check the service on the server

### Troubleshooting Record

```
## Troubleshooting Record — Day 20

**Problem:** SSH connection to EC2 times out
**Symptoms:** `ssh: connect to host X port 22: Connection timed out`
**Environment:** AWS EC2 (t2.micro, Ubuntu 22.04)
**What I checked:**
1. `ping IP` → worked (server is reachable)
2. `curl http://IP` → worked (port 80 open)
3. `nc -zv IP 22` → timed out (port 22 blocked)

**Commands used:**
- `ping -c 4 IP` — confirmed basic connectivity
- `curl -I http://IP` — confirmed port 80 accessible
- `nc -zv IP 22` — confirmed port 22 unreachable

**Evidence:** Ping and HTTP worked, SSH didn't. Problem is port-specific, not server-wide.

**Hypothesis:** Security Group is blocking port 22.

**Root Cause:** SSH (port 22) inbound rule was missing from Security Group.

**Fix:** Added SSH rule (port 22, Source: My IP) to Security Group.

**Verification:** SSH connected immediately after adding the rule.

**Prevention:** Always verify Security Group rules before launching instances. Keep a checklist of required ports.

**What I learned:** A dropped packet (Security Group) looks different from a closed port (service not running). Timeout = firewall. Refused = service issue.
```

**Interview Question:**

"A customer launches an EC2 instance but can't SSH into it. Walk me through your troubleshooting steps."

**Strong answer includes:**
1. Verify the instance is in **Running** state
2. Check **Security Group** — is port 22 allowed from their IP?
3. Check if the instance has a **public IP** (auto-assign enabled?)
4. Verify the **key pair** matches the one attached to the instance
5. Check the **username** — Ubuntu uses `ubuntu`, Amazon Linux uses `ec2-user`
6. Verify key file **permissions** (chmod 400 on Linux/Mac)
7. Check **NACL** (subnet-level firewall) — is ephemeral port range allowed outbound?
8. If all else fails: **get console output** from AWS Console → Instance → Actions → Monitor and troubleshoot → Get system log

### The Pattern — When SSH Fails

1. **Ping the IP** — is the server reachable? (If no → instance issue or network issue)
2. **Check port with `nc -zv`** — is the specific port open? (If no → Security Group or NACL)
3. **Check Security Group** — is the inbound rule there? (Most common cause)
4. **Check NACL** — subnet-level blocking? (Less common)
5. **Check Status Checks** — 1/2 = AWS infra issue (stop/start), 2/2 = your config
6. **Check console output** — any boot errors? (Last resort)
