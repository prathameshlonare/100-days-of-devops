## Part 1: Why This Matters for Dorm-and-Dish (15 min)

Your project repo has a 575-line `main.tf` (AI-generated, reference-only). That file mixes VPC, subnets, SGs, EC2, and outputs in one flat list. Three reasons that fails in a team:

1. **Blast radius:** One typo in a subnet CIDR forces you to re-read 575 lines to find it. A module isolates the fault to `modules/vpc/`.
2. **Copy-paste drift:** Need the same VPC shape for `dev` and `prod`? Without modules you copy-paste 100 lines twice and they drift. With modules you call the same block twice with different inputs.
3. **Undefendable in interviews:** "Explain line 340 of main.tf" is unanswerable. "Explain my `sg` module's inputs and outputs" is answerable — and it is what the Day 68 drill tests.

### Feeder Role Relevance

- **Cloud Support Engineer:** Customers paste `module "vpc" { source = "./modules/vpc" }` errors (`Module not installed`, `Unsupported attribute`). You must read the module wiring, not just the resource.
- **Junior DevOps Engineer:** Every production TF repo is modules + thin root. If you can only write flat files, you cannot contribute.

### Concept Table

| Concept | What it is | Analogy |
|---|---|---|
| Root module | The directory where you run `terraform apply` | `main()` function |
| Child module | A folder with its own `.tf` files, called via `module` block | Imported function |
| `source` | Path (or registry address) of the child module | Import path |
| Input variable | `variable` block inside child, value passed from root | Function parameter |
| Output value | `output` block inside child, read as `module.<name>.<out>` | Return value |
| Data source | Read-only lookup (`data "aws_ssm_parameter"`) | Live query, never creates infra |

## Part 2: Module Anatomy — The 4 Files (30 min)

### The Problem

You know resources (`resource "aws_vpc"`) and variables from Days 24-25, but you have never packaged them. What are the minimum pieces of a module?

### Build It Now

A local module is just a folder with `.tf` files. Terraform treats **every folder** as a module; the one you `cd` into is the root. Three rules:

1. **Child never configures provider/backend.** Only the root has `provider.tf` (and later `backend.tf`). Children inherit the provider.
2. **Child communicates ONLY via `variables.tf` (in) and `outputs.tf` (out).** Never hardcode environment-specific values inside a child — pass them in.
3. **Root calls children with `module` blocks.** Changing inputs = new infrastructure without editing the child.

```
day-27-tf/
├── main.tf            # root: three module blocks
├── variables.tf       # root inputs (region, CIDRs, instance type)
├── outputs.tf         # root re-exports (vpc_id, subnet_id, instance_id)
├── provider.tf        # root only
└── modules/
    ├── vpc/
    │   ├── main.tf        # aws_vpc + subnet + IGW + route table
    │   ├── variables.tf   # vpc_cidr, subnet_cidr, az, name_prefix
    │   └── outputs.tf     # vpc_id, subnet_id
    ├── sg/
    │   ├── main.tf        # aws_security_group
    │   ├── variables.tf   # vpc_id, allowed_ssh_cidr
    │   └── outputs.tf     # sg_id
    └── ec2/
        ├── main.tf        # aws_instance (+ data aws_ssm after fix)
        ├── variables.tf   # subnet_id, sg_id, instance_type, ami_id
        └── outputs.tf     # instance_id, public_ip
```

## Part 3: Build the `vpc` Module (30 min)

### The Problem

We need a VPC + public subnet + IGW + route, but packaged so Day 28 workspaces can call it twice (dev/prod) without edits.

### Build It Now

**`modules/vpc/variables.tf`:**

```hcl
variable "vpc_cidr" {
  description = "CIDR for the VPC"
  type        = string
  default     = "10.27.0.0/16"
}

variable "subnet_cidr" {
  description = "CIDR for the public subnet"
  type        = string
  default     = "10.27.1.0/24"
}

variable "az" {
  description = "Availability zone"
  type        = string
  default     = "eu-north-1a"
}

variable "name_prefix" {
  description = "Prefix for Name tags"
  type        = string
  default     = "day27-lab"
}
```

**`modules/vpc/main.tf`:**

```hcl
resource "aws_vpc" "this" {
  cidr_block           = var.vpc_cidr
  enable_dns_support   = true
  enable_dns_hostnames = true

  tags = {
    Name = "${var.name_prefix}-vpc"
  }
}

resource "aws_subnet" "public" {
  vpc_id                  = aws_vpc.this.id
  cidr_block              = var.subnet_cidr
  availability_zone       = var.az
  map_public_ip_on_launch = true

  tags = {
    Name = "${var.name_prefix}-public-sub"
  }
}

resource "aws_internet_gateway" "this" {
  vpc_id = aws_vpc.this.id

  tags = {
    Name = "${var.name_prefix}-igw"
  }
}

resource "aws_route_table" "public" {
  vpc_id = aws_vpc.this.id

  route {
    cidr_block = "0.0.0.0/0"
    gateway_id = aws_internet_gateway.this.id
  }

  tags = {
    Name = "${var.name_prefix}-public-rt"
  }
}

resource "aws_route_table_association" "public" {
  subnet_id      = aws_subnet.public.id
  route_table_id = aws_route_table.public.id
}
```

**`modules/vpc/outputs.tf`:**

```hcl
output "vpc_id" {
  description = "VPC ID"
  value       = aws_vpc.this.id
}

output "subnet_id" {
  description = "Public subnet ID"
  value       = aws_subnet.public.id
}
```

> **WHY `this` as resource label?** Convention inside reusable modules: the resource name (`this`) is generic because the `module` block label (`module "vpc"`) already provides context. `module.vpc.vpc_id` reads cleanly.

### The Problem

SG needs the VPC ID (created in another module). EC2 needs subnet + SG IDs plus an AMI. How do modules share values without hardcoding?

Answer: root wires outputs → inputs. Each module declares what it needs.

### Build It Now

**`modules/sg/variables.tf`:**

```hcl
variable "vpc_id" {
  description = "VPC to attach the SG to"
  type        = string
}

variable "allowed_ssh_cidr" {
  description = "Your IP in CIDR form, e.g. 1.2.3.4/32"
  type        = string
}

variable "name_prefix" {
  type    = string
  default = "day27-lab"
}
```

**`modules/sg/main.tf`:**

```hcl
resource "aws_security_group" "this" {
  name        = "${var.name_prefix}-sg"
  description = "Day 27 lab SG"
  vpc_id      = var.vpc_id

  ingress {
    description = "SSH from operator only"
    from_port   = 22
    to_port     = 22
    protocol    = "tcp"
    cidr_blocks = [var.allowed_ssh_cidr]
  }

  ingress {
    description = "HTTP world-open (lab)"
    from_port   = 80
    to_port     = 80
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]
  }

  egress {
    from_port   = 0
    to_port     = 0
    protocol    = "-1"
    cidr_blocks = ["0.0.0.0/0"]
  }

  tags = {
    Name = "${var.name_prefix}-sg"
  }
}
```

## Part 6: Break-It Lab — Hardcoded AMI That Doesn't Exist (45 min)

**INTENTIONAL FAILURE — scratch lab, $0 risk.**

### Prove WORKING First? (Gate — modified)

Normally the gate is a green `apply`. Today the gate is a green `plan` + `validate`, because the breakage is **baked into the first apply**. Confirm:

```powershell
terraform validate
# Success! The configuration is valid.
```

Gate passed ✅ — modules wire correctly. Now watch the AMI kill the apply.

### What We're Breaking: Regional AMI Hardcode

AMIs are per-region objects. Teams hardcode an AMI copied from a blog (`us-east-1` Ubuntu) or a stale wiki, then apply in `eu-north-1`. AWS cannot find it.

### Steps to Break It

```powershell
terraform apply -var="allowed_ssh_cidr=$(curl -s ifconfig.me)/32" -auto-approve
```

### Symptoms to Observe

```text
╷
│ Error: creating EC2 Instance: InvalidAMIID.NotFound: The image id
│ '[ami-0deadbeef12345678]' does not exist
│   status code: 400, request id: xxxxx
│
│   with module.ec2.aws_instance.this,
│   on modules/ec2/main.tf line 1, in resource "aws_instance" "this":
│    1: resource "aws_instance" "this" {
│
╵
```

Note three things:

1. The error prefix `module.ec2` tells you exactly which module failed.
2. Nothing was created — VPC/SG planned but apply aborted on the EC2 step.
3. Re-running apply without fixing the AMI fails identically. The AMI is the sole blocker.

### YOUR TURN: Diagnose (answer before reading the fix)

1. **Why is hardcoding `ami-0…` fragile even if it worked today?** (AMIs rotate on patch Tuesdays; old IDs get deregistered; each region has different IDs for the same Ubuntu release.)
2. **What AWS service always knows the current Ubuntu AMI ID per region without you looking it up?** (SSM Parameter Store — Canonical publishes `/aws/service/canonical/ubuntu/...` parameters.)
3. **Should the SSM lookup live in the root or inside `modules/ec2`?** (Inside `ec2` — the module owns its AMI resolution; root just passes `subnet_id`/`sg_id`.)

### The Fix: `aws_ssm` Data Source Inside the EC2 Module

Replace the hardcoded variable with a live lookup. Edit **`modules/ec2/main.tf`** to:

```hcl
data "aws_ssm_parameter" "ubuntu" {
  name = "/aws/service/canonical/ubuntu/server/22.04/stable/current/amd64/hvm/ebs-gp2/ami-id"
}

resource "aws_instance" "this" {
  ami                    = data.aws_ssm_parameter.ubuntu.value
  instance_type          = var.instance_type
  subnet_id              = var.subnet_id
  vpc_security_group_ids = [var.sg_id]

  tags = {
    Name = "${var.name_prefix}-ec2"
  }
}
```

And remove the now-unused `ami_id` variable from **`modules/ec2/variables.tf`** (delete the whole block), and drop `ami_id` from the root `module "ec2"` block:

```hcl
module "ec2" {
  source        = "./modules/ec2"
  subnet_id     = module.vpc.subnet_id
  sg_id         = module.sg.sg_id
  instance_type = "t3.micro"
  name_prefix   = "day27-lab"
}
```

Verify:

```powershell
terraform init
terraform validate
terraform apply -var="allowed_ssh_cidr=$(curl -s ifconfig.me)/32" -auto-approve
```

Expected: `Apply complete! Resources: 5 added.` Then:


## Part 7: Troubleshooting Challenge (30 min)

### Real-World Incident Scenario

> A teammate clones your Day 27 repo, runs `terraform init`, then `terraform plan`, and gets:
> `Error: Module not installed — Module "sg" refers to ./modules/sg but it is not installed.`
> They insist: *"I ran init! Why is the module missing?"*

### Investigation Path (9-Step Chain)

1. **SYMPTOM:** `plan` fails with `Module not installed` for `module.sg`.
2. **OBSERVATION:** Error is about module installation, not AWS. Happens before any cloud call.
3. **HYPOTHESIS:** A: `source` path typo. B: `init` was run in the wrong directory (e.g. inside `modules/sg`). C: folder renamed but `main.tf` not updated.
4. **CHECK:** `pwd` → are you in `day-27-tf/` (root)? `ls modules/` → does `sg/` exist with that exact lowercase spelling?
5. **EVIDENCE:** Teammate ran `terraform init` inside `modules/ec2/` while following the SSM fix. That initialized the child, not the root — root's `.terraform/modules` manifest was never written.
6. **ROOT CAUSE:** `terraform init` installs modules **relative to the directory you run it in**. Running it in a child does not install siblings.
7. **FIX:** `cd` back to root (`day-27-tf/`) and re-run `terraform init`. Always `init`/`plan`/`apply` from root.
8. **VERIFY:** `terraform plan -var="allowed_ssh_cidr=..."` proceeds past module installation.
9. **PREVENTION:** Never `cd` into `modules/*` to run Terraform. Treat children as libraries — read-only from the terminal. CI `working-directory` must point at root.

Second drill (5 min, on your own): in root `outputs.tf`, type `module.vpc.subnet` (missing `_id`) and run `validate`. Observe `Unsupported attribute` — the fix is using exactly the names declared in the child's `outputs.tf`.

## Part 9: Root-Cause Discussion (15 min)

### The Question

*Why does the SSM data source fix the AMI problem permanently, while pasting today's correct AMI ID would only fix it temporarily?*

### The Technical Answer

1. **Static ID = snapshot.** An AMI ID names one exact image build in one region. Canonical deregisters old builds; each region mints different IDs. Your pasted ID rots.
2. **SSM parameter = pointer.** `/aws/service/canonical/ubuntu/server/22.04/stable/current/...` is a pointer Canonical updates on every release. The *name* is stable across regions and time; the *value* (the ID) is resolved fresh on every `plan`/`apply` in whatever region your provider points at.
3. **Data source = read during plan.** `data "aws_ssm_parameter"` executes an SSM `GetParameter` API call at plan time — no resource is created. If the parameter name is wrong, you fail fast at plan (cheap) instead of mid-apply (after VPC/SG already created).
4. **Module ownership.** Because the lookup lives inside `modules/ec2`, every future caller (`dev`, `prod` workspaces Day 28, capstone Day 51) gets correct-AMIs for free. Hardcoding in root would force every caller to repeat the lookup.

## Part 11: Job Readiness (10 min)

### Interview Question

*"Why split Terraform into modules instead of one big main.tf? And how do you avoid hardcoded AMIs breaking deploys in a new region?"*

### Strong Answer

"Flat files don't scale — a 500-line `main.tf` has a huge blast radius and can't be reused across envs. I split VPC, SG, and EC2 into local modules with explicit inputs and outputs, so the root is three `module` blocks and `module.vpc.vpc_id`-style wiring. Each module is independently understandable and reusable — Day 28 workspaces will call the same VPC module twice.

For AMIs, IDs are regional snapshots that get deregistered, so hardcoding breaks on region change or image rotation with `InvalidAMIID.NotFound` — which I reproduced in the lab. The fix is a data source: `aws_ssm_parameter` for Canonical's `/aws/service/canonical/ubuntu/...` path inside the EC2 module, resolved fresh per region at plan time. That way the module always launches the current Ubuntu 22.04 without callers passing an ID."

## Part 12: Recap (10 min)

### Concept Summary Table

| Component | Where | Role |
|---|---|---|
| Root module | `day-27-tf/*.tf` | Provider, variables, three `module` blocks, re-exports |
| `vpc` module | `modules/vpc/` | VPC + subnet + IGW + route; outputs `vpc_id`, `subnet_id` |
| `sg` module | `modules/sg/` | SG bound to `var.vpc_id`; outputs `sg_id` |
| `ec2` module | `modules/ec2/` | SSM lookup + instance; outputs `instance_id`, `public_ip` |
| AMI resolution | `data.aws_ssm_parameter.ubuntu` | Region-correct Ubuntu ID at plan time |
| Wiring syntax | `module.<label>.<output>` | Only cross-module communication channel |

### The Pattern: Module Build Flow

1. **Shape inputs:** Declare `variables.tf` per child (no env-specific hardcodes).
2. **Build child:** Resources reference `var.*` only.
3. **Expose outputs:** `outputs.tf` per child for everything the root needs.
4. **Wire root:** `module` blocks with `source = "./modules/<name>"`, pass `module.*.*` values.
5. **`init` from root:** Installs all children at once.
6. **`validate` → `plan`:** Catches wiring errors cheaply (AMI not yet checked).
7. **`apply` → verify:** Catches cloud-side errors (AMI validated here).
8. **Data-source dynamic values:** SSM/AMI lookups inside the owning module, never hardcoded IDs in root.
