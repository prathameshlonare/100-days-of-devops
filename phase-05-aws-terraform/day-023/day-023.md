## Part 1: Why This Matters & The Core Mental Model (15 min)

In cloud infrastructure, "Application worked yesterday, getting 403 today" is one of the most common tickets a Cloud Support or Operations engineer handles.

Beginner engineers assume that if an IAM policy says `Allow`, the request will succeed. In AWS, this is only half the equation.

### The 3 Rules of AWS Policy Evaluation
Whenever a request hits an AWS resource in the same account:
1. **Default Deny:** If there is no `Allow` statement anywhere, the request is denied silently.
2. **Explicit Deny Beats Everything:** If a single matching policy statement has `"Effect": "Deny"`, the request is immediately rejected. It does not matter if you have 10 other `Allow` statements.
3. **The Same-Account Union:** To access a resource like S3, you need an `Allow` in the caller's IAM policy OR in the S3 Bucket Policy (assuming no explicit Deny).

```text
Incoming Request
       │
       ▼
Is there an EXPLICIT DENY? ──YES──► Access Denied (403)
       │ (No)
       ▼
Is there an EXPLICIT ALLOW? ──NO──► Access Denied (403, Default Deny)
       │ (Yes)
       ▼
Access Granted (200 OK)
```

### Feeder Role Relevance
- **Cloud Support Associate / L1 Cloud Engineer:** Customers frequently add bucket policies to enforce encryption or private paths, inadvertently locking out legitimate IAM users. Knowing that Deny overrides Allow solves these tickets in 2 minutes.

## Part 2: Hands-On Build — The Working Baseline (45 min)

We build a clean baseline: an S3 bucket with a private file and an IAM user who can successfully read it.

### Step 1: Create the S3 Bucket
1. Open the AWS Console in **`eu-north-1` (Stockholm)**.
2. Navigate to **S3** -> **Create bucket**.
3. Bucket name: `day23-lab-dish-assets-<your-account-id>` (must be globally unique).
4. Keep **Block all public access** checked (ON).
5. Click **Create bucket**.

### Step 2: Upload Test Object
1. Create a local text file named `menu.json` with the content:
   ```json
   {"dish": "misal pav", "price": 80}
   ```
2. Open your bucket in the S3 console, click **Upload**, select `menu.json`, and upload it.

### Step 3: Create the Test IAM User
1. Navigate to **IAM** -> **Users** -> **Create user**.
2. User name: `day23-lab-app`.
3. Select **Provide user access to the AWS Management Console**.
4. Set a custom password (e.g. `DevOpsLab2026!`). Uncheck "Users must create a new password at next sign-in".
5. Click **Next** -> On the permissions screen, select **Attach policies directly** -> click **Next** (attach nothing yet).
6. Click **Create user**. Note your Account ID.

### Step 4: Attach Scoped IAM Read Policy
1. Click on the newly created user `day23-lab-app`.
2. Under **Permissions policies**, click **Add permissions** -> **Create inline policy**.
3. Select the **JSON** tab and paste:
   ```json
   {
     "Version": "2012-10-17",
     "Statement": [
       {
         "Sid": "AllowMenuRead",
         "Effect": "Allow",
         "Action": "s3:GetObject",
         "Resource": "arn:aws:s3:::day23-lab-dish-assets-<your-account-id>/menu.json"
       }
     ]
   }
   ```
   *(Make sure to replace `<your-account-id>` with your bucket name).*
4. Policy name: `day23-lab-app-read` -> **Create policy**.

### Step 5: Verify Working Baseline
1. Open an **Incognito / Private browser window**.
2. Go to `https://<your-account-id>.signin.aws.amazon.com/console`.
3. Sign in as `day23-lab-app`.
4. Navigate to **S3** -> open your bucket -> click `menu.json`.
5. Click **Download** or **Open**.
6. **Result:** The file downloads and displays `{"dish": "misal pav", "price": 80}`.
7. **Gate Passed:** The IAM Allow works as expected.

## Part 3: Break-It Lab — The 403 Access Denied Conflict (45 min)

Now we intentionally inject a conflicting Bucket Policy to prove that an explicit Deny overrides the user's IAM Allow.

### Step 1: Inject an Explicit Deny Bucket Policy
In your **Admin window**:
1. Navigate to **S3** -> select `day23-lab-dish-assets-<your-account-id>`.
2. Click the **Permissions** tab -> scroll down to **Bucket policy** -> click **Edit**.
3. Paste the following policy, which explicitly denies access to all download requests:
   ```json
   {
     "Version": "2012-10-17",
     "Statement": [
       {
         "Sid": "BlockAllDownloads",
         "Effect": "Deny",
         "Principal": "*",
         "Action": "s3:GetObject",
         "Resource": "arn:aws:s3:::day23-lab-dish-assets-<your-account-id>/*"
       }
     ]
   }
   ```
4. Click **Save changes**.

### Step 2: Observe the Symptoms
Switch back to your **Incognito window** (signed in as `day23-lab-app`):
1. Refresh the page showing `menu.json`.
2. Click **Download** or **Open**.
3. **Observed Symptom:**
   ```text
   <Error>
     <Code>AccessDenied</Code>
     <Message>Access Denied</Message>
   </Error>
   HTTP 403 Forbidden
   ```
4. Check the IAM console in your Admin window: The user `day23-lab-app` still clearly has `Effect: Allow` for `s3:GetObject`.

### Step 3: Diagnostic Triage
Why is this failing if IAM says Allow?
- Check 1: Did the user lose their IAM policy? (No, `day23-lab-app-read` is still attached).
- Check 2: Does an S3 Bucket Policy exist? (Yes, on the bucket Permissions tab).
- Check 3: What does the Bucket Policy declare? (`"Effect": "Deny"`).
- **Root Cause:** In AWS evaluation logic, **Explicit Deny > Explicit Allow**. Because the bucket policy matches `s3:GetObject` with `Deny`, the IAM Allow is completely negated.

### Step 4: Apply the Fix
In your **Admin window**:
1. Go to the S3 bucket's **Permissions** tab.
2. Click **Bucket policy** -> **Delete**. Confirm deletion.
3. Switch to the **Incognito window**, refresh, and click **Download**.
4. **Verification:** The file downloads successfully again.

## Part 4: Troubleshooting Record (15 min)

```markdown
## Troubleshooting Record — Day 23

**Problem:** IAM user `day23-lab-app` receives HTTP 403 Access Denied when downloading an S3 object despite having an active IAM Allow policy.
**Symptoms:** Browser returns `<Code>AccessDenied</Code>` with HTTP 403; IAM policy shows `s3:GetObject` is Allowed.
**Environment:** AWS `eu-north-1` (Stockholm), S3 Bucket + IAM User.
**What I checked:**
1. Verified IAM inline policy `day23-lab-app-read` had valid JSON syntax and correct object ARN.
2. Checked S3 Bucket Permissions tab for resource-based policies.
3. Identified an explicit `"Effect": "Deny"` statement targeting `"Action": "s3:GetObject"`.
**Commands / Tools used:** AWS Console, S3 Object Download, Incognito session testing.
**Evidence:** S3 Bucket policy contained statement `"Sid": "BlockAllDownloads"`, overriding IAM policy.
**Hypothesis:** The explicit Deny in the resource policy is overriding the identity-based Allow.
**Root Cause:** AWS policy evaluation hierarchy enforces that any matching Explicit Deny overrides all Explicit Allows.
**Fix:** Removed the offending explicit Deny statement from the bucket policy.
**Verification:** User successfully downloaded `menu.json` returning HTTP 200 and expected payload.
**Prevention:** Always verify resource policies, SCPs, and permission boundaries before modifying IAM user permissions during 403 triage.
**What I learned:** Never stop at checking IAM policies when debugging 403 errors; always check the resource policy on S3.
```

## Part 5: Job Readiness & Interview Defense (15 min)

### Feeder Role Connection
- **Role:** Cloud Support Associate (AWS / Consultancies)
- **Ticket Scenario:** *"Our app server is receiving 403 Access Denied when trying to fetch configuration files from an S3 bucket. Our team lead verified the EC2 IAM role has AmazonS3FullAccess. What is happening?"*

### Top 1% Interview Answer
When an interviewer asks: *"An IAM role has Full S3 permissions, but still gets 403 Access Denied on a bucket. What are the first 3 things you check?"*

Give this structured response:
1. **S3 Bucket Policy:** Check if the bucket has a resource policy with an **Explicit Deny** (e.g. denying requests not originating from a specific VPC endpoint or IP range). Explicit Deny overrides the IAM role's FullAccess.
2. **KMS Key Policy (if encrypted):** If the S3 object is encrypted with AWS KMS (SSE-KMS), the caller needs permissions on both the S3 bucket AND the KMS key (`kms:Decrypt`). If the KMS key policy doesn't allow the role, S3 returns 403.
3. **Service Control Policies (SCPs) / Permissions Boundaries:** Check if the AWS Account has an AWS Organizations SCP or an IAM Permissions Boundary attached that limits S3 actions.
