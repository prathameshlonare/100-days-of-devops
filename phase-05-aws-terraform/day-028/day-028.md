## Part 1: Why This Matters & The Core Mental Model (15 min)

In production environments, two common challenges arise:
1. **Managing Multiple Environments (`dev` vs `prod`):** How do you avoid copy-pasting 300 lines of Terraform into multiple folders?
2. **Infrastructure Drift (Click-Ops):** What happens when an on-call engineer logs into the AWS Console at 2 AM to fix an incident, manually edits a Security Group rule, and forgets to commit it to Git?

### What is Cloud Drift?
Cloud drift occurs when the physical infrastructure in AWS diverges from the declaration in your Terraform code.

```text
Desired State (.tf code):      Ingress: Port 80, Port 22
                                           ▲
                                           │ (MISMATCH = DRIFT!)
                                           ▼
Physical State (AWS Console):  Ingress: Port 80, Port 22, Port 8080 (Manual Edit)
```

If an engineer adds an unauthorized port in the console:
- Your Git repo doesn't know about it.
- Your security audit cannot trace who opened it.
- The next time someone runs `terraform apply`, Terraform detects the drift and removes it to restore the code's declared state.

### What are Terraform Workspaces?
A Terraform workspace allows a single directory of `.tf` code to maintain **independent state files**.
- In the `default` workspace, state is stored in `terraform.tfstate`.
- In a custom workspace like `dev`, state is stored in `terraform.tfstate.d/dev/terraform.tfstate`.
- Switching workspaces changes the active state file without modifying your code.

### Feeder Role Relevance
- **Cloud Support Engineer / Junior Cloud Ops:** A frequent ticket reads: *"Someone added a temporary firewall rule in the console, and our scheduled deployment wiped it out. Why did Terraform delete our change?"* Knowing how Terraform enforces declarative state solves this ticket immediately.

## Part 2: Hands-On Build — Workspaces & Baseline Infrastructure (45 min)

We write a clean network configuration and deploy it inside a dedicated `dev` workspace.

### Step 1: Configure Infrastructure Code
Create a working directory `day-028-tf/` and add `provider.tf`:

```hcl
terraform {
  required_version = ">= 1.5.0"
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }
}

provider "aws" {
  region = "eu-north-1"
}
```

Create `main.tf`:
```hcl
resource "aws_vpc" "lab_vpc" {
  cidr_block           = "10.28.0.0/16"
  enable_dns_support   = true
  enable_dns_hostnames = true

  tags = {
    Name        = "day28-lab-vpc"
    Environment = terraform.workspace
  }
}

resource "aws_security_group" "web_sg" {
  name        = "day28-lab-sg-${terraform.workspace}"
  description = "Managed web security group"
  vpc_id      = aws_vpc.lab_vpc.id

  ingress {
    description = "Allow HTTP"
    from_port   = 80
    to_port     = 80
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]
  }

  ingress {
    description = "Allow SSH"
    from_port   = 22
    to_port     = 22
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]
  }

  egress {
    description = "Allow all outbound"
    from_port   = 0
    to_port     = 0
    protocol    = "-1"
    cidr_blocks = ["0.0.0.0/0"]
  }

  tags = {
    Name        = "day28-lab-sg-${terraform.workspace}"
    Environment = terraform.workspace
  }
}
```

Notice `${terraform.workspace}`: Terraform dynamically names resources based on the active workspace.

### Step 2: Initialize & Manage Workspaces
Run:
```bash
terraform init
```

List existing workspaces:
```bash
terraform workspace list
```
Output shows `* default`. Every Terraform folder starts with one built-in `default` workspace.

Create and switch to your `dev` workspace:
```bash
terraform workspace new dev
```
Terraform creates the workspace and automatically switches your terminal context into `dev`.

### Step 3: Deploy Baseline
Deploy the baseline infrastructure:
```bash
terraform apply -auto-approve
```
**Verification:** In AWS Console (`eu-north-1`), open **Security Groups**. You will see `day28-lab-sg-dev` with exactly 2 inbound rules (Port 80 and Port 22).

## Part 3: Break-It Lab — Out-of-Band Cloud Drift Drill (45 min)

Now we simulate an unauthorized manual hotfix directly in the AWS Console.

### Step 1: Inject Out-of-Band Drift in AWS Console
1. Open your browser and navigate to **AWS EC2 Console** in **`eu-north-1` (Stockholm)**.
2. In the left navigation, click **Security Groups**.
3. Select **`day28-lab-sg-dev`**.
4. Click the **Inbound rules** tab -> click **Edit inbound rules**.
5. Click **Add rule**:
   - **Type:** Custom TCP
   - **Port range:** `8080` (simulate an unauthorized test port)
   - **Source:** Anywhere-IPv4 (`0.0.0.0/0`)
   - **Description:** `Emergency hotfix via console (UNTRACKED DRIFT)`
6. Click **Save rules**.

You have now created physical cloud drift. The AWS Console has 3 rules (22, 80, 8080), but your source code in `main.tf` only declares 2 rules (22, 80).

### Step 2: Detect Drift with `terraform plan`
Back in your terminal (without modifying any code!), run:
```bash
terraform plan
```

### Step 3: Observe the Symptoms
Look at the terminal output:
```text
aws_security_group.web_sg: Refreshing state... [id=sg-0xxxxxxxxxxxx]

Terraform will perform the following actions:

  # aws_security_group.web_sg will be updated in-place
  ~ resource "aws_security_group" "web_sg" {
        id   = "sg-0xxxxxxxxxxxx"
        name = "day28-lab-sg-dev"

      ~ ingress {
          - cidr_blocks = ["0.0.0.0/0"]
          - description = "Emergency hotfix via console (UNTRACKED DRIFT)"
          - from_port   = 8080
          - protocol    = "tcp"
          - to_port     = 8080
        }
        # (rules for port 22 and 80 remain unchanged)
    }

Plan: 0 to add, 1 to change, 0 to destroy.
```

**What happened under the hood?**
During the **Refresh** phase, Terraform queried the AWS API. It compared reality with your `main.tf`. Seeing that Port 8080 is not in your code, Terraform calculated that reality must be altered to match the desired state by removing the unauthorized rule.

### Step 4: Reconcile Drift Back to Code
Execute the reconciliation:
```bash
terraform apply -auto-approve
```
**Verification:** Refresh the AWS Console. The unauthorized Port 8080 rule has vanished. The cloud infrastructure is strictly reconciled back to the declared source code.

### Feeder Role Connection

### Top 1% Fresher Interview Q&A (2026 Standards)

#### Q1: "What is infrastructure drift, and how does Terraform detect it?"
- **Answer:** *"Infrastructure drift occurs when physical cloud resources are modified outside of Terraform (such as through manual AWS Console clicks, AWS CLI commands, or automated scaling). Terraform detects drift during the refresh phase of `terraform plan` or `terraform apply` by querying the AWS API, comparing live cloud state against the recorded state file and code, and calculating the exact diff needed to bring reality back into alignment."*

#### Q2: "How can a team automatically detect drift before a deployment?"
- **Answer:** *"In 2026 CI/CD pipelines, teams schedule nightly automated jobs running `terraform plan -detailed-exitcode`. If there is zero drift, the command exits with code `0`. If drift is detected (a diff exists), it exits with code `2`, triggering an alert in Slack or Microsoft Teams so engineers can investigate unauthorized changes before they cause production incidents."*

#### Q3: "What is the difference between Terraform Workspaces and Directory-based isolation?"
- **Answer:** *"Terraform Workspaces use one codebase and switch state files automatically using `terraform.workspace`. They are ideal for testing identical feature branches or identical dev/stage setups. However, for true production isolation, industry best practice prefers directory-based isolation (`environments/dev/` and `environments/prod/`) with separate state backends and different IAM access boundaries so a developer cannot accidentally destroy production by forgetting to switch workspaces."*
