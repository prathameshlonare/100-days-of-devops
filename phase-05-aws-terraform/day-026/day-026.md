## Part 1: Why This Matters & The Core Mental Model (15 min)

By default, Terraform saves state locally in `terraform.tfstate`. In a solo lab, this works. In a team or production environment, local state creates four fatal problems:

### The 4 Fatal Flaws of Local State
1. **Concurrency Race Conditions:** If Developer A and Developer B (or a CI/CD pipeline) run `terraform apply` at the same second, both read the old state, make conflicting modifications, and overwrite each other. State becomes corrupt.
2. **Git Merge Conflicts:** State is a dynamic JSON dependency graph with timestamps and serial numbers. Merging state conflicts in Git is nearly impossible without corrupting resources.
3. **Plaintext Secret Leaks:** Terraform state records all resource attributes in plain text (including database passwords, tokens, and private keys). Committing `.tfstate` to Git exposes credentials.
4. **Local Desynchronization:** If Developer A deploys a database from their laptop, Developer B's laptop has no record of it. When B runs `plan`, Terraform tries to recreate it.

### The Solution: S3 + DynamoDB Architecture

```text
Developer Laptop / CI Pipeline
       │
       ├─► 1. Acquires Lock ─────► DynamoDB (day26-tfstate-locks)
       │                              │ (Prevents concurrent applies)
       ├─► 2. Reads/Writes State ─► S3 Bucket (day26-tfstate-bucket)
       │                              │ (Versioned + Encrypted at rest)
       └─► 3. Releases Lock ─────► DynamoDB Table
```

- **Amazon S3** provides a shared, highly durable single source of truth. Versioning allows rolling back if state is ever corrupted.
- **Amazon DynamoDB** acts as a distributed mutex (lock). Before modifying state, Terraform writes an item with `LockID`. If another process attempts to run `apply`, DynamoDB rejects it, preventing simultaneous updates.

## Part 2: Hands-On Build — S3 Backend & DynamoDB Locking (45 min)

We bootstrap the state storage and configure Terraform to use it.

### Step 1: Bootstrap S3 Bucket & DynamoDB Table (AWS Console)
Terraform cannot store state in S3 until the bucket exists (the "chicken-and-egg" problem). We bootstrap the storage once in **`eu-north-1` (Stockholm)**:

1. **Create S3 Bucket:**
   - Name: `day26-tfstate-bucket-<your-account-id>` (must be globally unique).
   - Region: `eu-north-1` (Stockholm).
   - **Block all public access:** Checked (ON). State must never be public!
   - **Bucket Versioning:** Enable. (Allows rollback if state ever corrupts).
   - **Default Encryption:** Amazon S3 managed keys (SSE-S3).
   - Click **Create bucket**.

2. **Create DynamoDB Lock Table:**
   - Table name: `day26-tfstate-locks`.
   - Partition key: `LockID` *(Case-sensitive! Exactly capital `L`, capital `ID`, type `String`)*.
   - Table settings: Select **Customize settings** -> Capacity mode: **On-demand** (ensures $0 cost when idle).
   - Click **Create table**.

### Step 2: Configure Terraform Remote Backend (`backend.tf`)
In your `day-026-tf/` folder, create `backend.tf`:

```hcl
terraform {
  backend "s3" {
    bucket         = "day26-tfstate-bucket-<your-account-id>"
    key            = "day26/scratch/terraform.tfstate"
    region         = "eu-north-1"
    dynamodb_table = "day26-tfstate-locks"
    encrypt        = true
  }
}
```

## Part 3: Break-It Lab — State Locking & Deadlock Recovery (45 min)

We examine how DynamoDB locking prevents simultaneous modifications and how to recover from a stuck lock.

### Step 1: How DynamoDB State Locking Works Under the Hood
Whenever `terraform plan` or `terraform apply` runs:
1. Terraform creates an item in `day26-tfstate-locks` where `LockID = "day26-tfstate-bucket-.../day26/scratch/terraform.tfstate-md5"`.
2. It writes attributes: `Info` (JSON containing who, which machine, and timestamp).
3. If another engineer runs `apply` at the same time, DynamoDB's conditional write rejects it with `ConditionalCheckFailedException`.

### Step 2: What a State Lock Collision Looks Like
When two applies collide (or a previous CI/CD run crashed before releasing the lock), Terraform halts with this error:

```text
Error: Error acquiring the state lock

Error message: ConditionalCheckFailedException: The conditional request failed
Lock Info:
  ID:        b8a3e7a1-8d24-4f32-9c1a-xxxxxxxxxxxx
  Path:      day26-tfstate-bucket-.../terraform.tfstate
  Operation: OperationTypeApply
  Who:       runner@github-actions-worker-01
  Version:   1.5.7
  Created:   2026-09-29 14:30:00.000000000 +0000 UTC
  Info:      
```

### Step 3: How to Safely Resolve a Deadlock
If a process is legitimately running, **you must wait**. Never break a lock while a teammate is deploying.

However, if an automated runner crashed midway through execution (or network dropped), the lock remains stuck indefinitely. Every subsequent run will fail.

To resolve a deadlocked state:
1. Verify no teammate or runner is actively writing.
2. Note the **Lock ID** from the error output (e.g. `b8a3e7a1-8d24-4f32-9c1a-xxxxxxxxxxxx`).
3. Run the safe unlock command:
   ```bash
   terraform force-unlock <LOCK-ID>
   ```
4. Terraform removes the row from DynamoDB and releases the lock for future runs.

## Part 4: Troubleshooting Record (15 min)

```markdown
## Troubleshooting Record — Day 26

**Problem:** Pipeline or developer unable to run `terraform apply` due to `Error acquiring the state lock`.
**Symptoms:** Terminal returns `ConditionalCheckFailedException` displaying Lock Info with ID, Who, and Created timestamp.
**Environment:** AWS `eu-north-1`, S3 State Backend + DynamoDB Lock Table.
**What I checked:**
1. Inspected error output for Lock Info to identify who holds the lock and timestamp.
2. Verified whether the active process (e.g. GitHub Actions runner) was still running or had crashed.
3. Checked DynamoDB table `day26-tfstate-locks` items in AWS Console.
**Commands used:** `terraform plan`, `aws dynamodb scan --table-name day26-tfstate-locks`, `terraform force-unlock <ID>`.
**Evidence:** Lock row existed in DynamoDB with a timestamp from an aborted run 2 hours prior.
**Hypothesis:** An interrupted deployment exited ungracefully without executing the lock release cleanup phase.
**Root Cause:** Orphaned lock entry in DynamoDB preventing new state operations.
**Fix:** Executed `terraform force-unlock <LOCK-ID>` after confirming no active deployment was occurring.
**Verification:** Re-ran `terraform plan`; state lock acquired and released successfully with zero errors.
**Prevention:** Configure CI/CD runners with appropriate timeouts and post-action cleanup hooks; never terminate `terraform apply` processes with `kill -9`.
**What I learned:** DynamoDB locking acts as a safety guard. You should never force-unlock blindly without verifying the process that created the lock has truly terminated.
```

### Top 1% Fresher Interview Q&A (2026 Standards)

#### Q1: "Why do we use an S3 bucket with DynamoDB as a backend in Terraform?"
- **Answer:** *"S3 provides a centralized, secure single source of truth for the state file with versioning (enabling disaster recovery) and server-side encryption. DynamoDB provides distributed locking using its `LockID` partition key, ensuring that two team members or CI/CD pipelines cannot modify the same infrastructure simultaneously, which would cause state corruption."*

#### Q2: "Why must the DynamoDB partition key be specifically named `LockID`?"
- **Answer:** *"Terraform's built-in S3 backend driver is hardcoded to look for a partition key named exactly `LockID` (type String). If you name it anything else (e.g. `Id` or `lock_id`), DynamoDB will fail to store lock entries and Terraform throws an initialization error."*

#### Q3: "What happens if someone accidentally corrupts the remote `terraform.tfstate` in S3?"
- **Answer:** *"Because we enabled S3 Bucket Versioning when setting up the backend, every modification saves a new version of the JSON state file. If a corrupted state is uploaded, we can navigate to the S3 bucket, view historical versions, and restore the previous known-good state version without losing or destroying physical AWS resources."*
