## Part 1: Why This Matters & The Core Mental Model (15 min)

Beginners hardcode everything inside their `.tf` files: hardcoded AMI IDs (`ami-01234...`), hardcoded regions (`eu-north-1`), and hardcoded instance sizes (`t3.micro`).

### Why Hardcoding Fails in Production
1. **AMI IDs are Region-Locked:** An Amazon Linux AMI ID in Stockholm (`eu-north-1`) does not exist in Mumbai (`ap-south-1`) or Virginia (`us-east-1`). Running hardcoded code in another region crashes instantly.
2. **No Environment Reusability:** You cannot reuse the same code for `dev` (t3.micro) and `prod` (t3.large) without duplicating files.
3. **No Automation Handoff:** After creating an EC2 instance, automated scripts or CI/CD pipelines need the server's public IP address. Without Terraform `outputs`, external systems must guess or manually query AWS APIs.

### The 3-File Standard
Professional DevOps teams organize Terraform into three core files:

```text
┌─────────────────┐       ┌──────────────────────┐       ┌──────────────────┐
│  variables.tf   │ ───►  │       main.tf        │ ───►  │    outputs.tf    │
│ (Input Schema)  │       │   (Resource Logic)   │       │ (Exported State) │
└─────────────────┘       └──────────────────────┘       └──────────────────┘
         ▲
         │ (Overrides)
┌─────────────────┐
│terraform.tfvars │
│(Concrete Values)│
└─────────────────┘
```

### Variable Precedence (Lowest to Highest)
When the same variable is passed from multiple places, Terraform resolves it in this strict order:
1. `default` inside `variables.tf` (lowest priority)
2. Environment variable: `TF_VAR_variable_name`
3. `terraform.tfvars` file
4. `*.auto.tfvars` files
5. CLI flag: `-var="instance_type=t3.small"` (highest priority)

### Dynamic Data Sources (`data "aws_ami"`)
Instead of hardcoding an AMI string, we use a `data` block. A `data` block is **read-only**: it asks the AWS API: *"Find the most recent official Amazon Linux 2023 AMI owned by Amazon in this region"*. This makes your Terraform code 100% portable across all AWS regions worldwide.

## Part 2: Hands-On Build — Parameterized EC2 Web Server (45 min)

We build a complete, parameterized web server using the standard 3-file structure.

### Step 1: Declare Inputs (`variables.tf`)
```hcl
variable "aws_region" {
  description = "AWS region for all provisioned resources"
  type        = string
  default     = "eu-north-1"
}

variable "vpc_cidr" {
  description = "CIDR block for the lab VPC"
  type        = string
  default     = "10.25.0.0/16"
}

variable "public_subnet_cidr" {
  description = "CIDR block for the public subnet"
  type        = string
  default     = "10.25.1.0/24"
}

variable "instance_type" {
  description = "EC2 instance type"
  type        = string
  default     = "t3.micro"
}

variable "key_name" {
  description = "Name of existing EC2 Key Pair in eu-north-1"
  type        = string
}
```

### Step 2: Assign Environment Values (`terraform.tfvars`)
Create `terraform.tfvars` to supply your concrete values:
```hcl
aws_region    = "eu-north-1"
instance_type = "t3.micro"
key_name      = "devops key" # Use your existing key pair name
```

### Step 3: Write Infrastructure Logic (`main.tf`)
`main.tf` defines the network, the dynamic AMI lookup, the security group, and the EC2 instance:

```hcl
resource "aws_vpc" "lab_vpc" {
  cidr_block           = var.vpc_cidr
  enable_dns_support   = true
  enable_dns_hostnames = true

  tags = {
    Name = "day25-lab-vpc"
  }
}

resource "aws_subnet" "public_sub" {
  vpc_id                  = aws_vpc.lab_vpc.id
  cidr_block              = var.public_subnet_cidr
  availability_zone       = "${var.aws_region}a"
  map_public_ip_on_launch = true

  tags = {
    Name = "day25-lab-public-sub"
  }
}

resource "aws_internet_gateway" "lab_igw" {
  vpc_id = aws_vpc.lab_vpc.id

  tags = {
    Name = "day25-lab-igw"
  }
}

resource "aws_route_table" "public_rt" {
  vpc_id = aws_vpc.lab_vpc.id

  route {
    cidr_block = "0.0.0.0/0"
    gateway_id = aws_internet_gateway.lab_igw.id
  }

  tags = {
    Name = "day25-lab-rt-public"
  }
}

resource "aws_route_table_association" "public_assoc" {
  subnet_id      = aws_subnet.public_sub.id
  route_table_id = aws_route_table.public_rt.id
}

resource "aws_security_group" "web_sg" {
  name        = "day25-lab-ec2-sg"
  description = "Allow inbound SSH and HTTP traffic"
  vpc_id      = aws_vpc.lab_vpc.id

  ingress {
    description = "SSH"
    from_port   = 22
    to_port     = 22
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]
  }

  ingress {
    description = "HTTP"
    from_port   = 80
    to_port     = 80
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]
  }

  egress {
    description = "Allow all outbound traffic"
    from_port   = 0
    to_port     = 0
    protocol    = "-1"
    cidr_blocks = ["0.0.0.0/0"]
  }

  tags = {
    Name = "day25-lab-ec2-sg"
  }
}

# Dynamic AMI Data Source
data "aws_ami" "amazon_linux_2023" {
  most_recent = true
  owners      = ["amazon"]

  filter {
    name   = "name"
    values = ["al2023-ami-2023.*-x86_64"]
  }

  filter {
    name   = "virtualization-type"
    values = ["hvm"]
  }
}

# EC2 Instance with User Data Web Server
resource "aws_instance" "web_server" {
  ami                         = data.aws_ami.amazon_linux_2023.id
  instance_type               = var.instance_type
  key_name                    = var.key_name
  subnet_id                   = aws_subnet.public_sub.id
  vpc_security_group_ids      = [aws_security_group.web_sg.id]
  associate_public_ip_address = true

  user_data = <<-EOF
              #!/bin/bash
              dnf update -y
              dnf install -y httpd
              systemctl start httpd
              systemctl enable httpd
              echo "<h1>Day 25: Terraform EC2 Provisioning Successful</h1><p>Instance: $(hostname -f)</p>" > /var/www/html/index.html
              EOF

  tags = {
    Name = "day25-lab-web-server"
  }
}
```

### Step 4: Export Computed Outputs (`outputs.tf`)
```hcl
output "instance_public_ip" {
  description = "Public IPv4 address of the EC2 instance"
  value       = aws_instance.web_server.public_ip
}

output "website_url" {
  description = "Direct HTTP URL to the test page"
  value       = "http://${aws_instance.web_server.public_ip}"
}
```

### Step 5: Format, Validate & Deploy
Run:
```bash
terraform fmt
terraform validate
terraform apply -auto-approve
```
**Verification:** Wait 60 seconds for Apache to initialize. Copy the `website_url` output and open it in your browser (or run `curl http://<public-ip>`).
You will see: `Day 25: Terraform EC2 Provisioning Successful`.

## Part 3: Break-It Lab — The Key Pair Mismatch (45 min)

Now we inject a common real-world error: passing a non-existent Key Pair name.

### Step 1: Inject Non-Existent Key Name
In `terraform.tfvars`, change `key_name` to an invalid string:
```hcl
key_name = "fake-key-does-not-exist"
```

### Step 2: Run `terraform plan`
Run:
```bash
terraform plan
```
**Observation:** `terraform plan` passes with zero errors! Why? Because Terraform validates that `key_name` is a valid string type. It does not check if the key exists inside AWS EC2.

### Step 3: Run `terraform apply`
Execute:
```bash
terraform apply -auto-approve
```
**Observed Symptom (Failure):**
```text
Error: creating EC2 Instance: InvalidKeyPair.NotFound: The key pair 'fake-key-does-not-exist' does not exist
	status code: 400, request id: xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx
```
**Root Cause:** The AWS EC2 API rejected the request during instance creation. Key pairs are regional objects, and AWS validates their existence server-side before booting compute.

### Step 4: Apply the Fix
Revert `key_name` in `terraform.tfvars` back to your valid key name and run `terraform apply -auto-approve`. The instance recovers successfully.

## Part 4: Troubleshooting Record (15 min)

```markdown
## Troubleshooting Record — Day 25

**Problem:** `terraform apply` fails with `InvalidKeyPair.NotFound` during EC2 instance provisioning.
**Symptoms:** `terraform plan` succeeds, but `apply` returns HTTP 400 error: `The key pair 'fake-key-does-not-exist' does not exist`.
**Environment:** AWS `eu-north-1` (Stockholm), Terraform CLI v1.5+, EC2 `t3.micro`.
**What I checked:**
1. Checked `variables.tf` — `key_name` variable type constraint was satisfied.
2. Verified `terraform.tfvars` value for `key_name`.
3. Queried AWS via CLI: `aws ec2 describe-key-pairs --region eu-north-1`.
**Commands used:** `terraform plan`, `terraform apply`, `aws ec2 describe-key-pairs`.
**Evidence:** AWS EC2 Console in `eu-north-1` contained `devops key`, but `terraform.tfvars` specified `fake-key-does-not-exist`.
**Hypothesis:** Key pairs are region-specific and validated by the AWS API only at apply time, not during local plan execution.
**Root Cause:** Mismatch between declared key pair variable and physical key pairs in `eu-north-1`.
**Fix:** Updated `key_name = "devops key"` in `terraform.tfvars` and re-applied.
**Verification:** EC2 instance entered `running` state with public IP assigned; HTTP web page returned 200 OK.
**Prevention:** In production, use standard naming conventions or look up existing key pairs using `data "aws_key_pair"`.
**What I learned:** Local validation and speculative plans do not verify external cloud dependencies (like key pair names or custom AMI IDs); only AWS APIs validate their physical existence.
```

### Top 1% Fresher Interview Q&A (2026 Standards)

#### Q1: "What is the difference between a `resource` block and a `data` block in Terraform?"
- **Answer:** *"A `resource` block manages lifecycle: it creates, updates, and deletes infrastructure components (like `aws_instance`). A `data` block is read-only: it queries existing infrastructure or cloud metadata (like `data "aws_ami"`) and exposes attributes to other resources without managing or deleting anything."*

#### Q2: "Why must you explicitly declare an `egress` rule in a Terraform Security Group?"
- **Answer:** *"When creating a Security Group in the AWS Console, AWS automatically attaches a default allow-all outbound rule (`0.0.0.0/0`). Terraform, by design, starts completely empty for security. If you omit the `egress` block in Terraform, the security group will block 100% of outbound traffic, preventing the EC2 instance from reaching package managers or internet APIs."*

#### Q3: "How do you pass sensitive variables (like DB passwords or API tokens) into Terraform without leaking them in Git?"
- **Answer:** *"First, mark the variable with `sensitive = true` in `variables.tf` so Terraform masks it from terminal output and logs. Second, never commit `terraform.tfvars` containing secrets to Git (add it to `.gitignore`). Third, pass sensitive values via environment variables prefixed with `TF_VAR_` (e.g. `TF_VAR_db_password`), or retrieve them directly from AWS Secrets Manager using a Terraform data source."*
