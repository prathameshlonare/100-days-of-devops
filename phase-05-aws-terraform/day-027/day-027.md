## Part 1: Why This Matters & The Core Mental Model (15 min)

Beginner projects almost always keep all infrastructure in one massive 500+ line `main.tf` file. 

### Why Monolithic Code Fails in Real Teams
1. **Uncontrolled Blast Radius:** If you make a typo in a subnet configuration, you risk modifying or destroying your entire database or cluster in the same file.
2. **Copy-Paste Drift:** If you need the exact same VPC for `dev` and `prod`, copy-pasting 80 lines into two places leads to drift when bug fixes are only applied to one.
3. **No Code Reusability:** Other teams cannot reuse your proven security group or network topology.

### The Software Analogy: Modules are Functions
Think of a Terraform module like a function in Python or JavaScript:

```text
┌────────────────────────────────────────────────────────┐
│ CHILD MODULE (Function Definition: modules/vpc/)      │
│ 1. Input Parameters  ──► variables.tf (e.g. vpc_cidr)  │
│ 2. Function Body     ──► main.tf (aws_vpc, subnets)   │
│ 3. Return Values     ──► outputs.tf (e.g. vpc_id)      │
└────────────────────────────────────────────────────────┘
                           ▲
                           │ Called by
┌──────────────────────────┴─────────────────────────────┐
│ ROOT MODULE (Caller: main.tf)                          │
│ module "vpc" {                                         │
│   source   = "./modules/vpc"                           │
│   vpc_cidr = "10.27.0.0/16"                            │
│ }                                                      │
└────────────────────────────────────────────────────────┘
```

### Module Wiring (Data Flow)
Resources inside a child module are **private** by default. If `modules/sg` needs the VPC ID created by `modules/vpc`, the root module acts as the conductor:

```text
module.vpc  ──(exports vpc_id via outputs.tf)──► Root main.tf
                                                       │
                                            (passes vpc_id as input)
                                                       ▼
                                                   module.sg
```

### The Cardinal Rule of Terraform Modules
**Child modules must NEVER configure `provider` or `backend` blocks.**
Child modules define *what* to build. The root module configures *where* and *how* to authenticate. Children automatically inherit the provider configured at the root.

## Part 2: Hands-On Build — The 3-Module Architecture (45 min)

We organize our code into a clean, professional directory structure:

```text
day-027-tf/
├── provider.tf
├── variables.tf
├── outputs.tf
├── main.tf                 <-- Root module (orchestrator)
└── modules/
    ├── vpc/                <-- Child: Network infrastructure
    │   ├── main.tf
    │   ├── variables.tf
    │   └── outputs.tf
    ├── sg/                 <-- Child: Security groups
    │   ├── main.tf
    │   ├── variables.tf
    │   └── outputs.tf
    └── ec2/                <-- Child: Compute & AMI lookup
        ├── main.tf
        ├── variables.tf
        └── outputs.tf
```

### Step 1: The VPC Child Module (`modules/vpc/`)
`modules/vpc/variables.tf`:
```hcl
variable "vpc_cidr" { type = string }
variable "subnet_cidr" { type = string }
variable "az" { type = string }
variable "name_prefix" { type = string }
```

`modules/vpc/main.tf`:
```hcl
resource "aws_vpc" "this" {
  cidr_block           = var.vpc_cidr
  enable_dns_support   = true
  enable_dns_hostnames = true
  tags                 = { Name = "${var.name_prefix}-vpc" }
}

resource "aws_subnet" "public" {
  vpc_id                  = aws_vpc.this.id
  cidr_block              = var.subnet_cidr
  availability_zone       = var.az
  map_public_ip_on_launch = true
  tags                    = { Name = "${var.name_prefix}-public-sub" }
}

resource "aws_internet_gateway" "this" {
  vpc_id = aws_vpc.this.id
  tags   = { Name = "${var.name_prefix}-igw" }
}

resource "aws_route_table" "public" {
  vpc_id = aws_vpc.this.id
  route {
    cidr_block = "0.0.0.0/0"
    gateway_id = aws_internet_gateway.this.id
  }
  tags = { Name = "${var.name_prefix}-rt" }
}

resource "aws_route_table_association" "public" {
  subnet_id      = aws_subnet.public.id
  route_table_id = aws_route_table.public.id
}
```

`modules/vpc/outputs.tf` *(Exporting return values)*:
```hcl
output "vpc_id" { value = aws_vpc.this.id }
output "subnet_id" { value = aws_subnet.public.id }
```

### Step 2: The Security Group Child Module (`modules/sg/`)
`modules/sg/variables.tf`:
```hcl
variable "vpc_id" { type = string }
variable "allowed_ssh_cidr" { type = string }
variable "name_prefix" { type = string }
```

`modules/sg/main.tf`:
```hcl
resource "aws_security_group" "this" {
  name        = "${var.name_prefix}-sg"
  description = "Allow inbound SSH and HTTP"
  vpc_id      = var.vpc_id

  ingress {
    from_port   = 22
    to_port     = 22
    protocol    = "tcp"
    cidr_blocks = [var.allowed_ssh_cidr]
  }

  ingress {
    from_port   = 80
    to_port     = 80
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]
  }

  egress {
    from_port   = 0
    to_port     = 0
    protocol    = "-1"
    cidr_blocks = ["0.0.0.0/0"]
  }

  tags = { Name = "${var.name_prefix}-sg" }
}
```

`modules/sg/outputs.tf`:
```hcl
output "sg_id" { value = aws_security_group.this.id }
```

### Step 3: The EC2 Child Module (`modules/ec2/`)
`modules/ec2/variables.tf`:
```hcl
variable "subnet_id" { type = string }
variable "sg_id" { type = string }
variable "instance_type" { type = string }
variable "name_prefix" { type = string }
```

`modules/ec2/main.tf`:
```hcl
data "aws_ami" "amazon_linux_2023" {
  most_recent = true
  owners      = ["amazon"]
  filter {
    name   = "name"
    values = ["al2023-ami-2023.*-x86_64"]
  }
}

resource "aws_instance" "this" {
  ami                         = data.aws_ami.amazon_linux_2023.id
  instance_type               = var.instance_type
  subnet_id                   = var.subnet_id
  vpc_security_group_ids      = [var.sg_id]
  associate_public_ip_address = true
  tags                        = { Name = "${var.name_prefix}-ec2" }
}
```

`modules/ec2/outputs.tf`:
```hcl
output "instance_id" { value = aws_instance.this.id }
output "public_ip" { value = aws_instance.this.public_ip }
```

### Step 4: The Root Module Orchestrator (`main.tf`)
In the root directory `day-027-tf/main.tf`, wire the three modules together:

```hcl
module "vpc" {
  source      = "./modules/vpc"
  vpc_cidr    = "10.27.0.0/16"
  subnet_cidr = "10.27.1.0/24"
  az          = "eu-north-1a"
  name_prefix = "day27-lab"
}

module "sg" {
  source           = "./modules/sg"
  vpc_id           = module.vpc.vpc_id
  allowed_ssh_cidr = var.allowed_ssh_cidr
  name_prefix      = "day27-lab"
}

module "ec2" {
  source        = "./modules/ec2"
  subnet_id     = module.vpc.subnet_id
  sg_id         = module.sg.sg_id
  instance_type = "t3.micro"
  name_prefix   = "day27-lab"
}
```

### Step 5: Initialize & Deploy
Whenever you add or modify module paths, you **must** run `init`:
```bash
terraform init
```
**Notice what happens:** Terraform reads the `source` arguments and indexes the modules in `.terraform/modules/modules.json`.

Now format, validate, and deploy:
```bash
terraform fmt -recursive
terraform validate
terraform apply -auto-approve
```
**Verification:** Run `terraform output`. All three modules deployed cleanly and are wired through explicit dependency parameters.

## Part 3: Break-It Lab — Module Wiring Triage (45 min)

We examine the two most common errors developers encounter when working with modules.

### Error 1: The "Module Not Installed" Trap
1. In root `main.tf`, add a dummy new module block:
   ```hcl
   module "database" {
     source = "./modules/db"
   }
   ```
2. Run `terraform plan` without running `terraform init`.
3. **Observed Symptom:**
   ```text
   Error: Module not installed
     on main.tf line 25:
     25: module "database" {
   This module is not yet installed. Run "terraform init" to install all modules required by this configuration.
   ```
4. **Lesson:** Unlike simple resource blocks, Terraform maintains a local module registry cache in `.terraform/modules/`. Whenever a new module is added, `terraform init` is mandatory. Remove the dummy block.

### Error 2: The "Unsupported Attribute" Encapsulation Trap
1. In root `main.tf`, try to access an internal resource directly instead of using the module's output:
   Change `subnet_id = module.vpc.subnet_id` to:
   ```hcl
   subnet_id = module.vpc.aws_subnet.public.id   # ERROR!
   ```
2. Run `terraform validate`.
3. **Observed Symptom:**
   ```text
   Error: Unsupported attribute
   This object does not have an attribute named "aws_subnet".
   ```
4. **Root Cause:** Encapsulation. Resources inside a child module are completely hidden from the outside world. The root module can **only** read values explicitly exposed in the child's `outputs.tf`.

## Part 4: Troubleshooting Record (15 min)

```markdown
## Troubleshooting Record — Day 27

**Problem:** Root configuration fails during `terraform validate` with `Error: Unsupported attribute` when referencing a child module resource.
**Symptoms:** Terraform reports object does not have the specified attribute; deployment blocked before plan phase.
**Environment:** AWS `eu-north-1`, Terraform CLI v1.5+, Modular Architecture (`modules/vpc`, `modules/sg`, `modules/ec2`).
**What I checked:**
1. Inspected child module `modules/vpc/main.tf` to verify the resource name (`aws_subnet.public`).
2. Checked child module `modules/vpc/outputs.tf` to see what outputs were exported.
3. Verified how the root module was referencing the child module's attribute.
**Commands used:** `terraform validate`, `cat modules/vpc/outputs.tf`.
**Evidence:** The root module attempted to read `module.vpc.aws_subnet.public.id` directly instead of referencing the exported output `module.vpc.subnet_id`.
**Hypothesis:** Child modules enforce strict encapsulation; internal resource blocks cannot be accessed directly without an explicit output block.
**Root Cause:** Direct resource addressing across module boundaries is prohibited in Terraform HCL.
**Fix:** Referenced the official exported output attribute `module.vpc.subnet_id` in root `main.tf`.
**Verification:** `terraform validate` returned `Success! The configuration is valid`; `terraform plan` calculated correct dependency graph.
**Prevention:** Always define clean, semantic outputs in `outputs.tf` for every resource attribute that downstream modules need to consume.
**What I learned:** Think of Terraform modules as black boxes: parameters enter via `variables.tf` and return values exit via `outputs.tf`. Nothing else is visible to the outside.
```

## Part 5: Job Readiness & Interview Defense (15 min)

### Feeder Role Connection

- **Ticket Scenario:** *"Our team is refactoring a 600-line monolithic Terraform configuration into modules. Why do we need this, and what happens to the provider blocks inside the child modules?"*

### Top 1% Fresher Interview Q&A (2026 Standards)

#### Q1: "What is the difference between a root module and a child module?"
- **Answer:** *"The root module is the top-level directory where you execute `terraform init`, `plan`, and `apply`. It configures the providers and backends. A child module is a self-contained subfolder containing `.tf` files that is called by another module using a `module` block. Child modules are reusable functions that inherit providers from the root."*

#### Q2: "Can a child module declare a `provider` or `backend` block?"
- **Answer:** *"No. Best practice strictly dictates that child modules must never declare provider or backend blocks. They should only declare `required_providers` specifying provider versions. The root module is responsible for defining the actual provider authentication and remote state backend. Child modules automatically inherit the root provider configuration."*

#### Q3: "What are the different types of module `source` addresses in Terraform?"
- **Answer:** *"There are three primary sources: (1) Local file paths like `./modules/vpc`, (2) Terraform Public or Private Registry like `terraform-aws-modules/vpc/aws`, and (3) Remote Git repositories like `git::https://github.com/org/repo.git?ref=v1.2.0` which allow version-pinning with Git tags."*
