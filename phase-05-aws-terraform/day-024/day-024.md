## Part 1: Why This Matters & The Core Mental Model (15 min)

In real companies, nobody clicks around in the AWS Console to launch infrastructure. Manual clicks are impossible to audit, easy to forget, and cannot be recreated if a region fails.

### Declarative vs Imperative
- **Imperative (Bash / Python scripts):** You tell the computer *every step*: *"Create a VPC, wait 5 seconds, create subnet 1, if it fails retry, then create subnet 2"*. If you run it twice, it crashes or duplicates resources.
- **Declarative (Terraform HCL):** You declare the *end state* you want: *"I want 1 VPC and 2 subnets"*. Terraform figures out which API calls to make. Running it multiple times produces the exact same outcome (**Idempotency**).

### The 3-Way State Machine
Terraform does not remember infrastructure in memory. It balances three realities:

```text
┌─────────────────┐       ┌──────────────────────┐       ┌─────────────────┐
│ Desired State   │       │ Recorded State       │       │ Physical State  │
│ (.tf files)     │ <───> │ (terraform.tfstate)  │ <───> │ (AWS Cloud API) │
└─────────────────┘       └──────────────────────┘       └─────────────────┘
```

1. **Desired State (`.tf` code):** What you wrote in your editor.
2. **Recorded State (`terraform.tfstate`):** A JSON ledger recording the mapping between your code names (`aws_vpc.main`) and real AWS IDs (`vpc-0abc1234`).
3. **Physical State (AWS):** What actually exists in Stockholm right now.

When you run `terraform plan`, Terraform refreshes against the AWS API, compares reality against your code, and calculates the exact diff (`+ create`, `~ update`, `- destroy`).

### Feeder Role Relevance
- **Cloud Support Associate / Junior DevOps:** In support tickets, customers report that `terraform plan` is trying to recreate existing servers. Knowing how the state file maps to AWS resource IDs allows you to identify missing state entries or configuration drift immediately.

## Part 2: Hands-On Build — Provider, VPC, and Subnets (45 min)

We build a clean VPC and two subnets from scratch using clean, modular code.

### Step 1: Configure Provider (`provider.tf`)
Create a dedicated working folder and add `provider.tf`:

```hcl
terraform {
  required_version = ">= 1.5.0"
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }
}

provider "aws" {
  region = "eu-north-1"
}
```

### Step 2: Initialize Terraform
Run in your terminal:
```bash
terraform init
```
**What happened under the hood?**
1. Terraform read `provider.tf`.
2. It contacted the HashiCorp Registry, downloaded the AWS provider plugin into a hidden `.terraform/` directory.
3. It created `.terraform.lock.hcl`. This lock file records the exact cryptographic SHA-256 hash of the provider plugin so every team member downloads the identical binary.

### Step 3: Write Infrastructure (`main.tf`)
Create `main.tf` and define your VPC and public subnet:

```hcl
resource "aws_vpc" "main" {
  cidr_block           = "10.24.0.0/16"
  enable_dns_support   = true
  enable_dns_hostnames = true

  tags = {
    Name = "day24-lab-vpc"
  }
}

resource "aws_subnet" "public" {
  vpc_id                  = aws_vpc.main.id
  cidr_block              = "10.24.1.0/24"
  availability_zone       = "eu-north-1a"
  map_public_ip_on_launch = true

  tags = {
    Name = "day24-lab-public-sub"
  }
}
```

### Step 4: Validate & Format (The Professional Standard)
Run these two commands before any deployment:
```bash
terraform fmt       # Automatically formats code to canonical HCL style
terraform validate  # Checks syntax, argument names, and types locally
```
Output: `Success! The configuration is valid.`

### Step 5: Plan and Apply
Run the dry-run plan:
```bash
terraform plan
```
Notice `Plan: 2 to add, 0 to change, 0 to destroy.` Notice also:
`vpc_id = (known after apply)`. 
Terraform automatically detected that `aws_subnet.public` requires `aws_vpc.main.id`. This is an **implicit dependency**. Terraform knows it must call `ec2:CreateVpc` first before calling `ec2:CreateSubnet`.

Deploy to AWS:
```bash
terraform apply -auto-approve
```
**Verification:** Open AWS Console -> VPC -> Subnets in Stockholm (`eu-north-1`). Both `day24-lab-vpc` and `day24-lab-public-sub` exist.

## Part 3: Break-It Lab — The CIDR Overlap Conflict (45 min)

Now we inject a real-world mistake: trying to provision a second subnet with an overlapping IP range.

### Step 1: Inject Conflicting Subnet
Append a private subnet to `main.tf`, but assign it the exact same CIDR as the public subnet:

```hcl
resource "aws_subnet" "private" {
  vpc_id            = aws_vpc.main.id
  cidr_block        = "10.24.1.0/24"   # ERROR: Overlaps with public subnet!
  availability_zone = "eu-north-1b"

  tags = {
    Name = "day24-lab-private-sub"
  }
}
```

### Step 2: Run `terraform plan`
Run:
```bash
terraform plan
```
**Surprise:** `terraform plan` reports: `Plan: 1 to add, 0 to change, 0 to destroy`. It does not show any error!

**Why did plan succeed?**
Terraform CLI validates syntax and checks the state file. It does not contain an internal IP calculator that simulates all AWS VPC routing rules.

### Step 3: Run `terraform apply`
Execute the deployment:
```bash
terraform apply -auto-approve
```
**Observed Symptom (Failure):**
```text
Error: creating EC2 Subnet: InvalidSubnet.Conflict: The CIDR '10.24.1.0/24' conflicts with another subnet
	status code: 400, request id: 12345678-xxxx-xxxx-xxxx-xxxxxxxxxxxx
```
**Diagnosis:**
1. The error came from the **AWS API** (HTTP 400), not the Terraform CLI.
2. Terraform successfully created the VPC previously and recorded it in `terraform.tfstate`. The VPC was not destroyed or damaged by this failed subnet call.
3. The CIDR block `10.24.1.0/24` is already bound to `eu-north-1a`. AWS subnets within the same VPC cannot overlap.

### Step 4: Apply the Fix
Edit `main.tf` and change the private subnet CIDR to a non-overlapping block:
```hcl
  cidr_block = "10.24.2.0/24"
```
Re-run:
```bash
terraform apply -auto-approve
```
**Verification:** `Apply complete! Resources: 1 added, 0 changed, 0 destroyed.` Both subnets now coexist cleanly.

## Part 4: Troubleshooting Record (15 min)

```markdown
## Troubleshooting Record — Day 24

**Problem:** `terraform apply` fails with `InvalidSubnet.Conflict` when provisioning a second subnet.
**Symptoms:** `terraform plan` succeeds, but `apply` returns AWS API Error: `InvalidSubnet.Conflict: The CIDR '10.24.1.0/24' conflicts with another subnet (status code: 400)`.
**Environment:** AWS `eu-north-1`, Terraform CLI v1.5+, AWS Provider ~> 5.0.
**What I checked:**
1. Ran `terraform validate` — syntax and HCL types were valid.
2. Inspected `main.tf` CIDR allocations for both subnets.
3. Checked `terraform.tfstate` to see if public subnet was already registered on `10.24.1.0/24`.
**Commands used:** `terraform plan`, `terraform apply`, `cat terraform.tfstate | grep cidr_block`.
**Evidence:** Both `aws_subnet.public` and `aws_subnet.private` declared `cidr_block = "10.24.1.0/24"` under the same VPC ID.
**Hypothesis:** `terraform plan` only verifies HCL syntax and state diffs, while AWS enforces IP uniqueness server-side during the API call.
**Root Cause:** Subnet CIDR collision within the same VPC.
**Fix:** Changed `aws_subnet.private` CIDR to `10.24.2.0/24` and re-ran `terraform apply`.
**Verification:** Subnet created successfully in `eu-north-1b`; AWS Console shows 2 active subnets under `day24-lab-vpc`.
**Prevention:** Plan IP subnetting schema in advance (e.g. `10.X.1.0/24` for public, `10.X.2.0/24` for private) and use Terraform CIDR functions (`cidrsubnet`) when scaling.
**What I learned:** A successful `terraform plan` does not guarantee AWS API acceptance. Server-side validation errors only surface during `apply`.
```

### Top 1% Fresher Interview Q&A (2026 Standards)

#### Q1: "What is the difference between `terraform plan` and `terraform apply`?"
- **Answer:** *" `terraform plan` is a read-only speculative execution. It queries the AWS API to refresh the current state, compares it with `.tf` code, and generates an execution plan without modifying cloud resources. `terraform apply` executes the generated plan by issuing authenticated REST API calls (like `CreateVpc` or `RunInstances`) to AWS, and updates the `terraform.tfstate` file with the returned resource IDs."*

#### Q2: "What is `terraform.lock.hcl` and why should it be committed to Git?"
- **Answer:** *"The dependency lock file records the exact version and cryptographic checksums (hashes) of provider plugins used. Committing it ensures that every engineer and the CI/CD pipeline run the exact same provider binary, preventing pipeline breaks caused by sudden minor version upgrades."*

#### Q3: "What happens if someone manually deletes an EC2 instance in the AWS Console, and you run `terraform plan`?"
- **Answer:** *"During `terraform plan`, Terraform performs a refresh phase where it queries AWS for the instance ID recorded in `terraform.tfstate`. AWS returns that the instance does not exist. Terraform updates its in-memory state and outputs a plan with `+ create` to recreate the instance so physical reality matches the code."*
