## Part 1: Why This Matters for Dorm-and-Dish (15 min)

Your Dorm-and-Dish backend reads dish images and menus from S3. In Days 20-22 you were the *caller* (SSH, curl). Today you are the *bouncer's boss* — you write the rules that decide which callers get through:

- **Identity policy (IAM)** = badge the person carries. "This app user may read this bucket."
- **Resource policy (S3 bucket policy)** = guest list on the door. "Nobody downloads except through the approved path — even badge-holders."
- **The conflict:** badge says YES, door list says NO → **NO wins. Always.** That sentence resolves half of all real-world 403 tickets.

| Concept | What it does | Dorm-and-Dish use |
|---|---|---|
| Explicit Deny | A `Deny` statement anywhere applicable → final answer Deny | Bucket policy Deny beats IAM Allow |
| Implicit deny (default deny) | No Allow anywhere → denied, no error detail | Fresh `day23-lab-app` with zero policies can't even ListBucket |
| Allow | Must exist in identity OR resource policy (same account) | `s3:GetObject` Allow on the app user |
| Permissions boundary / SCP | Ceilings that can only shrink access, never grow it | Theory today (Part 4) — you can't safely demo SCPs without an Organization |
| Policy Simulator | Console tool that shows which statement decided | Your proof instrument in Part 6 |

### Feeder Role Relevance

**Today's skill is relevant to:** Cloud Support Engineer, Junior Cloud Administrator, IAM Support, Cloud Security Trainee.

**Why:** "App worked yesterday, 403 today, nobody changed the app" is almost always a policy someone else edited — bucket policy, boundary, or SCP. Support engineers who can read the evaluation chain close these tickets in minutes.

## Part 2: The Evaluation Chain — Deny > Allow > Default-Deny (30 min)

**READING-FIRST (theory hour — read before building):**
AWS docs: "Policy evaluation logic" (IAM User Guide — search that exact title, open the `reference_policies_evaluation-logic` page). Read the same-account summary + the "difference between explicit and implicit denies" page.
Optional video: AWS official "IAM Policy Evaluation Chains Explained" (aws.amazon.com video hub, Nov 2024). Match by section title, not minute number.
Pause-and-do: (1) when the docs say "an explicit deny in any applicable policy overrides any allow", pause and write down which two policies in YOUR lab will play those roles (IAM inline `day23-lab-app-read` = Allow, bucket policy = Deny); (2) when you reach the permissions-boundary/SCP section, pause and write one sentence on why a boundary can never *grant* access; (3) after, run the Part 2 "Try It Now" and predict the Simulator verdict before clicking Simulate.

### The Problem

`day23-lab-app` currently has ZERO policies. It tries to read `menu.json`. What happens? Not "maybe" — **implicit deny**. AWS denies everything by default; the request dies before any policy is even consulted. Every 403 you will ever see is one of exactly three things: explicit Deny, missing Allow (implicit deny), or a ceiling (boundary/SCP) shrinking an Allow. Memorize that trio — Part 7's scenario is one of them in disguise.

### Build It Now — the Allow half (console clicks)

1. IAM → Users → `day23-lab-app` → Permissions tab → Add permissions → Create inline policy → JSON tab → paste:
```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowMenuReads",
      "Effect": "Allow",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::day23-lab-dish-assets/menu.json"
    }
  ]
}
```
Replace `` with yours. Name it `day23-lab-app-read` → Create policy.
2. Read the console's policy-check warnings (if any) — green "valid" is part of today's proof habit.

### Key facts (Level-2 core — the only 4 sentences that matter)

1. **Default deny:** no Allow anywhere → Deny. Silent, no explanation in the error.
2. **Explicit Deny wins:** one matching Deny in ANY applicable policy → final Deny, even with ten Allows.
3. **Same-account union:** Allow in identity policy OR resource policy suffices (S3 is the classic union case).
4. **Ceilings only shrink:** permissions boundaries, session policies, and SCPs intersect with Allows — they can remove access, never add it.

### Try It Now (Policy Simulator — predict first)

1. IAM → Users → `day23-lab-app` → **Simulate** (or open the IAM Policy Simulator, select the user) → Service S3 → Action `GetObject` → Resource ARN `arn:aws:s3:::day23-lab-dish-assets/menu.json` → Simulate.
2. Verdict now: **Allowed** (your inline policy). Screenshot it — Part 6 flips exactly this cell to Denied without touching the IAM policy.

2. Say aloud the trio: "403 means explicit Deny, missing Allow, or ___."
3. Answer: why does the Simulator say Allowed here even though no bucket policy exists yet? (Union rule — identity Allow suffices same-account.)

## Part 3: Bucket Policies — The Guest List on the Door (30 min)

### The Problem

IAM policies control *who the caller is*. Bucket policies control *the room itself* — they can grant access to strangers (cross-account) and, more importantly for today, **deny your own users** when a condition fails. Teams add "Deny unless request comes through our VPC endpoint" to force private-path traffic — then every laptop-direct and mis-routed call starts 403ing while IAM looks perfectly fine.

### Build It Now — read your (empty) guest list (console, read-only)

1. S3 → your bucket → Permissions tab → Bucket policy → **Edit** (don't save yet) → observe: empty. No statement = bucket policy contributes nothing; identity Allow decides alone.
2. Note the Block Public Access banner (all ON) — it stays on. Our Deny uses a condition key, not public access, so nothing here changes.

### Key facts

1. Bucket policies are **resource-based**: `Principal` field names who they hit (`*` = everyone including your own users).
2. A `Deny` with `*` principal + failing condition = your own IAM users get 403 despite their Allows. This is today's break, pre-staged.
3. `aws:SourceVpce` condition = "request arrived through this VPC endpoint". Real pattern for forcing private S3 traffic. You will write it with aVPCE ID that *doesn't exist in your path* — that's what manufactures the 403 on purpose.
4. Editing a bucket policy takes effect fast (~seconds). No propagation excuse in Part 6 — if it still works, your Deny JSON is wrong, not "still propagating".

### Exercise

1. In your own words: why can a bucket policy break your own app but an IAM policy can never break someone else's bucket?
2. Which principal value hits "everyone including day23-lab-app"? (Answer: `"AWS": "*"`.)
3. Predict: after Part 6 adds the Deny, will the Policy Simulator verdict from Part 2 change? (No — Simulator evaluates identity policies, not the live bucket call. The 403 proof comes from the real download, not the Simulator. Remember this in Part 9.)

## Part 4: Ceilings — Boundaries and SCPs (Theory Only, 20 min)

No console clicks. Read-only section — you do NOT build these today (boundaries need careful cleanup, SCPs need an Organization; both are easy to lock yourself out with at Level 2).

The mental model in one diagram — draw on paper:

```
Request → SCP allows? (if org exists; default FullAWSAccess = yes)
        → Identity policy allows? (day23-lab-app-read = YES for menu.json)
        → Bucket policy denies? (after Part 6 = YES → STOP, final Deny)
        → Boundary allows? (none attached = skip)
        → Decision: ALLOW only if an Allow exists AND zero Denys AND all ceilings pass
```

Three consequences worth memorizing:

1. **SCP Deny on `s3:*`** would 403 your app even with perfect IAM + bucket policies — and nothing you edit on either policy page would fix it. That's why "nobody changed the app" tickets escalate to the org admin.
2. **Permissions boundary** is an intersection: `Allows ∩ Boundary`. Attaching a boundary that lacks `s3:GetObject` silently 403s a previously working app.
3. **Interview trap:** "IAM Allows, no bucket policy, still 403 — what else?" Answer order: boundary on the user → SCP on the account → KMS key policy (if SSE-KMS object) → VPC endpoint policy (if routed through VPCE). Part 7 tests exactly this ordering instinct.

## Part 5: Least-Privilege Fix Pattern (20 min)

You will apply this in Part 6's fix step. Read now, execute later.

The broken state (Part 6) will be: IAM Allows `GetObject` on one object + bucket Denies `s3:Get*` for everyone except a VPCE that isn't in your path. The fix is NOT "delete the whole bucket policy" — in production that guest list protects real data. Least-privilege fix = **narrow the Deny to what it was meant to protect and add the matching Allow path**, or scope the Deny off your app's principal:

Option A (today's fix — smallest diff): change the bucket-policy Deny to exclude your app principal. Practically: delete the Deny statement (scratch lab, no real data) OR add `"StringNotEquals": {"aws:PrincipalArn": "<admin-arn>"}`-style carve-outs. In THIS lab, deleting the Deny is acceptable and you will state why (scratch bucket, zero real data, Block Public Access still on).

Option B (production pattern — understand, don't build): keep the Deny, route app traffic through the VPCE (gateway endpoint for S3 is free), grant the endpoint policy. Mention it in your Troubleshooting Record's Prevention line.

Rule of thumb for the interview answer: "I narrowed the Deny to the smallest scope that still enforced the intent, verified the Allow path, and left Block Public Access untouched."

3. Admin window: S3 → bucket → Permissions → Bucket policy = **empty**, Block Public Access = all ON.

Gate result: identity Allow works ✅, live download works ✅, no Deny anywhere ✅. Now you may break it.

### What We're Breaking

Drill A (core): add a bucket-policy explicit Deny (everyone except a VPCE that isn't in your request path) so the live download 403s while the IAM policy still Allows. Symptom: `Access Denied (403)` on the object, Simulator still says Allowed — the signature of a resource-policy Deny.

### Steps to Break It (admin window, console clicks, numbered)

1. S3 → your bucket → Permissions → Bucket policy → Edit → paste (fix ``):
```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyUnlessPrivatePath",
      "Effect": "Deny",
      "Principal": "*",
      "Action": "s3:Get*",
      "Resource": [
        "arn:aws:s3:::day23-lab-dish-assets/*",
        "arn:aws:s3:::day23-lab-dish-assets/*"
      ],
      "Condition": {
        "StringNotEquals": {
          "aws:SourceVpce": "vpce-0deadbeef00000000"
        }
      }
    }
  ]
}
```
2. Save changes. Wait ~30s. Touch nothing in IAM.

### Symptoms to Observe

Incognito (lab user) window: S3 → bucket → click `menu.json` → **Error: Access Denied (403)**. Refresh to be sure.
Admin window: re-run the Policy Simulator for the same action → still **Allowed**. Write both facts down — their contradiction IS the diagnosis.

Optional Drill B (if time): in the admin window, attach an inline Deny to the USER instead (`Effect: Deny`, `Action: s3:GetObject`, same resource, policy name `day23-lab-app-deny-test`) → Simulator flips to Denied → download still 403 → delete the inline Deny right after. Same verdict, different bouncer — proves identity-side Deny vs resource-side Deny both end at Deny.

## Part 7: Troubleshooting Challenge (30 min)

**Scenario-based debugging — answer before reading the chain.**

### Scenario

> Dorm-and-Dish images stopped loading at 11 AM. The app (IAM role `dish-api-role`) reads `s3:GetObject` from the menu-assets bucket — worked for months. No app deploy today. The bucket team "just tightened access" yesterday: new bucket policy denies `s3:Get*` unless `aws:SourceVpc` matches the prod VPC. Your laptop test with the app's keys also 403s. Teammate insists "IAM allows it, so AWS is broken." Standup in 30 minutes.

### Investigation Path (follow in order, don't skip)

1. **SYMPTOM:** 403 on GetObject from all paths (app + laptop keys) — started after a policy change, no app change.
2. **OBSERVATION:** IAM role policy unchanged (Allow present). Yesterday's change was bucket-side. So: identity half ✅ (unchanged), resource half ❌ (just edited).
3. **HYPOTHESIS:** New bucket Deny with `SourceVpc` condition fails for callers outside prod VPC (app runs in prod VPC? maybe not — or the condition key/value is wrong).
4. **CHECK:** S3 → menu-assets bucket → Permissions → Bucket policy tab. Read the Deny statement's Condition block.
5. **EVIDENCE:** Deny fires for any request whose source VPC ≠ prod (laptop keys always fail; app fails if it doesn't actually route through that VPC/VPCE).
6. **ROOT CAUSE:** Resource-policy explicit Deny overriding a valid identity Allow — condition scoped to a path the callers don't use.
7. **FIX (console):** Narrow the Deny (correct VPC ID / add VPCE exception / carve out the app role) — smallest scope preserving intent — or route callers through the approved path.
8. **VERIFY:** App image load 200; laptop direct still 403 (expected — proves the Deny still guards the wrong path); Simulator Allowed throughout (identity half was never broken).
9. **PREVENTION:** Policy changes get a Simulator + live-call test from BOTH paths (approved + unapproved) before merge; bucket-policy diffs reviewed like code; alarm on 4xx spike from the bucket.

## Part 8: Build Task — `policy-403-triage.sh` (60 min)

A 30-second triage script for "app gets S3 403" tickets. It checks the local half (credentials present? object path right?) and then prints the exact console screens for the policy half — because IAM/bucket/SCP evaluation is invisible from the box.

### Create the file (on any machine with bash — your EC2 or WSL/Git-Bash)

```bash
mkdir -p ~/devops-journey/day-23 && cd ~/devops-journey/day-23
nano policy-403-triage.sh
```

### Write this script (FULL code — copy-paste ready)

```bash
#!/bin/bash
# policy-403-triage.sh — "S3 403" triage for Dorm-and-Dish app buckets.
# Usage: ./policy-403-triage.sh <bucket> <key> [profile]
# Local half runs real checks; policy half prints the console path
# because IAM/bucket/SCP evaluation is invisible from the instance.
set -u

BUCKET="${1:-}"
KEY="${2:-}"
PROFILE="${3:-default}"
if [ -z "$BUCKET" ] || [ -z "$KEY" ]; then
  echo "Usage: $0 <bucket> <key> [profile]"
  exit 2
fi
echo "=== S3 403 triage — s3://$BUCKET/$KEY (profile: $PROFILE) ==="

echo "--- [1/4] Who am I? (credentials present?) ---"
if command -v aws >/dev/null 2>&1; then
  aws sts get-caller-identity --profile "$PROFILE" 2>&1 | head -5 || echo "MISS: no valid credentials for profile $PROFILE."
else
  echo "(aws cli not installed — check env/role attachment instead)"
fi

echo "--- [2/4] Does the object exist? (403 hides 404!) ---"
echo "(Run as ADMIN, not the app user:)"
echo "  aws s3api head-object --bucket $BUCKET --key $KEY --profile <admin>"
echo "If admin gets 404: object/key wrong — not a policy problem at all."

echo "--- [3/4] Identity half (Simulator verdict) ---"
echo "IAM -> Users/Roles -> <app-identity> -> Simulate: s3:GetObject on arn:aws:s3:::$BUCKET/$KEY"
echo "Allowed = identity half clean. Denied = fix the identity policy / boundary first."

echo "--- [4/4] Resource + ceiling half (console path, THIS order) ---"
cat <<'EOF'
1. S3 -> bucket -> Permissions -> Bucket policy tab: any Deny with Principal "*" whose Condition fails for your path? (Simulator-Allowed + live-403 lives HERE.)
2. S3 -> bucket -> Permissions -> Block Public Access: irrelevant for IAM 403s, leave it ON.
3. IAM -> user/role -> Permissions: permissions boundary attached? Boundary lacking s3:GetObject = silent 403.
4. KMS: object SSE-KMS? Key policy must allow the app identity too (second Deny surface).
5. ORG (escalate): SCP denying s3:* on the account? Nothing on IAM/S3 screens fixes that — org admin only.
Rule of thumb: Simulator-Allowed + live-403 = resource-policy Deny. Simulator-Denied = identity/boundary. All-paths-403-after-policy-change = read the diff of yesterday's edit.
EOF
echo "=== done ==="
```

### Make it executable + test it (dry run — needs no AWS access)

```bash
chmod +x policy-403-triage.sh
./policy-403-triage.sh day23-lab-dish-assets/* menu.json
```

Healthy output = the four printed checklists. The script's value is the ORDER (identity → resource → ceilings), not automation — automation can't see your console policies.

### What you just built

A reusable first-5-minutes tool for Dorm-and-Dish on-call: it separates "object doesn't exist" (head-object as admin) from "policy denies" (Simulator vs live-call split) and forces the console check order bucket-policy → boundary → KMS → SCP so you stop re-attaching IAM Allows to a Deny problem.

## Part 9: Root-Cause Discussion (15 min)

Why did Drill A behave the way it did?

- **Simulator stayed Allowed:** it evaluates the identity half (user policies + boundary), not the live resource policy on your call path. Allowed there + Denied live = the Deny lives outside the identity half. That contradiction is the whole diagnosis — no guessing needed.
- **Every path 403'd:** the Deny principal was `*` with a condition no incognito/console call could satisfy (fake VPCE ID). Union rule says one Allow suffices — but explicit Deny short-circuits the union before it matters.
- **Deleting the Deny fixed it instantly:** removing the only Deny restored union evaluation → identity Allow decides → download works. Block Public Access stayed on throughout, proving it was never the actor.
- **The mental model:** 403 = which of the trio? Explicit Deny (this drill) vs missing Allow (fresh user, Part 2) vs ceiling (Part 4 theory). Ask in that order — Deny first because one grep for `"Effect": "Deny"` across both policy screens answers it in seconds.
