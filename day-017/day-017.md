## Part 1: Why This Matters for Online-voting-system (10 min)

Right now, you push code to GitHub and... nothing happens. You have to manually build, test, and deploy. Every. Single. Time.

CI/CD automates this. Push code → tests run → image builds → deploys to AWS. No manual steps. No "it works on my machine" excuses.

| Concept | What it does | When I'd use it |
|---------|--------------|-----------------|
| Continuous Integration (CI) | Auto-run tests on every push | Every commit to main |
| Continuous Delivery (CD) | Auto-build + stage for deploy | After tests pass |
| Continuous Deployment (CD) | Auto-deploy to production | After staging passes |
| Pipeline | Sequence of automated steps | Every project |

## Part 2: CI vs CD vs CD — The Confusion (20 min)

### The Problem

Everyone says "CI/CD" like it's one thing. It's actually three different concepts that got mashed together. Let's untangle them.

### The Three Pillars

```
CI (Continuous Integration)
├── Trigger: git push
├── Actions: lint → test → build
└── Output: verified artifact (Docker image)

CD (Continuous Delivery)
├── Trigger: CI passes
├── Actions: push to registry → stage
└── Output: deploy-ready artifact (manual approval needed)

CD (Continuous Deployment)
├── Trigger: Delivery passes
├── Actions: deploy to production
└── Output: live in prod (no human involved)
```

### Real Example: Online-voting-system

**Without CI/CD:**
```
1. Write code locally
2. Run tests locally (maybe)
3. Build Docker image locally
4. Push to Docker Hub manually
5. SSH into server
6. Pull new image
7. Restart container
8. Pray it works
```

Time: 20-30 minutes per deploy. Error-prone. Forgettable steps.

**With CI/CD (GitHub Actions):**
```
1. git push origin main
2. GitHub Actions triggers automatically
3. Lint code
4. Run tests
5. Build Docker image
6. Push to ECR
7. Deploy to ECS
8. Health check passes
```

Time: 3-5 minutes. Zero manual steps. Repeatable.

## Part 3: Pipeline Stages — The Assembly Line (20 min)

### The Problem

A pipeline is just an assembly line for code. Each stage does one thing. If any stage fails, the whole pipeline stops. No broken code gets through.

### The Stages

```
┌─────────┐    ┌─────────┐    ┌─────────┐    ┌─────────┐
│  LINT   │───▶│  TEST   │───▶│  BUILD  │───▶│ DEPLOY  │
│         │    │         │    │         │    │         │
│ Style   │    │ Unit +  │    │ Docker  │    │ ECS /   │
│ check   │    │ integ   │    │ image   │    │ Lambda  │
└─────────┘    └─────────┘    └─────────┘    └─────────┘
     │              │              │              │
     ▼              ▼              ▼              ▼
   Fail?          Fail?          Fail?          Fail?
   STOP           STOP           STOP           STOP
```

### Stage Breakdown

| Stage | What it checks | Tool | Online-voting-system |
|-------|---------------|------|---------------------|
| Lint | Code style, syntax errors | ESLint, Prettier | React frontend linting |
| Test | Unit tests, integration tests | Jest, React Testing Library | Vote logic, auth flows |
| Build | Compile, bundle, create artifact | Docker, npm | Docker image for frontend |
| Deploy | Push to registry, update service | AWS ECR, ECS | Deploy to ECS cluster |

### Why Each Stage Matters

**Lint catches:**
- Unused variables
- Inconsistent formatting
- Syntax errors before they reach tests

**Test catches:**
- Broken functionality
- Regression bugs
- Edge cases

**Build catches:**
- Missing dependencies
- Environment issues
- Dockerfile problems

**Deploy catches:**
- Configuration errors
- Resource limits
- Network issues

## Part 4: GitHub Actions — Your Pipeline Engine (15 min)

### The Problem

You need a server to run your pipeline. GitHub gives you one for free — 2,000 minutes/month on public repos, 500 minutes on private.

### How GitHub Actions Works

```yaml
# .github/workflows/ci.yml
name: CI Pipeline

on:
  push:
    branches: [main]        # Trigger on push to main
  pull_request:
    branches: [main]        # Trigger on PR to main

jobs:
  lint-and-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4      # Clone repo
      - uses: actions/setup-node@v4    # Install Node
        with:
          node-version: '18'
      - run: npm ci                     # Install deps
      - run: npm run lint               # Lint
      - run: npm test                   # Test

  build:
    needs: lint-and-test               # Only if tests pass
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: docker build -t voting-frontend .
```

### Key Concepts

| Concept | What it means | Example |
|---------|--------------|---------|
| **Workflow** | The entire pipeline | "CI Pipeline" |
| **Job** | A group of steps | "lint-and-test" |
| **Step** | One command or action | "npm test" |
| **Action** | Reusable component | "actions/checkout@v4" |
| **Trigger** | When pipeline runs | "on: push" |

When setting up CI/CD for a new project:
1. **Start with CI** — lint + test on every push (Day 18)
