## Part 1: Why This Matters for Dorm-and-Dish (15 min)

In your `Dorm-and-Dish` repository, the AI-generated `main.tf` file has hardcoded values everywhere: hardcoded AMI IDs (`ami-0123...`), hardcoded instance types (`t2.micro`), hardcoded CIDR blocks, and hardcoded region strings.

### Why hardcoding fails in production:
1. **AMI IDs are region-specific:** An Amazon Linux AMI in `eu-north-1` has a completely different AMI ID than one in `us-east-1` or `eu-central-1`. If you run that code in another region, it crashes immediately.
2. **Environment replication:** You cannot reuse hardcoded code to create both a `dev` environment (`t3.micro`, small disk) and a `prod` environment (`t3.large`, bigger disk) without copy-pasting the entire file.
3. **No CI/CD handoff:** When your deployment pipeline finishes creating an EC2 instance, how does your automated test script know what IP address was assigned? Without Terraform `outputs`, external systems have to manually query the AWS API.

### Feeder Role Relevance
- **Junior Cloud Engineer / Cloud Support:** When customers submit tickets stating "Terraform throws InvalidAMIID.NotFound" or "Pipeline can't grab instance IP after provisioning", you must immediately recognize hardcoded variables and missing output blocks.
- **Junior DevOps:** Clean separation of configuration (`variables.tf`), execution logic (`main.tf`), and exported metadata (`outputs.tf`) is the baseline standard for any code review.

## Part 2: Input Variables — Definition & Types (30 min)

### The Problem
Yesterday in Day 24, we hardcoded `cidr_block = "10.24.0.0/16"` directly inside the resource block. If we wanted to change the network, we had to edit production code. We need a way to pass inputs into our configuration dynamically.

### Build It Now
1. Open your terminal and create a dedicated workspace folder for Day 25:
   ```bash
   mkdir -p D:\projects\Learning\devops-journey\01-daily-posts\day-025\day-25-tf
   cd D:\projects\Learning\devops-journey\01-daily-posts\day-025\day-25-tf
   ```
2. Create `provider.tf`:
   ```hcl
   terraform {
     required_version = ">= 1.5.0"
     required_providers {
       aws = {
         source  = "hashicorp/aws"
         version = "~> 5.0"
       }
     }
   }

   provider "aws" {
     region = var.aws_region
   }
   ```
3. Create `variables.tf`. This file acts as your input contract:
   ```hcl
   variable "aws_region" {
     description = "AWS region for all provisioned resources"
     type        = string
     default     = "eu-north-1"
   }

   variable "vpc_cidr" {
     description = "CIDR block for the lab VPC"
     type        = string
     default     = "10.25.0.0/16"
   }

   variable "public_subnet_cidr" {
     description = "CIDR block for the public subnet"
     type        = string
     default     = "10.25.1.0/24"
   }

   variable "instance_type" {
     description = "EC2 instance type"
     type        = string
     default     = "t3.micro"
   }

   variable "key_name" {
     description = "Name of existing EC2 Key Pair in eu-north-1"
     type        = string
     # No default provided on purpose! Terraform will prompt or require it from tfvars.
   }
   ```
4. Create `main.tf` referencing these variables using the `var.<variable_name>` syntax:
   ```hcl
   # VPC
   resource "aws_vpc" "lab_vpc" {
     cidr_block           = var.vpc_cidr
     enable_dns_support   = true
     enable_dns_hostnames = true

     tags = {
       Name        = "day25-lab-vpc"
       Environment = "lab"
     }
   }

   # Public Subnet
   resource "aws_subnet" "public_sub" {
     vpc_id                  = aws_vpc.lab_vpc.id
     cidr_block              = var.public_subnet_cidr
     availability_zone       = "${var.aws_region}a"
     map_public_ip_on_launch = true

     tags = {
       Name = "day25-lab-public-sub"
     }
   }

   # Internet Gateway
   resource "aws_internet_gateway" "lab_igw" {
     vpc_id = aws_vpc.lab_vpc.id

     tags = {
       Name = "day25-lab-igw"
     }
   }

   # Route Table
   resource "aws_route_table" "public_rt" {
     vpc_id = aws_vpc.lab_vpc.id

     route {
       cidr_block = "0.0.0.0/0"
       gateway_id = aws_internet_gateway.lab_igw.id
     }

     tags = {
       Name = "day25-lab-rt-public"
     }
   }

   # Route Table Association
   resource "aws_route_table_association" "public_assoc" {
     subnet_id      = aws_subnet.public_sub.id
     route_table_id = aws_route_table.public_rt.id
   }
   ```

## Part 3: Providing Variable Values & Precedence (30 min)

### The Problem
You cannot sit at a terminal and type variable values interactively in an automated CI/CD pipeline. You need automated, repeatable ways to pass variable values without modifying `.tf` code.

### Build It Now
Terraform looks for variable values in several places. The most common method is a `terraform.tfvars` file.

1. Create a file named `terraform.tfvars` in your directory:
   ```hcl
   aws_region   = "eu-north-1"
   instance_type = "t3.micro"
   key_name      = "day25-key"  # Set to your actual key pair name in eu-north-1
   ```
2. Any file named exactly `terraform.tfvars` is loaded **automatically** by Terraform during `plan` and `apply`.

### Variable Precedence Order (Lowest to Highest)
If the same variable is defined in multiple places, Terraform resolves it in this strict order:
1. **Default value** (inside `variable` block in `variables.tf`)
2. **Environment variable** (`TF_VAR_variable_name`, e.g. `export TF_VAR_key_name="day25-key"`)
3. **`terraform.tfvars` file**
4. **`*.auto.tfvars` files** (processed in alphabetical order)
5. **CLI `-var` or `-var-file` flags** (e.g. `terraform plan -var="instance_type=t3.small"`)

### Try It Now
Test overriding `instance_type` using the CLI flag:
```bash
terraform plan -var="instance_type=t3.small"
```
Notice that even though `variables.tf` has default `"t3.micro"` and `terraform.tfvars` has `"t3.micro"`, the CLI flag wins.

### Exercise
1. Run `terraform plan`. Does it prompt for `key_name` anymore? Why not? (Answer: No, because it read `key_name` from `terraform.tfvars`).
2. Why should `terraform.tfvars` often be added to `.gitignore` if it contains account IDs or database passwords? (Answer: To prevent committing sensitive configurations or environment-specific values to version control).

## Part 4: Security Group via Terraform (30 min)

### The Problem
An EC2 instance without a Security Group cannot receive inbound traffic (SSH, HTTP) and cannot communicate securely. In AWS Console click-ops, AWS silently attaches the "default" security group. In Terraform, you must explicitly declare security groups and rules.

### Build It Now
Add the Security Group resource to `main.tf`:

```hcl
# Security Group for EC2 Web Server
resource "aws_security_group" "web_sg" {
  name        = "day25-lab-ec2-sg"
  description = "Allow inbound SSH and HTTP traffic"
  vpc_id      = aws_vpc.lab_vpc.id

  # Inbound Rule: SSH (Port 22)
  ingress {
    description = "SSH from trusted IP"
    from_port   = 22
    to_port     = 22
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"] # In real production, restrict to your public IP /32
  }

  # Inbound Rule: HTTP (Port 80)
  ingress {
    description = "HTTP web traffic"
    from_port   = 80
    to_port     = 80
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]
  }

  # Outbound Rule: Allow all egress traffic
  egress {
    description = "Allow all outbound traffic"
    from_port   = 0
    to_port     = 0
    protocol    = "-1" # -1 means all protocols
    cidr_blocks = ["0.0.0.0/0"]
  }

  tags = {
    Name = "day25-lab-ec2-sg"
  }
}
```

### Critical Gotcha: Terraform vs Console Security Groups
When you create a Security Group in the AWS Console, AWS automatically creates an outbound "Allow All" egress rule. 
**Terraform DOES NOT do this.** If you omit the `egress` block in Terraform, your security group will have **ZERO** outbound access. Your EC2 instance won't be able to run `yum update`, reach package repositories, or talk to anything on the internet!

### Try It Now
Run:
```bash
terraform plan
```
Verify that Terraform plans to create `aws_security_group.web_sg` with 2 ingress rules and 1 egress rule.

## Part 5: Dynamic AMI Lookup & EC2 Instance (30 min)

### The Problem
Hardcoding an AMI ID like `ami-0abcdef1234567890` is dangerous. AWS rotates and deprecates AMIs regularly, and IDs differ across regions. We need Terraform to automatically discover the latest official Amazon Linux 2023 AMI in whatever region we run in.

### Build It Now
1. In `main.tf`, add an `aws_ami` data source block. A `data` source reads existing information from AWS without creating a new resource:
   ```hcl
   # Look up the latest official Amazon Linux 2023 AMI
   data "aws_ami" "amazon_linux_2023" {
     most_recent = true
     owners      = ["amazon"]

     filter {
       name   = "name"
       values = ["al2023-ami-2023.*-x86_64"]
     }

     filter {
       name   = "virtualization-type"
       values = ["hvm"]
     }
   }
   ```
2. Add the EC2 instance resource block referencing our subnet, security group, key pair, and dynamic AMI:
   ```hcl
   # EC2 Web Server Instance
   resource "aws_instance" "web_server" {
     ami           = data.aws_ami.amazon_linux_2023.id
     instance_type = var.instance_type
     key_name      = var.key_name

     subnet_id                   = aws_subnet.public_sub.id
     vpc_security_group_ids      = [aws_security_group.web_sg.id]
     associate_public_ip_address = true

     # Bootstrap a minimal web server using user_data
     user_data = <<-EOF
                 #!/bin/bash
                 dnf update -y
                 dnf install -y httpd
                 systemctl start httpd
                 systemctl enable httpd
                 echo "<h1>Day 25: Terraform EC2 Provisioning Successful</h1><p>Instance: $(hostname -f)</p>" > /var/www/html/index.html
                 EOF

     tags = {
       Name        = "day25-lab-web-server"
       Environment = "lab"
     }
   }
   ```
3. Create `outputs.tf` to export computed attributes so you don't have to search the AWS Console for them:
   ```hcl
   output "vpc_id" {
     description = "ID of the lab VPC"
     value       = aws_vpc.lab_vpc.id
   }

   output "instance_id" {
     description = "ID of the provisioned EC2 instance"
     value       = aws_instance.web_server.id
   }

   output "instance_public_ip" {
     description = "Public IPv4 address of the EC2 instance"
     value       = aws_instance.web_server.public_ip
   }

   output "instance_public_dns" {
     description = "Public DNS of the EC2 instance"
     value       = aws_instance.web_server.public_dns
   }

   output "website_url" {
     description = "Direct HTTP URL to the test page"
     value       = "http://${aws_instance.web_server.public_ip}"
   }
   ```

### What We're Breaking: Key Pair Region Mismatch
Key Pairs in AWS are strictly **regional** resources. A key pair created in `us-east-1` or `ap-south-1` does NOT exist in `eu-north-1` unless manually imported there.

We will set the `key_name` variable to a key name that exists in another region or does not exist in `eu-north-1`.

### Steps to Break It
1. Open `terraform.tfvars`.
2. Modify `key_name` to point to a non-existent or wrong-region key:
   ```hcl
   key_name = "mumbai-production-key"  # Does NOT exist in eu-north-1!
   ```
3. Run `terraform plan`:
   ```bash
   terraform plan
   ```
   **Observation:** Notice that `terraform plan` says:
   `~ update in-place` or proposes to replace the instance. It reports **SUCCESS**! It finds zero errors with the key name.
4. Now execute the change:
   ```bash
   terraform apply -auto-approve
   ```

### Symptoms to Observe
The terminal immediately halts with an AWS API crash:
```text
Error: creating EC2 Instance: InvalidKeyPair.NotFound: The key pair 'mumbai-production-key' does not exist
  with aws_instance.web_server,
  on main.tf line 20, in resource "aws_instance" "web_server":
  20: resource "aws_instance" "web_server" {
```

2. **What does `InvalidKeyPair.NotFound` tell you about where AWS validates key pairs (client-side vs AWS API server-side)?**
3. **If this happened in production, what command would you run to list all valid key pairs in `eu-north-1`?**

1. List the valid key pairs in `eu-north-1`:

3. Re-run `terraform apply -auto-approve`.

## Part 7: Troubleshooting Challenge (30 min)

### Real-World Incident Scenario
> A developer on your team changed the `instance_type` in `variables.tf` to `default = "t3.nano"`, but in production, `terraform apply` unexpectedly launched a `t3.large` instance instead! 
> The company received an unexpected billing alert. Management asks: "Why did Terraform ignore the default variable?"

### Investigation Path
1. **SYMPTOM:** Terraform deployed `t3.large` despite `variables.tf` stating `default = "t3.nano"`.
2. **OBSERVATION:** Check where `instance_type` might be assigned elsewhere in the project directory or environment.
3. **HYPOTHESIS:** A source higher in the Terraform Variable Precedence hierarchy overrode the default value.
4. **CHECK:**
   - Step A: Check `terraform.tfvars` for `instance_type`.
   - Step B: Check for any `*.auto.tfvars` files in the directory.
   - Step C: Check the terminal shell environment for `TF_VAR_instance_type`.
   - Step D: Check the CI/CD pipeline command line for `-var="instance_type=t3.large"`.
5. **EVIDENCE:** In the shell environment, running `echo $env:TF_VAR_instance_type` (PowerShell) or `env | grep TF_VAR` revealed `TF_VAR_instance_type=t3.large` had been exported by a developer during an earlier debugging session.
6. **ROOT CAUSE:** Variable precedence. Environment variables (`TF_VAR_*`) and `terraform.tfvars` override the `default` defined in `variables.tf`.
7. **FIX:** Unset the environment variable (`Remove-Item Env:\TF_VAR_instance_type` in PowerShell or `unset TF_VAR_instance_type` in Linux/Mac) and run `terraform plan` to confirm the desired instance type.
8. **VERIFY:** `terraform plan` now shows `instance_type: "t3.large" => "t3.nano"`.
9. **PREVENTION:** Never rely solely on variable defaults for critical production sizing. Explicitly pass an environment-specific `.tfvars` file (e.g. `terraform apply -var-file="prod.tfvars"`) in automated pipelines.

```hcl
  description = "HTTP URL to access Apache test page"
  value       = "http://${aws_instance.web_server.public_ip}"
}
```

3. Run `terraform apply -auto-approve`.
4. Run `terraform output`.
5. Curl the `website_url` output or visit it in your browser.

## Part 9: Root-Cause Discussion (15 min)

### The Question:
*Why does `terraform plan` pass cleanly when you specify a nonexistent `key_name` or invalid IAM role, only to crash during `terraform apply`?*

### The Technical Answer:
1. **Schema Validation vs State Validation vs Provider API Execution:**
   - When you execute `terraform plan`, Terraform checks:
     - Is the syntax valid HCL? (Yes)
     - Does the `aws_instance` resource schema accept a string argument named `key_name`? (Yes, it is a valid string attribute)
     - Are internal dependencies resolved? (Yes)
   - However, Terraform does **NOT** call the AWS EC2 `DescribeKeyPairs` API for every string attribute during `plan`. Key pairs are referenced as plain strings, not as first-class Terraform resource references with implicit dependencies.
2. **When the Crash Occurs:**
   - During `terraform apply`, Terraform makes the actual REST API call: `ec2:RunInstances` with parameter `KeyName: "mumbai-production-key"`.
   - The **AWS EC2 Control Plane** validates the request parameters against the regional database. Because that key pair does not exist in `eu-north-1`, the AWS API returns an HTTP 400 Client Error: `InvalidKeyPair.NotFound`.
   - Terraform intercepts the error code from the HTTP response, marks the resource as failed in the execution graph, and halts.

```markdown
**Problem:** Terraform apply failed with `InvalidKeyPair.NotFound` while provisioning an EC2 instance.
**Symptoms:** `Error: creating EC2 Instance: InvalidKeyPair.NotFound: The key pair 'mumbai-production-key' does not exist`.

**What I checked:** 
1. Verified that `terraform plan` had passed with zero warnings.
2. Read the error message indicating `InvalidKeyPair.NotFound`.
3. Ran `aws ec2 describe-key-pairs --region eu-north-1` to list all existing keys in the active region.
**Commands used:** 
- `terraform apply`
- `aws ec2 describe-key-pairs --region eu-north-1 --query "KeyPairs[*].KeyName" --output text`
**Evidence:** The key pair name in `terraform.tfvars` was created in another region and did not exist in `eu-north-1`.
**Hypothesis:** Key pairs are regional AWS resources; passing an out-of-region key name causes the AWS RunInstances API call to reject the request.
**Root Cause:** Hardcoded or incorrect string passed to the `key_name` variable in `terraform.tfvars`. `terraform plan` only performs schema validation and does not verify string existence against the AWS API.
**Fix:** Corrected `key_name = "day25-key"` in `terraform.tfvars` to match an existing key pair in `eu-north-1`, then re-ran `terraform apply`.
**Verification:** Instance was provisioned, status checks reached 2/2, and Apache test page loaded on the public IP.
**Prevention:** In multi-region deployments, either manage the key pair as a Terraform resource (`aws_key_pair`) using an exported public key, or validate key availability in the target region before running the deployment pipeline.
**What I learned:** Terraform plan checks schema and graph logic, not cloud provider resource existence for plain string references.
```

## Part 11: Job Readiness (10 min)

### Interview Question:
*"Explain the difference between Terraform input variables and outputs. How does Terraform determine variable precedence if a variable is defined in multiple places?"*

### Strong Answer:
"Input variables parameterize a Terraform module so the same infrastructure code can be deployed across different environments or regions without modifying the resource blocks. Outputs export computed resource attributes—like an EC2 instance's dynamically allocated public IP or a VPC ID—so they can be queried on the CLI or passed to downstream modules and CI/CD pipelines.

When resolving variable values, Terraform follows a strict precedence hierarchy. From lowest to highest:
1. Default values in the variable definition block.
2. Environment variables prefixed with `TF_VAR_`.
3. The `terraform.tfvars` file.
4. `*.auto.tfvars` files in alphabetical order.
5. Command-line `-var` or `-var-file` flags, which always have the final word."

## Part 12: Recap (10 min)

### Concept Summary Table

| Concept | File / Syntax | Purpose |
|---|---|---|
| Variable Declaration | `variable "name" { type = string }` in `variables.tf` | Defines input parameters, types, and defaults |
| Variable Assignment | `name = "value"` in `terraform.tfvars` | Supplies actual environment values |
| Variable Reference | `var.name` in `main.tf` | Uses variable value inside a resource block |
| Output Export | `output "name" { value = ... }` in `outputs.tf` | Exposes computed attributes after apply |
| Dynamic AMI | `data "aws_ami" "name"` | Discovers regional AMIs dynamically from AWS |
| CLI Query | `terraform output <name>` | Retrieves specific output value without console |

### The Pattern: Parameterized Infrastructure Flow
1. **Declare the contract:** Define inputs in `variables.tf`.
2. **Provide values:** Set specific values in `terraform.tfvars`.
3. **Reference dynamically:** Use `var.*` and `data.*` in `main.tf`.
4. **Export results:** Expose necessary endpoints in `outputs.tf`.
5. **Validate & Plan:** Run `terraform validate` then `terraform plan`.
6. **Apply & Verify:** Run `terraform apply`, then test outputs.
